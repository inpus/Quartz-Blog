# 音频播放后视频无变化

这次排查先后遇到了视频等待音频、音频断续、服务器断流三个现象。表现相近，但发生在不同环节，需要分别根据日志判断。

## 一、最初现象：播放声音后视频不再更新

音频和鼠标控制仍能工作，但拉流端看不到画面变化。

早期推流统计摘录如下，箭头为排查时添加的说明：

```text
16:17:25.607  push=130  blocked=0  bytes=629KB    audio: 0
16:17:29.633  audio pkt=310 ...                   ← 音频开始
16:17:30.812  push=129  blocked=0  bytes=3348KB   audio: push=51
16:17:35.987  push=130  blocked=0  bytes=3423KB   audio: push=39
16:17:41.162  push=128  blocked=0  bytes=3888KB   audio: 0
```

服务器另一次统计中也出现了：

```text
[STAT] rtmp recv 5s: video=127 (731KB, key=4) audio=0 (0KB) vts=80225ms ats=42031ms stream=/live/2
```

这说明该窗口内仍收到视频，但没有新音频。`vts`、`ats` 是最近收到的对应媒体时间戳，没有新音频时，`ats` 会停留在旧值。

### 原因：视频一直等待停止更新的音频时钟

当时拉流端存在以下行为：

1. 音频时钟只在写入新音频数据时更新。
2. 视频领先音频超过约 50 ms，就进入等待循环，缺少超时回退。
3. 音频中断后，时钟停止更新；视频继续到达，但视频线程一直等待，旧帧积压。
4. 原时钟按累计音频播放量推进，没有正确覆盖音频 PTS 的间隙，声音恢复也不一定能立即恢复画面。

有视频数据到达，不代表视频线程能走到显示画面的步骤。

### 曾经的误判：把问题归因于音频格式

排查中曾怀疑采集格式、拷贝字节数和 AAC 输入格式不匹配。但不能由上述时间戳统计推导这个结论，也没有建立“格式错误导致视频无限等待”的完整证据链，因此不将其记录为本次已验证根因。

描述格式时还应区分：32 位浮点 PCM 不等于 `AV_SAMPLE_FMT_S32`；交错与平面是另一项区别，不能混写。

## 二、第一轮修改：让视频不再无限等待

### 1. 视频临时改用单调主时钟

通过起始视频 PTS 和 `steady_clock` 的经过时间建立播放时间轴：

```text
当前媒体时间 = 起始视频 PTS + 单调时钟经过的时间
```

音频中断后时间轴仍能前进；明显的时间戳跳变或长时间卡顿后，再重新对齐。

### 2. 限制视频和界面刷新积压

这一版解码队列上限为视频 3 帧、音频 8 帧，优先保留新画面，合并 Qt 刷新请求。严重的压缩视频积压则等待下一个 IDR 恢复解码。

### 3. 固定约 10 ms 混音

混音线程按固定采样节奏读取系统音和麦克风；一路缺数据就补零，两路都缺数据也继续编码静音。麦克风不再依赖系统音回调才能送出。

这一版采用带时间戳的 PCM 缓冲，后续发现其读取窗口对齐会损伤采样连续性。

### 4. 按编码包 PTS 发送音频

AAC 编码存在缓存和延迟，“这次输出的包”不一定对应“这次刚输入的声音”。发送时间戳使用编码包 PTS 换算后的媒体时间，而非编码函数返回时的当前时间。

### 5. 调整线程和退出顺序

音频输出设备在音频线程内创建、使用和释放；推流时间基准加锁；退出时先停止采集与编码，再释放推流器。

**这一轮反馈：播放声音时，控制和画面更新能够继续。但系统音从开始就频繁断续。**

## 三、音频断续：推流端和拉流端各有一处问题

添加 `[AMIX]`、`[AENC]`、`[ADEC]`、`[APLAY]`、`[ASINK]` 日志，分别观察混音、编码、解码、播放调度和输出设备。

### 1. 推流端边丢 PCM、边补静音

有系统音输入的一个 5 秒窗口，关键字段为：

```text
rate=44100 ticks=501
sysIn=220864 sysRead=210305
sysPad=10636 sysPadPct=4.813955
lateDiscard=10697 capacityDrop=0
```

按 501 次、每次 441 个采样帧计算，需要 220941 个采样帧，实际输入数量接近这个值。但仍丢掉 10697 个采样帧、补入 10636 个静音采样帧，分别约为 243 ms 和 241 ms。

说明按时间戳窗口对齐时，一部分已有声音被判为过期丢弃，再用静音补足输出，采样连续性受到损伤。仅凭汇总日志，不能进一步区分采集时间戳间隙和对齐策略各自的影响。

> [!warning]
> 没有播放声音时，`sysIn=0`、`sysPadPct=100%` 可以是预期的连续静音输出，不能单凭补零比例高就认定采集故障。

### 2. 拉流端按 150 ms 门限主动丢音频

拉流端另一个窗口的日志摘录：

```text
[APLAY] dtMs=5000 written=131 lateDrop=87
lateDropMs=2020.053000 lateMaxMs=190.812000
bufferMinMs=0.000000 queue=0
```

这个窗口主动丢弃了 87 个解码后的音频帧，合计约 2.02 秒声音，输出缓冲也曾耗尽，会直接造成断续。

`lateMaxMs` 是音频相对当时主时钟的落后量，包含采集、编码、传输、排队和播放时间轴关系，**不能直接等同于网络传输抖动**。

这一轮断续存在两个因素，不能全部归因于推流端补静音，或全部归因于拉流端丢音频。

## 四、第二轮修改：FIFO 连续读取，音频设备进度作为主时钟

### 推流端

- 系统音和麦克风分别进入 FIFO，混音仍由固定采样节奏驱动。
- 按顺序连续读取 PCM，采集块时间戳只用于诊断，不再按时间戳窗口裁剪正常数据。
- 数据不足时补零，保持输出音轨连续；预留少量启动缓冲，并限制真正的积压。
- 发送时间戳继续由采样时间轴和 AAC 编码包 PTS 确定。

FIFO 不表示永远不丢数据：超过容量的实际积压仍会被限制，但正常采集块不会再因窗口对齐而被裁剪。

### 拉流端

通过 `QAudioSink::processedUSecs()` 获取设备报告的处理进度，并映射回音频帧 PTS。静音 PCM 也会推进这个进度。

- 取消普通播放阶段“落后 150 ms 就丢音频”的策略，输出缓冲目标约 100 ms。
- 没有新包写入时，也定期刷新音频时钟。
- 设备空闲、不可用或进度停滞超过约 100 ms 时，使用单调时钟回退；恢复后重新以音频设备进度为准。
- 视频跟随健康的音频主时钟，保留丢旧视频帧、等待上限和界面刷新合并。
- 当前解码队列上限为视频 12 帧、音频 24 帧。严重断流恢复、明显 PTS 跳变仍单独处理，不代表任何情况下都不丢音频。

**这一轮反馈：音频连续，但停止声音后，画面又停止更新。** 需要重新检查数据是否到达，不能直接判断又是音频时钟停住。

## 五、发现并修复客户端 IOCP 重复完成通知

服务器曾出现异常 RTMP 消息类型。检查客户端后发现：未开启“立即成功时跳过完成通知”的模式，`WSARecv()`、`WSASend()` 立即成功时，系统仍会投递完成通知，代码却又手动投递了一次，存在重复通知及错误关联后续操作的风险。

修改为：

```text
立即成功或 WSA_IO_PENDING：等待系统完成通知
真正提交失败：手动投递一次异步错误通知
```

保留音视频日志，补充 `[IOCP]` 提交失败、未知完成事件诊断，版本标记为 `iocp_fix=v1_os_completion`。

**修复后，停止声音导致冻结仍然复现。** IOCP 是已发现的独立缺陷，不能写成所有冻结现象的唯一原因。

## 六、最新定位：服务器因包头不完整主动断流

### 1. 拉流端主时钟仍在前进，但没有新音频包

以下为日志关键字段摘录：

```text
14:31:11.811 [AMASTER] source=steady_fallback audioMs=16618 masterMs=16618
14:31:17.793 [ADEC] packets=0 decoded=0
14:31:30.013 [APLAY] source=steady_fallback written=0 masterMs=34820
```

回退主时钟继续增长，但解码器没有新音频包，和最初“视频数据继续到达，却一直等待旧音频时钟”的情况不同。

### 2. 服务器明确记录了关闭推流连接

```text
14:30:40.090 Buffer is not enough for message header 5 < 12
14:30:40.090 closing connection on socket 15
14:30:40.090 Event: publish,stop, Stream Path: /live/2
```

断开前，仍收到 PTS 为 `16595 ms`、消息体为 8 字节的静音 AAC 数据，以及 PTS 为 `16694 ms` 的视频。

两台机器的系统时间相差约 31.6 秒，应结合媒体 PTS 对照，不能直接相减两端日志时间来计算传输延迟。

### 3. 消息体有半包处理，包头处理却不一致

```cpp
// 原消息体处理：不足时等待。
if (buf_size < chunk_size) {
    return 0;
}

// 原包头处理：不足时却返回错误。
if (buf_size < bytes_read + msg_header_len) {
    return -1;
}
```

上层收到 `0` 就结束本次解析、保持连接；收到负值则返回失败并关闭连接。因此准确说法是：**遗漏了包头不完整时的等待处理**，而非完全没有半包处理。

### 4. 包头和消息体为什么会分开？

包头描述类型、时间戳、长度等信息，消息体承载实际音视频数据。这里具体指 RTMP chunk 头，较大消息的消息体还会分成多个 chunk。

TCP 不保证一次接收对应一个完整 chunk。例如可能读到：

```text
[前一个 chunk 的剩余内容][下一个 chunk 包头的前 5 字节]
```

解析完前面的内容，只剩 5 字节。它是缓冲区当前可读长度，不是客户端专门发送的“5 字节包”。上述排列是机制示例，现有日志无法还原当时完整的接收边界。

`Retrieve(len)` 只移动读位置，未读完的数据仍在原缓冲区。后续接收本来可以追加，但原代码在这之前已经关闭连接。

正确流程是：

```text
包头不足 → 保留缓冲区，返回 0 → 结束本次解析，保持连接
→ 下次接收追加数据 → 包头完整后继续解析
```
