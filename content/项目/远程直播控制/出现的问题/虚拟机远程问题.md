> 发现是transport error, error=10053
> csid = 3 RTMP_CHUNK_INVOKE_ID  = 3;   // 命令消息（AMF invoke）← 你看到的 csid=3
> payload_szie = 26 = createStream； 35 = deleteStream

#### 原因可能

> 客户端在 publish 完成之前就发视频帧 → 服务端还没建 session → 拒收并关连接 → RST → 客户端收到 10053。
- 证据: 只要connect就可以pushvideo了
```c++
bool RtmpPublisher::IsConnected()
{
    if(rtmp_conn_ && !rtmp_conn_->IsClosed()){
        return true;                 // ← 只要 socket 在，就返回 true
    }
    return false;
}
```
```c++
// RtmppushManager.cpp:906
void RtmpPushManager::PushVideo(const quint8 *data, quint32 size, uint64_t timestamp_us)
{
    if(size == 0 || !data || !pusher_ || !pusher_->IsConnected()){
        return;
    }
    pusher_->PushVideoFrame(const_cast<uint8_t*>(data), size, timestamp_us);
}
```
##### 2个状态机不同步，进行提前发送

```text
t=0ms      信令 cmd=7 到达 → state_ = PUSHER          ← 业务说"可以推了"
t=0ms      Open() → TCP connect 开始（异步）
t=0ms      编码线程启动 → 第一帧 33ms 后出来
           ┌──────── RTMP 协议在慢慢走 ────────┐
t=5ms      connect 完成
t=20ms     createStream 完成
t=40ms     publish 发出 → 这时服务端才有 session
           └──────────────────────────────────┘
```
- 信令状态
```text
NONE → IDLE → PUSHER / PULLER
```
用来判断当前流的状态
- RTMP 状态
```c++
enum ConnectionState
{
    HANDSHAKE,              // 构造时
    START_CONNECT,          // :334 发 connect 之后
    START_CREATE_STREAM,    // :349 发 createStream 之后
    START_DELETE_STREAM,    // :377 发 deleteStream 之后
    START_PUBLISH,          // :362 发 publish 之后  ← 闸门要等这个
};
```
#### 总原因

> 导致信令为`PUSHER`,但是RTMP状态仍在CONNECT,最后服务器收到信息给客户端判断错误，最后关闭连接
> 而本机进行测试没出现问题是因为RTMP状态交换比较快，导致没有问题


### 解决

> 直接判断rtmp状态是否到publish再发送数据
