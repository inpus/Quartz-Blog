# 拉流窗口关闭问题

## openglwidget关闭不会停止拉流和推流

## 情况

关掉远程预览窗口之后，出现了三件不该发生的事：

- 控制端本地还在拉流（`av_read_frame` 一直在读）
- 被控端还在采集和推流（屏幕还在抓、NVENC 还在编码）
- 两边 CPU / GPU 占用不降，只有下次点「开始控制」把旧窗口顶掉才会停

## 根因

不是一个 bug，是三个缺口叠在一起。

### 缺口一：关窗只是 hide，对象没死

`PullerWgt` 由 `RemoteManager` 的 `unique_ptr` 持有，且没有设置 `Qt::WA_DeleteOnClose`。

```cpp
// 关闭窗口 === QWidget::close()
// 没有 WA_DeleteOnClose 时，它只做两件事：隐藏 + 记一个 WA_WState_Hidden
// 对象不析构 → ~AVPlayer 不执行 → 停流代码根本没机会跑
```

而停流逻辑全在析构里：`~PullerWgt → ~AVPlayer → Close()`。窗口一藏，这条链就断了。
拉流线程和解封装线程都是 `while(...)` 死循环，没人置退出标志，它们就一直跑。

### 缺口二：关窗不发消息，服务端不知道

采集和推流的生命周期**只由信令驱动**：

```text
服务端 DELETESTREAM(stream_count == 0)  →  被控端 stopStreamCb_  →  RtmpPushManager::Close()  →  停采集
```

服务端发这条消息的唯一入口是 `SigConnection::Clear()`，而它只由「客户端主动发 DELETESTREAM」或「TCP 断开」触发。

窗口 hide 既不发包也不断 TCP，所以整条通知链一根线都没被碰到。

> 顺带一个更隐蔽的问题：`RtmpPushManager` 从不订阅推流器的断开回调。
> 就算服务端把 RTMP 连接硬踢掉，采集线程也不会停，只是帧被丢掉——看起来像停了，机器还在烧。

### 缺口三：RTMP 层没有「没人看就停」的判断

`RtmpSession::RemoveSink` 在观众退出时只清 SPS/PPS，不发任何通知。
`RtmpServer` 那个 3 秒定时器只负责把空 session 从 map 里删掉，而且 `GetClients()` 把主播也算进去了，只要推流端在，session 永远删不掉。

## 修复总览

三条路径各自负责一类场景，任何一条生效都能停下来：

```text
路径 A（正常关窗）
  点 X → PullerWgt::closeEvent → AVPlayer::Shutdown()
       → 发 DELETESTREAM → 服务端 Clear/Detach → 通知被控端 stream_count=0
       → 被控端停采集
       → 同时本地 join 播放线程、释放 demuxer、断信令连接

路径 B（客户端崩溃 / 断网 / 机器断电）
  客户端停止心跳 → 服务端 15s 收不到 → 判定连接已死 → Disconnect
       → 走和 A 一样的清理 → 通知被控端停推

路径 C（服务端判定无人观看）
  最后一个观众离开 → 20s 宽限期定时器 → 到期复查仍为 0
       → 断开推流端的 RTMP 连接
       → 被控端 monitorLink() 发现连接断了 → UI 调 Close() 停采集
```

## 客户端改动

### 1. 关窗要真的停：`PullerWgt::closeEvent`

```cpp
void PullerWgt::closeEvent(QCloseEvent *event)
{
    if(player_){
        player_->Shutdown();   // 先停流、通知服务器，再谈销毁
    }
    QMainWindow::closeEvent(event);
    emit sig_closed();         // 交给 RemoteManager 排队销毁
}
```

> 不在 `closeEvent` 里 `delete this`。此时 Qt 的 close 流程还没走完，销毁窗口会让它访问已释放的成员。

### 2. 停流要分两种：`Stop` 和 `Shutdown`

原来的 `Close()` 只 join 线程，既不通知服务器，也不复位状态，关掉之后再想拉流会崩。拆成两个语义：

| 方法 | 做什么 | 用在哪 |
| :--- | :--- | :--- |
| `Stop(bool notifyServer)` | 停播放线程 + 释放 demuxer + 清队列，**保留信令连接** | 服务端说「对端不推了」时 |
| `Shutdown()` | `Stop(true)` + 断信令连接 + 释放解码上下文 | 关窗、析构 |

顺序不能换：

```cpp
void AVPlayer::Stop(bool notifyServer)
{
    if(stopped_) return;
    stopped_ = true;
    stop_.store(true);

    // 1) 先发消息：必须在连接还活着的时候
    if(notifyServer && sig_conn_ && !sig_conn_->IsClosed()){
        sig_conn_->SendDeleteStream();
    }

    // 2) 停播放线程：必须在 demuxer 复位之前 join，
    //    否则它们会并发读一个正在析构的 unique_ptr
    if(audioThread_ && audioThread_->joinable()) audioThread_->join();
    ...
    // 3) 释放解封装器：它的析构里才真正 join 读线程、掐断 RTMP
    avDEMuxer_.reset();

    // 4) 清残留帧，避免下次拉流先画出上一场的旧画面
    avContext_->audio_queue_.clear();
    avContext_->video_queue_.clear();
}
```

> `stopped_` 加 `recursive_mutex` 保护：关窗走 UI 线程，而「对端不推了」走信令线程，两条路都会调到这里。

### 3. 窗口由谁销毁

```cpp
QObject::connect(wgt, &PullerWgt::sig_closed, wgt, [this, wgt](){
    if(pullerWgt_.get() == wgt){
        pullerWgt_.release();
        wgt->deleteLater();     // 彻底离开当前调用栈再删
    }
}, Qt::QueuedConnection);
```

> `QueuedConnection` 保证槽在 close 流程结束后才执行；`deleteLater` 再兜一层，避免在栈中途销毁自己。

### 4. 心跳上报

```cpp
// 每 3s 一次，服务端靠它判断这条连接是不是还活着
heartbeat_timer_ = task_scheduler_->AddTask([weak_self](){
    auto self = weak_self.lock();
    if(!self) return false;          // 对象没了，定时器自己停
    if(self->tcp_conn_ && !self->tcp_conn_->IsClosed()){
        Heartbeat_body body;
        self->Send((const char*)&body, body.len);
    }
    return true;                     // 重复执行
}, 3000);
```

### 5. 推流端要能感知链路断

采集线程本身不看连接状态，所以单独起一个监视线程：

```cpp
void RtmpPushManager::monitorLink()
{
    bool seen_connected = false;
    while(!exit_){
        sleep(200ms);
        if(!isConnect.load() || !pusher_) continue;

        if(pusher_->IsConnected()){ seen_connected = true; continue; }

        // 建连之后又断开，才算链路中断；
        // 没经历过 connected 的是启动阶段还没握手完，不能误判
        if(!seen_connected) continue;

        link_lost_.store(true);
        isConnect.store(false);
        exit_.store(true);           // 只置标志，回收交给 UI 线程（自己 join 自己会死锁）
        return;
    }
}
```

UI 侧每秒刷状态时顺手收尾：

```cpp
if(manager_->isLinkLost() && !linkStopHandled_){
    linkStopHandled_ = true;
    manager_->StopPushOnLinkLoss();   // 先发 DELETESTREAM 让服务端回 IDLE，再 Close 停采集
}
```

### 6. 主窗口关闭要退出进程

`PullerWgt` 是独立顶层窗口，它开着的时候关主窗口不算「最后一个窗口关闭」，`quitOnLastWindowClosed` 不触发，进程会残留继续拉流。

```cpp
void ClientStream::closeEvent(QCloseEvent *event)
{
    QWidget::closeEvent(event);
    QApplication::quit();
}
```

## 服务端改动

### 1. 心跳看门狗

```cpp
void SigConnection::StartWatchdog()
{
    scheduler->AddTask([weak_self](){
        auto self = weak_self.lock();
        if(!self || self->IsClosed()) return false;

        if(self->IdleMs() > SIG_HEARTBEAT_TIMEOUT_MS){   // 15s
            self->Disconnect();     // → DisConnected() → Clear() → 通知对端
            return false;
        }
        return true;
    }, SIG_WATCHDOG_INTERVAL_MS);  // 3s 查一次
}
```

> 收到任何报文都会 `Touch()` 刷新时间，不只是心跳包。

### 2. 无人观看 → 断推流端

`RtmpSession` 维护观众数（只算 `Isplayer()`，不含主播），数量变化时在**锁外**回调上层：

```cpp
{
    std::lock_guard<std::mutex> lock(mutex_);
    ...
    cb = player_count_cb_;              // 先取出来
    players = CountPlayersLocked();
}                                       // 解锁
if(cb) cb(players, has_publisher);      // 再回调（避免和 RtmpServer 的锁形成环）
```

`RtmpServer` 拿到「观众归零且主播还在」就起一个 20 秒的一次性定时器：

```text
观众数归零 → 起 20s 定时器（只起一次，不是轮询）
                 ├─ 期间有人回来 → 立刻 RemoveTimer 撤掉
                 └─ 20s 到期 → 复查 GetPlayerCount()
                                 └─ 仍为 0 → 断开推流端的 RTMP 连接
```

```cpp
// 撤销和创建必须成对：players > 0 就是"有人回来了"，
// 此时不清掉挂起的定时器，20 秒后就会把有人看的流断掉
if(players > 0 || !has_publisher){
    if(it != pending_no_viewer_.end()){
        cancel_id = it->second;
        pending_no_viewer_.erase(it);
    }
}
```

> `pending_no_viewer_` 不是观众表，是**待停推定时器表**。里面只应该有「观众为 0、主播还在」的条目。

为什么直接断 RTMP，而不是走信令发 DELETESTREAM：

> RTMP 服务器本来就该自己保证带宽不被空占，不该依赖信令是否可靠。
> 断开的走的是普通 TCP 关闭流程，`RtmpConnection::OnClose → HandleDeleteStream` 会把 publisher 正常摘出 session，不留脏状态。
> 代价是必须配客户端的 `monitorLink()`，否则只是断了网、采集还在跑。

### 3. 停流不再等于断连

原来收到 `DELETESTREAM` 直接 `Clear()`，而 `Clear()` 会把连接从 code 表里摘掉：

```text
控制端停一次 → 服务端 RemoveConn(code) → 下次 ObtainStream 找不到 code → 再也连不回来
```

拆成两层：

```cpp
void SigConnection::HandleDeleteStream(const packet_head *data)
{
    if(!IsBusy()) return;
    DetachStreams();      // 只解除流关系 + 通知对端还剩几个观众
    role_state_ = IDLE;   // 连接保留，等着被再次调用
}
```

`DetachStreams()` 只清 `objects_` 和通知对端；`Clear()` 才会 `RemoveConn`，只在连接真的断开时走。

> 被控端停推后也要回一条 `DELETESTREAM(0)`，让服务端状态从 PUSHER 退回 IDLE。
> 不回的话，服务端一直以为它还在推，下次有人要看时走的是「直接取地址」分支，拿到的是已经断掉的流。

### 4. 半包会让 IO 线程空转

```cpp
// 原来：数据不足时 HandleMessage 直接 return，不消费 buffer，
// 外层 while 继续调它 → 死循环把 CPU 打满
while(buffer.ReadableBytes() > 0){
    if(!HandleMessage(buffer)) break;   // 改成有返回值，半包就退出等下次
}
```

> 心跳包和业务包粘在一起时很容易触发，属于加心跳之后必须一起修的东西。

## 三条路径对照

| 场景 | 触发方 | 检测手段 | 停止耗时 |
| :--- | :--- | :--- | :--- |
| 用户点 X 关窗 | 客户端 | `closeEvent` 直接处理 | 立即 |
| 客户端崩溃 / 断网 | 服务端 | 15s 心跳超时 | ≈15s |
| 观众全部离开但推流端还在 | 服务端 RTMP 层 | 20s 宽限期到期复查 | ≈20s |

三条路径最终汇聚到同一个动作：**被控端 `RtmpPushManager::Close()` → 停采集线程 + 停编码器 + 关采集设备**。

## 几个容易踩的点

- 关窗停流的顺序不能换：先通知、再 join 播放线程、最后释放 demuxer。顺序错了就是并发读一个正在析构的 `unique_ptr`。
- `Stop` 之后必须能重新拉流：`avDEMuxer_` 要重建、`stop_` 要复位，否则「停了再开」直接空指针崩。
- 客户端 `RtmpPushManager::Close()` 之后 `exit_` 要复位，不然下次 `Open()` 起的线程会立刻退出。
- 定时器回调里不要持锁调上层接口，`RtmpSession` 是「锁内取数、锁外回调」，`TimerQueue` 是「锁内摘取、锁外执行」。
- `pullpushTest()` 里 `main()` 结尾是 `while(getchar() != '\n')`，后台启动必须保住 stdin，否则读到 EOF 立刻退出：
  `setsid sh -c "sleep infinity | ./build/bin/LiveStream > /tmp/ls_run.log 2>&1" &`
