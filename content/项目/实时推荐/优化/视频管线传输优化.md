# 视频管线传输优化

## CPU 中转路径的拷贝

```c++
ctx->context->CopyResource(ctx->staging.get(), tex.get());
D3D11_MAPPED_SUBRESOURCE map{};
winrt::check_hresult(
    ctx->context->Map(ctx->staging.get(), 0, D3D11_MAP_READ, 0, &map));
const std::size_t row_bytes = static_cast<std::size_t>(ctx->staging_w) * 4;
std::vector<uint8_t> bgra;
bgra.reserve(row_bytes * ctx->staging_h);
const uint8_t* src = static_cast<const uint8_t*>(map.pData);
for (UINT y = 0; y < ctx->staging_h; ++y) {
    bgra.insert(bgra.end(), src + y * map.RowPitch,
                src + y * map.RowPitch + row_bytes);
}
ctx->context->Unmap(ctx->staging.get(), 0);
raw.bgra = std::move(bgra);
raw_out_->push(std::move(raw));
```

## 帧拷贝流程

CPU 中转对照路径的一帧先由 WGC 输出到 GPU 纹理。客户端把纹理复制到可读的 staging 纹理并映射到 CPU 地址空间，再逐行复制到 `bgra`；行拷贝同时去掉 `RowPitch` 中的填充。随后 `raw_out_->push(std::move(raw))` 将 vector 所有权交给有界队列，不再复制像素。 [WGC staging 与逐行拷贝 (line 293)](D:/csevent/client/src/capture_video.cpp:293)

Publisher 取出 `RawVideoFrame` 后重新分配 `GstBuffer`，通过 `gst_buffer_fill` 把整帧从 `frame.bgra` 复制进去，再推入 `appsrc`。这条路径后续由 `videoconvert` 在 CPU 上把 BGRA 转成 NV12。 [GstBuffer 拷贝与提交 (line 1125)](D:/csevent/client/src/media/webrtc_publisher.cpp:1125) · [native 管线格式转换 (line 815)](D:/csevent/client/src/media/webrtc_publisher.cpp:815)

按当前配置的 1440×1080、30 fps 算，两次 CPU 拷贝各处理约 178 MiB/s 的像素；此外还要承担纹理回读和 CPU 颜色转换。 [client.webrtc.yaml (line 22)](D:/csevent/config/client.webrtc.yaml:22)

## 怎么优化：把采集源并入同一条管线

上面的两次 CPU 拷贝描述的是“原生采集适配到 Publisher”的路径。优化方向是让 WGC 采集源直接成为 GStreamer Publisher 管线的一部分：采集、格式转换、编码和 RTP 发送都在同一条管线中衔接，不再先把每帧搬进 C++ 的 `RawVideoFrame`，再通过 `appsrc` 交给 GStreamer。

当前 `media.video_backend=gstreamer` 时，`WebRtcPublisher` 将视频采集源、格式转换、编码和 RTP 发送串进同一条管线；采集分支大致如下，随后接入 H.264/RTP 发送链。 [管线构造 (line 808)](D:/csevent/client/src/media/webrtc_publisher.cpp:808)

```text
d3d11screencapturesrc capture-api=wgc window-capture-mode=client show-cursor=false
  ! video/x-raw(memory:D3D11Memory),format=BGRA,framerate=<target_fps>/1
  ! queue max-size-buffers=1 leaky=downstream
  ! d3d11convert
  ! video/x-raw(memory:D3D11Memory),format=NV12
  ! mfh264enc bitrate=<bitrate_kbps> low-latency=true
  ! H.264/RTP
```

当前实况配置选择 `video_backend=gstreamer`；`target_fps` 用于源端帧率约束，`bitrate_kbps` 用于编码器。 [媒体配置 (line 16)](D:/csevent/config/client.webrtc.yaml:16) · [编码配置 (line 23)](D:/csevent/config/client.webrtc.yaml:23) · [后端选择 (line 55)](D:/csevent/client/src/media/media_client.cpp:55)

采集源的 WGC API、客户区模式和光标选项直接写在管线描述中。`window_process` 仍由窗口监视器用于查找游戏窗口，找到后把 HWND 交给管线中的采集源。`width` 和 `height` 用于检查收到的帧尺寸是否受支持，当前管线不会用它们把画面缩放到目标尺寸。 [窗口绑定 (line 1046)](D:/csevent/client/src/media/webrtc_publisher.cpp:1046) · [帧尺寸检查 (line 727)](D:/csevent/client/src/media/webrtc_publisher.cpp:727)

与上面的 CPU 路径相比，这条路径不在应用代码里映射 D3D11 画面、逐行复制到 `frame.bgra`，也不再分配新的 `GstBuffer` 并用 `gst_buffer_fill` 复制整帧。BGRA 到 NV12 的转换由 `d3d11convert` 在 D3D11 管线路径中完成，避免应用层的 GPU→CPU 回读和 CPU 颜色转换。单帧队列限制缓存深度；编码跟不上时丢弃较旧帧，优先发送较新的画面，避免队列持续积压。

这项优化减少了视频路径中的显式 CPU 帧拷贝，不据此宣称编码器内部完全零拷贝。`video_backend=native` 仍保留原生采集加 `appsrc` 的对照路径；音频仍由独立 WASAPI 链路采集，本节描述的管线优化只针对视频。
