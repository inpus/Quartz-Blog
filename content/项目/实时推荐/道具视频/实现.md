## 2. 素材导入到托管目录

`clips-tool` 支持 `init`、`import` 和 `query`：

1. `init` 以可写模式打开 SQLite，创建版本化 `clips` 表与查询索引。数据库 schema 记录地图、阵营、utility、起点、落点、priority、duration、reviewed、说明和源 URL。
2. `import` 把 manifest 中相对的 `video_path` 解析到清单目录，再要求文件存在、非空且扩展名为 `.mp4` 或 `.mov`。
3. 地图、阵营、道具和点位经过归一化；点位由共享区域词典校验。地图缺少规范区域词典、起点/落点缺失、priority 越界或视频不合法都会使导入失败。
4. 每个合法条目写入 SQLite，并将原视频原样复制到 `clips_dir/db_<id>.<ext>`。批次由 SQLite 事务包围；失败时回滚事务并删除本批已复制的文件。表中 path 字段有 UNIQUE 约束，但导入后保存的是托管目录目的路径；导入时的 source path 会被更新掉，因此该约束不会自动阻止同一清单重复导入。重复运行 import 可能创建新 ID 和重复素材。正式资产应在入库前去重，重新执行前先核对数据库与本批文件。

### 主键与键约束

`clips.id` 是 `INTEGER PRIMARY KEY AUTOINCREMENT`。`clips-tool import` 的 `INSERT` 语句不包含 `id`，随后用 SQLite 的 `getLastInsertRowid()` 取回新 ID。`ClipRecord.id` 序列化为 API 字段 `clip_id`；同一个 ID 又用于 `db_<id>.<ext>` 文件名、`/clips/db_<id>.<ext>` URL，以及推荐和槽位消息中的 `clip_id`。因此 `id` 是数据库到播放链路的稳定关联键，只要数据库行保留，这些引用都指向同一素材。

`path TEXT NOT NULL UNIQUE` 是表中另一个唯一约束。导入时先以原片路径插入，复制成功后立即更新为托管目标路径；事务提交后的数据库只保存托管路径。唯一约束因此防止相同托管路径重复登记，但不能用原片路径做导入去重。表没有单独的 `source_id`、源路径或内容哈希，也没有其他素材关联表或外键；`source_url`、标签、点位和审核状态都只是普通元数据。重复导入原片时 SQLite 可以分配新的 `id` 与新托管文件名，造成重复记录。`idx_clips_query` 是查询索引，不是唯一键。
运行服务时 `SqliteClipRepository` 默认以只读方式打开数据库。若显式配置了 `clips_db` 却无法初始化，`server_main.cpp` 会记录错误并退出，不会悄悄切换到 mock 视频。`clips_db` 为空时，API 无 SQLite 后端并返回 503。

### SQLite 语句逐条对应到项目实现

#### 1. 建库、版本与建表

`SqliteClipRepository::Impl` 先执行 `PRAGMA user_version` 读取数据库版本。写模式打开数据库时执行以下 SQL；建表、建索引和设版本号由同一个 `SQLite::Transaction` 包围，成功后提交。只读服务不会初始化数据库，要求版本已经是 1。实现位置见 [`clip_repository.cpp`](D:/csevent/server/libs/core/clip_repository.cpp:189)。

```sql
PRAGMA journal_mode=WAL;

CREATE TABLE IF NOT EXISTS clips(
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  path TEXT NOT NULL UNIQUE,
  map TEXT NOT NULL,
  side TEXT NOT NULL CHECK(side IN ('T','CT')),
  utility TEXT NOT NULL CHECK(utility IN ('smoke','flash','molotov','he')),
  from_area TEXT NOT NULL,
  target_area TEXT NOT NULL,
  throw_type TEXT NOT NULL DEFAULT '',
  lineup_desc TEXT NOT NULL DEFAULT '',
  tags TEXT NOT NULL DEFAULT '',
  source_url TEXT NOT NULL DEFAULT '',
  priority REAL NOT NULL DEFAULT 0.5 CHECK(priority BETWEEN 0 AND 1),
  duration_s REAL NOT NULL DEFAULT 0 CHECK(duration_s>=0),
  reviewed INTEGER NOT NULL DEFAULT 1 CHECK(reviewed IN (0,1)),
  created_at TEXT DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_clips_query
  ON clips(map,side,from_area,reviewed,priority DESC,id);

PRAGMA user_version=1;
```

这些语句各自做的事：

| SQL | 项目里的作用 |
|---|---|
| `PRAGMA journal_mode=WAL` | 写模式启用 WAL 日志模式。 |
| `CREATE TABLE ... clips` | 创建素材元数据主表。`id` 是自动分配的整数主键；`path` 是非空唯一字段。`side`、`utility`、`priority`、`duration_s`、`reviewed` 由 `CHECK` 限制合法值；其余 `NOT NULL` 和 `DEFAULT` 约束保证必要字段及缺省值。 |
| `CREATE INDEX ... idx_clips_query` | 为地图、阵营、起点、审核状态筛选以及优先级/ID 排序建立普通索引。它不是唯一索引；`utility` 和 `target_area` 不在此索引列中。 |
| `PRAGMA user_version=1` | 写入 schema 版本。初始化前读取版本；程序拒绝不支持的版本，也拒绝把版本为 0 但已存在 `clips` 表的数据库直接当成新库使用。 |

项目仅建 `clips` 一张表，没有素材外键或关联表。列定义的使用方式如下：`map/side/utility/from_area/target_area` 供筛选；`priority` 控制候选排序；`reviewed` 控制是否发布；`throw_type/lineup_desc/tags/source_url` 是普通元数据；`created_at` 由 SQLite 自动生成。`path UNIQUE` 约束的是数据库当前保存的文件路径，并非原片的身份键。

#### 2. 导入时的 `INSERT` 和 `UPDATE`

`importManifest()` 归一化和校验每个条目及原片后，执行下面的参数化插入（实现位置见 [`importManifest()`](D:/csevent/server/libs/core/clip_repository.cpp:222)）：

```sql
INSERT INTO clips(path,map,side,utility,from_area,target_area,
                  priority,duration_s,reviewed,throw_type,lineup_desc,tags,source_url)
VALUES(?,?,?,?,?,?,?,?,?,?,?,?,?);
```

13 个 `?` 由 `SQLite::Statement::bind()` 按列顺序绑定：1 是原片的 canonical 绝对路径；2–6 是地图、阵营、道具、起点、落点；7–9 是优先级、时长、审核状态；10–13 是投掷类型、描述、标签和源 URL。SQL 不传 `id`，插入后通过 `getLastInsertRowid()` 取回 SQLite 生成的 ID；也不传 `created_at`，因此采用 `CURRENT_TIMESTAMP` 默认值。

获得 ID 后，代码将原片复制到 `clips_dir/db_<id>.<ext>`，再执行：

```sql
UPDATE clips SET path=? WHERE id=?;
```

两个参数分别是托管文件路径和刚生成的 ID。也就是说，行先以原片路径暂存，复制成功后把 `path` 改成托管路径；整个 manifest 导入由一个事务包围。异常时事务回滚，代码同时删除本批已复制的文件。项目没有按原片路径、`source_url` 或内容哈希先查重，也没有 `UPSERT`；原片路径被更新掉后，再导入同一原片仍可能插入新行并分配新 ID。

#### 3. 运行时 `SELECT` 查询

`query()` 通过 `SQLite::Statement` 执行参数化查询（实现位置见 [`query()`](D:/csevent/server/libs/core/clip_repository.cpp:280)）。按请求拼出的 SQL 结构如下；方括号表示可选分支，不是 SQL 字面语法：

```sql
SELECT id,path,map,side,utility,from_area,target_area,priority,duration_s,reviewed,
       throw_type,lineup_desc,tags,source_url
FROM clips
WHERE map=? AND side=? AND reviewed=1
  AND from_area IN (?, ...)
  [AND utility=?]
  [AND target_area IN (?, ...)]
ORDER BY priority DESC,id ASC;
```

地图、阵营和 `reviewed=1` 是固定条件；起点别名列表来自 `regions::dictionary().variants()`，手持道具存在时增加 `utility=?`，请求指定落点时再增加落点别名 `IN` 条件。`IN` 中的占位符数量按别名数量生成，实际值逐个绑定；拼入 SQL 的字段名来自代码常量，外部输入只作为绑定值。

查询没有 `JOIN`，也没有 SQL `LIMIT` 子句。C++ 逐行读取结果，到达 `q.limit` 后停止；随后再次规范化点位，并校验记录路径必须对应 `clips_dir/db_<id>.<ext>`、视频扩展名受支持且文件可播放。Drogon 查询 API 与 `clips-tool query` 共用该仓储实现。

## 3. 输入解析与 SQL 检索

### `clipQueryFromJson()`

它接收观测对象 `input`、查询上下文 `context`、结果上限和 VLM 最低置信度：

- 输入可为单个状态/观测，也可为 `{ocr, vlm}` 配对。可用 OCR 的 `status=published`、有效区域和 `self_area` 置信度至少 0.45 时优先采用；VLM 结果不能否决可用 OCR。
- OCR 不可用时要求 gameplay 类型及 VLM `region_candidates`。候选名称需在地图点位词典中，置信度默认至少 0.75；相机当前位置被映射为 `from_area`。VLM 不产生投掷落点。
- 从上下文补齐地图和阵营；阵营必须是 T 或 CT，地图、阵营和有效起点为必要字段。死亡、观战、未发布观测、无可信区域和无效 utility 都会以参数错误拒绝。
- 仓储查询只读取 `reviewed=1` 的记录，按地图、阵营和 `from_area` 的规范别名筛选；指定 utility 或 `target_area` 时再追加相应条件。SQL 使用绑定参数，候选按 `priority DESC, id ASC` 排序并受 limit 限制。

读取结果时还会再次检查区域词典、托管路径、MP4/MOV 扩展名、文件存在性和非空大小。错误或缺失的视频不会返回浏览器。

### Drogon API

`POST /api/clips/query` 先校验 `Authorization: Bearer <token>`，再确认 SQLite repository 已启用。合法请求返回 `status`、`query`、`clips[]` 和 `recommendations[]`；输入/schema 问题为 HTTP 400，未授权为 401，未配置数据库或查询故障为 503。此接口是只读查询，不写回 GameState 或 SlotManager。

### CLI JSON 查询与网页诊断

`clips-tool query` 复用同一套 `clipQueryFromJson()` 和仓储逻辑，输出 JSON 文件或 stdout。`/clips.html` 可以手动提交 JSON 调用 HTTP API，适合核对词典和匹配标签；正式副屏的输入来自实时观测，不依赖用户手动上传 JSON。

## 4. 正式副屏如何选择和播放

`panel.js` 把 `ocr_observation`、`vlm_event`、`media_status` 交给 `LiveRecommendations`；`LivePositions` 按 session/seq 拒绝旧消息，并选择新鲜 OCR 或 VLM 位置。发生区域变化或手持道具变化时，前端用不同帧确认后再查。

`LiveRecommendations.tick()` 组合固定地图、手持 utility、稳定位置和 session 生成查询键。请求使用 `AbortController`；新查询替代旧查询，版本号检查拦截已经失效的迟到响应。正式面板没有固定 side 时，用相同点位分别请求 T 和 CT；结果按 `clip_id` 去重、按 priority/ID 排序并截到槽位数。`show()` 比较 clip ID 和 URL 签名，相同结果不重建播放器。

`SlotGrid.render()` 将每个候选放进对应 `<video>` 槽，设置 `muted`、`loop`、`autoplay` 和 `playsInline`。如果旧式预载池里已经有这个 clip，则直接接管预载元素；否则把托管 URL 设为 `src`。结果不够 K 条时其余槽清空；无命中、观测过期、死亡/观战、采集停止、WebSocket 断开或查询失败都会暂停并移除旧 `src`。

## 5. HTTP Range 媒体服务

`Clips::get()` 仅接受安全字符集中的文件名和 `.mp4` / `.mov` 扩展名，把文件限定在配置的 `clips_dir` 中。普通 GET 返回 HTTP 200；合法 `Range: bytes=...` 返回 206 与 `Content-Range`；非法或越界范围返回 416。路径穿越输入被拒绝，缺失文件返回 404。MOV 返回 `video/quicktime`，MP4 返回 `video/mp4`。

浏览器的视频元素直接向同源 `/clips/...` 请求媒体字节；Drogon 不通过 WebSocket 搬运视频数据。范围请求使浏览器能分段读取视频，并支持播放器按需取数据和拖动进度。

## 6. 可见推荐与旧式预载路径

同一代码库保留 `SqliteRecommender`：它从权威 `GameState` 查询 SQLite，并可产生单条 `Recommendation` 和 `PreloadHints`。当前副屏把此消息用于登记 URL 或预载候选；`panel.js` 注释明确指出延迟状态推送不能恢复已清空视频。正式可见槽位由 `LiveRecommendations` 发起的 HTTP 批量查询管理。

这两条路径共享素材仓储和托管 URL，但职责不同：SQL recommender 是状态推荐与预载来源，浏览器实时查询是当前可见 K 槽快照的权威来源。固定素材预览 `CatalogPreview` 则是单独的显式诊断模式。

## 7. 配置与验证边界

`config/server.sqlite.yaml` 自述为独立 JSON 查询服务配置，示例使用 `var/clips.db` 和 `var/clip-media`。它不是运行服务当前配置的证明；实际部署需读取 systemd 环境中的 `TACTICLENS_CONFIG`，并核对 `clips_db` 与 `clips_dir`。

## 总结

- 素材通过 manifest 和 `clips-tool` 入库，SQLite 存标签，托管目录保留可播原片。
- 实时副屏使用已发布 OCR 点位，必要时回退 VLM；按当前手持状态查 T/CT 素材并稳定更新 K 个槽位。
- API 返回候选 JSON，浏览器通过同源 Range HTTP 读取 MOV/MP4；WebSocket `Recommendation` 消息服务于预载，不替代 live 查询结果。
