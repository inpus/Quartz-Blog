# 道具视频接入流程

> 本文把道具视频看成一条小型内容服务链：管理视频与标签、根据当前点位查询候选、把视频文件交给浏览器播放。查询 API 负责返回候选，不把观测写回权威 GameState。

## 在整条系统中的位置

道具视频模块有两段：素材准备通常在新增或更新视频时执行；实时部分跟随采集观测自动查询。视频内容通过 HTTP 直接传给浏览器，媒体文件不经 WebSocket 转发。

正式副屏的可见槽位由实时查询响应更新。旧式 WebSocket `recommendation` 消息只登记 URL，`preload_hints` 只预载候选；这两类消息本身不会替换正在显示的槽位。

## 1. 素材从原片进入 SQLite

每条素材由原片与 JSON 元数据组成。元数据描述地图、T/CT 阵营、道具类型、投掷位置 `from_area`、落点 `target_area`、优先级、审核状态和说明。两种位置字段含义不同：当前所在位置只能作为投掷起点，不能代填视频落点。

SQLite 只有一个 `clips` 主表。它用 `id INTEGER PRIMARY KEY AUTOINCREMENT` 作为主键：导入时不传 `id`，由 SQLite 分配整数 ID。这个 ID 也是 API 的 `clip_id`，并用于生成托管文件名 `db_<id>.<ext>` 和播放 URL `/clips/db_<id>.<ext>`。

| 字段 | 键/约束 | 用途 |
|---|---|---|
| `id` | 主键，自动递增 | 片段身份；数据库行、`clip_id`、托管文件名和 URL 的关联键 |
| `path` | `NOT NULL UNIQUE` | 数据库最终保存托管目录中的文件路径，避免相同托管路径对应多行 |
| `map`、`side`、`utility`、`from_area`、`target_area` | 普通属性与筛选条件 | 描述适用地图、阵营、道具和点位，不承担主键作用 |
| `source_url`、`tags`、`throw_type`、`lineup_desc` | 普通描述字段 | 辅助追溯与展示，不要求唯一 |

清单的 `video_path` 是导入输入，不是数据库中的稳定身份；导入会把行里的 `path` 更新成托管文件路径。没有 `source_id` 或源文件哈希的去重键，重复导入同一原片仍可能创建新的 `id`。

`clips-tool init` 初始化数据库；`clips-tool import` 读取清单，核对标签与区域词典，确认文件为非空 MP4/MOV，然后在一个批次事务中登记元数据并将原片复制到托管目录。导入保留 MOV/MP4 容器，不转码；文件以 `db_<ID>.<ext>` 命名，查询结果据此生成稳定 URL。批次失败时回滚数据库并删除本批新拷贝。导入流程不保证幂等：导入后数据库保存托管路径，同一清单再次导入可能新增重复 ID，重新导入前先核对数据库和资产。

## 2. 副屏选择可信观测并发起查询

1. 正式副屏通过 `/ws/panel` 接收带 `session_id` 和递增 `seq` 的 OCR/VLM 观测。
2. 观测按采集会话隔离，并有 4 秒时效。已发布且置信度至少 0.45 的有效 OCR 点位优先；缺少可用 OCR 时，等待 OCR 约 1.8 秒后才考虑 VLM。VLM 只接受 gameplay 画面中置信度至少 0.75 的规范区域候选。
3. 死亡或观战状态暂停推荐。区域切换须由两个不同帧确认；自动道具筛选读取当前选中道具的 `held_utility`，置信度至少 0.75，改变持有道具也用不同帧确认。库存栏不作为当前手持证据。
4. 点位、手持筛选或查询上下文改变时发起查询；相同查询键有未完成请求或 10 秒内已查过时不重复请求。超时、断线、停止采集和查询失败都会清空槽位，失效请求的迟到响应不会恢复旧结果。

正式副屏固定地图 `de_dust2`，默认按当前手持道具过滤。当前手持未知或为枪/刀时按区域查询全部道具；用户可在面板手动选择道具筛选。正式副屏通常不固定阵营，因此浏览器分别查询 T、CT，再按 `clip_id` 去重，以优先级降序、ID 升序排序并截取前 K 条。

## 3. 服务端按 SQLite 标签筛选

查询请求带观测和上下文，经 Bearer token 校验后进入 `clipQueryFromJson()`：

- 可用的已发布 OCR 位置优先；无可信 OCR 位置时，才从 VLM 候选中选择符合地图词典、上下文和置信度门槛的位置。
- 地图、阵营和 `from_area` 是基本条件；手持道具存在时追加 utility 条件。实时请求不指定 `target_area`，因此返回同一起点区域可用的候选落点。
- 死亡或观战状态、未知区域、非 gameplay 场景、未发布观测或不可信点位会被拒绝。
- SQLite 只匹配 `reviewed=1` 的记录，并验证对应托管文件存在、扩展名受支持、路径仍在托管目录中。

接口返回 `clips[]`、实际采用的点位来源和查询条件，以及对应的 `recommendations[]` 元数据。空结果以 `status=no_match` 返回；网页将其视作完整槽位快照并清空视频。

## 4. 浏览器通过 HTTP 播放

查询结果中的 `/clips/db_<ID>.mov` 或 `.mp4` 是同源相对 URL。浏览器把它设为视频元素 `src`，通过 HTTP 向 Drogon 请求媒体文件；播放与拖动进度时浏览器可以使用 Range 请求。服务端返回 `200` 全量内容、`206` 字节范围或 `416` 无效范围响应。槽位播放器静音、自动播放、循环播放；相同片段与 URL 的结果不会重启播放。

`/clips.html` 是独立诊断页，可手动上传 JSON 和选择查询条件；它不是正式副屏的必经操作。面板中的固定点位素材预览也是显式预览模式，不代表实时推荐结果。

## 实现边界

- `SqliteClipRepository` 的查询桥只读 SQLite，不修改权威 GameState。
- C++ `SqliteRecommender` 仍可从 GameState 产生单条 `Recommendation` 与预载提示；正式实时面板的槽位查询由浏览器直接调用查询 API。
- `config/server.sqlite.yaml` 是独立 JSON 查询服务的样例配置。实际实例是否启用 SQLite，取决于启动时加载的真实 `TACTICLENS_CONFIG`，不能只凭样例 YAML 判断。
- 视频、数据库和运行配置是服务器资产；Git 中的清单和代码不能单独证明服务器当前已有可播放文件。

## 总结

- 原片与标签由 `clips-tool` 一次性入库，元数据进 SQLite，原始 MP4/MOV 拷贝到托管目录。
- 正式副屏以可信 OCR 为主、VLM 为回退，根据点位与手持状态请求 SQLite；无阵营时并行查询 T/CT 并合并排序。
- 候选元数据走 HTTP JSON，视频字节走支持 Range 的 HTTP；WebSocket 只传观测与控制/提示消息。
