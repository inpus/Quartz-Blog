# 采集

> 本文说明真实视频、音频如何进入客户端的 Publisher：视频从窗口采集后形成 <code>RawVideoFrame</code>，音频通过 WASAPI 形成 <code>AudioPacket</code>；两者进入各自的 C++ 队列，由媒体主循环交给 <code>publisher-&gt;push(...)</code>。本页止于 Publisher 接口，GStreamer 发布管线见 [Publisher 管线实现](WebRTC实现.md#publisher-pipeline)。

## 采集启动时序

真实采集源只在 Publisher 报告 WebRTC 已连接后启动。视频后端由 <code>media.video_backend</code> 选择；音频由 <code>IndependentAudioSource</code> 启动两路 WASAPI 进程回环采集。

~~~mermaid
sequenceDiagram
    participant M as media_client
    participant P as WebRTC Publisher
    participant G as GstVideoSource
    participant T as 视频采集线程
    participant A as IndependentAudioSource

    loop 主循环
        M->>P: stats()
        alt connected 且 sources 尚未启动
            M->>M: start_sources()
            alt video_backend = gstreamer
                M->>G: gst_video.start(video, cfg)
                G->>G: initializeGstreamer()
                G->>T: 创建采集线程
                G-->>M: 返回
                T->>T: 查找窗口并创建、启动管线
            else video_backend = native
                M->>M: native_video.startRaw(...)
            end
            M->>A: audio.start(两条输出队列, cfg)
            A->>A: 启动 CS2、Oopz 两个采集线程
            M->>M: sources_started = true
        end
    end

    Note over G,T: gst_video.start() 在线程创建后返回；找到窗口后，采集线程才调用 gst_parse_launch() 并将管线设为 PLAYING。
    Note over M,A: sources_started 表示采集启动请求已发出，不代表已经收到视频帧或音频包。
~~~

音频采集使用 WASAPI，不经过 GStreamer。GStreamer 在音频进入 Publisher 后才负责后续编码和媒体发送。

## 游戏画面采集

### 视频采集数据流

视频后端可以是 GStreamer 或 native，两者都输出 <code>RawVideoFrame</code> 并进入同一个视频队列。下图展开 GStreamer 分支，并标出 native 分支的汇合点：

~~~mermaid
flowchart LR
    A[video_backend] --> B{选择后端}
    B -->|gstreamer| C[WGC d3d11screencapturesrc]
    C --> D[d3d11download]
    D --> E[appsink]
    E --> F[RawVideoFrame]
    B -->|native| G[WgcFrameSource startRaw]
    G --> F
    F --> H[视频队列 容量 1]
    H --> I[media_client tryPop]
    I --> J[publisher push]
~~~

### 查找目标窗口

源码：<code>client/src/media/gst_video_source.cpp</code>；进程名匹配：<code>client/src/capture_target.hpp</code>。

<code>GstVideoSource::start()</code> 在线程中先构造 <code>WindowSearch</code>，把要查找的进程名放进去，再调用 <code>EnumWindows</code>：

~~~c++
WindowSearch search{
    std::wstring(cfg.window_process.begin(), cfg.window_process.end())
};
EnumWindows(enumerate, reinterpret_cast<LPARAM>(&search));
~~~

<code>EnumWindows</code> 的第一个参数是回调函数；第二个参数是传给回调的用户数据。这里把 <code>search</code> 对象的地址转成 Windows 的 <code>LPARAM</code> 传入。<code>EnumWindows</code> 在枚举期间同步调用回调，因此局部变量 <code>search</code> 在回调运行时仍然有效。

回调函数的前两个参数由 <code>EnumWindows</code> 提供：

~~~c++
BOOL CALLBACK enumerate(HWND hwnd, LPARAM data) {
    auto& search = *reinterpret_cast<WindowSearch*>(data);
~~~

<code>hwnd</code> 是 <code>EnumWindows</code> 当前枚举到的窗口句柄，每次调用 `enumerate()` 时传入的窗口句柄，表示当前正在检查的顶层窗口。它只是候选窗口，经过可见性和进程名筛选后，符合条件的句柄才会保存到 `search.window`；

<code>data</code> 是刚才传入的 <code>&search</code>，通过 <code>reinterpret_cast</code> 还原成对同一个 <code>WindowSearch</code> 对象的引用。于是回调既拿到当前窗口，也能读取目标进程名，并在找到候选窗口时把结果写回 <code>search.window</code>。

下面分步看回调如何筛选窗口。回调返回 <code>TRUE</code> 表示继续枚举其他窗口。

~~~c++
if (!IsWindowVisible(hwnd) || IsIconic(hwnd)) return TRUE;

DWORD pid = 0;
GetWindowThreadProcessId(hwnd, &pid);
~~~

第一步先跳过不可见或最小化的窗口，再从 <code>HWND</code> 取得所属进程的 PID。这样的窗口不会作为采集目标。

接着打开进程并读取其 exe 路径：

~~~c++
auto process = OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, FALSE, pid);
if (!process) return TRUE;

wchar_t path[32768];
DWORD count = 32768;
const auto found = QueryFullProcessImageNameW(process, 0, path, &count);
CloseHandle(process);
~~~

<code>OpenProcess</code> 只请求查询进程信息所需的权限。打开失败时回调返回 <code>TRUE</code>，继续检查其他窗口。<code>QueryFullProcessImageNameW</code> 将 exe 路径写入 <code>path</code>；<code>count</code> 作为缓冲区容量传入，调用成功后变为实际路径长度。读取后立即用 <code>CloseHandle</code> 关闭进程句柄。

最后把进程路径和配置的目标名比较，并从符合条件的窗口中挑选客户区最大的一个：

~~~c++
RECT rect{};
if (found && processMatches(std::wstring_view(path, count), search.name) &&
    GetClientRect(hwnd, &rect)) {
    const auto area = (rect.right - rect.left) * (rect.bottom - rect.top);
    if (area > search.area) {
        search.area = area;
        search.window = hwnd;
    }
}
~~~

<code>processMatches</code> 负责判断 exe 路径是否匹配配置中的 <code>window_process</code>。<code>GetClientRect</code> 取得客户区尺寸；若同一进程有多个可见窗口，代码保留面积最大的客户区，并把对应 <code>HWND</code> 存入 <code>search.window</code>。

<code>EnumWindows</code> 返回后，<code>GstVideoSource::start()</code> 检查 <code>search.window</code>。没有找到时等待 100 毫秒后重新枚举；找到时将窗口句柄写入 GStreamer 源的 <code>window-handle</code> 属性。下一节展示这条 WGC 管线。

### GStreamer WGC 管线

源码：<code>client/src/media/gst_video_source.cpp</code>。

窗口找到后，代码用 <code>gst_parse_launch</code> 创建下面这条采集管线：

~~~text
d3d11screencapturesrc capture-api=wgc window-handle=&lt;HWND&gt;
  window-capture-mode=client show-cursor=false !
video/x-raw(memory:D3D11Memory),framerate=&lt;target_fps&gt;/1 !
d3d11download !
video/x-raw,format=BGRA !
appsink name=raw sync=false max-buffers=1 drop=true
~~~

- <code>d3d11screencapturesrc</code> 通过 Windows Graphics Capture 获取目标窗口客户区。
- 第一个 caps 限定源输出为 D3D11 内存，并设置目标帧率。
- <code>d3d11download</code> 将画面下载为后续 CPU 代码可读取的内存；后面的 caps 指定像素格式为 BGRA。
- <code>appsink name=raw</code> 把样本交给客户端代码读取，并把这个 element 命名为 <code>raw</code>；后续 <code>gst_bin_get_by_name(..., "raw")</code> 通过该名称取回它。它最多保留一个待取样本，积压时丢弃旧样本，优先保持画面新鲜。

### 获取 appsink 和 bus，并启动管线

管线描述创建成功后，代码取出后续要读取的 <code>appsink</code> 和用于接收管线消息的 <code>GstBus</code>，计算时钟偏移，然后请求管线进入 <code>PLAYING</code>：

~~~c++
auto* sink = gst_bin_get_by_name(GST_BIN(pipeline), "raw");
auto* bus = gst_element_get_bus(pipeline);

auto* gstclock = gst_system_clock_obtain();
const auto gst_now = gst_clock_get_time(gstclock);
const int64_t clock_offset =
    static_cast<int64_t>(clock::nowUs()) -
    static_cast<int64_t>(gst_now / 1000);
gst_object_unref(gstclock);

gst_element_set_state(pipeline, GST_STATE_PLAYING);
~~~

<code>gst_bin_get_by_name</code> 按管线中配置的名称 <code>raw</code> 找到 <code>appsink</code>；后续取帧时会使用 <code>sink</code>。

<code>gst_element_get_bus</code> 取得管线的消息总线；采集循环会从中读取 <code>ERROR</code> 和 <code>EOS</code> 消息。<code>sink</code> 和 <code>bus</code> 都会在管线清理时释放。

<code>gst_system_clock_obtain()</code> 获取 GStreamer 系统时钟，<code>gst_clock_get_time()</code> 返回当前时间，单位是纳秒。<code>clock::nowUs()</code> 返回客户端单调时钟的微秒值，所以计算时先将 <code>gst_now</code> 除以 1000，再用两者相减得到 <code>clock_offset</code>。后面**生成帧时间戳**时，会先将 GStreamer 的 <code>base_time + （采集源）PTS</code> 转成微秒，再加上这个偏移，映射到客户端单调时钟。临时取得的时钟引用在计算后立即用 <code>gst_object_unref</code> 释放。

> [!NOTE]
>
> - `base_time` 是这条 GStreamer 管线在 GStreamer 时钟域中的基准时间。
> - 这里的 `PTS` 是 **WGC 采集源输出的 buffer 时间戳**，不是编码后的时间戳。这条采集管线还没有编码器。
> - `base_time + PTS` 得到 GStreamer 时钟域中的时间；换算成微秒后，加上 `clock_offset`，映射到客户端的单调时钟。
>
> 可概括为：
>
> ```text
> 客户端单调时间 ≈ (pipeline base_time + 采集 buffer 的 PTS) / 1000
>                   + clock_offset
> ```

<code>gst_element_set_state</code> 请求整条管线进入 <code>PLAYING</code>，让采集和样本流动起来。该调用的返回值在这里没有检查；如果管线运行中出错，后续采集循环会从 <code>bus</code> 读取错误消息。

### 从 appsink 生成 RawVideoFrame

#### 拉取 appsink 样本

~~~c++
GstSample* sample = gst_app_sink_try_pull_sample(
    GST_APP_SINK(sink), 50 * GST_MSECOND);
~~~

采集线程最多等待 50 毫秒。拿到样本时继续读取和映射；如果返回空指针，表示这次等待没有取得样本，循环仍会继续检查管线消息。

#### 校验样本并映射视频帧

~~~c++
GstVideoInfo info;
GstBuffer* buffer = gst_sample_get_buffer(sample);
GstVideoFrame mapped;
if (GST_BUFFER_PTS_IS_VALID(buffer) &&
    gst_video_info_from_caps(&info, gst_sample_get_caps(sample)) &&
    gst_video_frame_map(&mapped, &info, buffer, GST_MAP_READ)) {
~~~

这几行先从 <code>sample</code> 取出 buffer，再用 buffer、caps 和视频信息映射出可读的帧。两个栈上对象分别保存视频格式描述和映射结果：

- <code>GstVideoInfo info</code>：用来描述图像格式、宽高、plane 布局和 stride 等信息；下面的 <code>gst_video_info_from_caps</code> 会填充它。
- <code>GstVideoFrame mapped</code>：保存映射后的帧视图，后续通过它访问像素平面。

逐个看 API 和参数：

| API / 返回值 | 参数在本次调用中的含义 | 作用 |
|---|---|---|
| <code>gst_sample_get_buffer(GstSample *sample) → GstBuffer*</code> | <code>sample</code> 是 appsink 取到的样本 | 取得样本关联的 buffer，像素数据和 PTS 都从它读取。返回指针由 sample 持有，sample 释放前有效；这里不单独 unref。API 允许没有关联 buffer，此时会返回空指针。[GstSample 文档](https://gstreamer.freedesktop.org/documentation/gstreamer/gstsample.html#gst_sample_get_buffer) |
| <code>GST_BUFFER_PTS_IS_VALID(buffer) → bool</code> | <code>buffer</code> 是上一步取得的 buffer | 检查 buffer 的 PTS 是否有值；PTS 是 GStreamer 时钟时间，单位为纳秒，未设置时为 <code>GST_CLOCK_TIME_NONE</code>。它是宏，不是函数。宏为 false 时，<code>&amp;&amp;</code> 会跳过后面的 caps 解析和帧映射。[GstBuffer PTS 文档](https://gstreamer.freedesktop.org/documentation/gstreamer/gstbuffer.html#GST_BUFFER_PTS_IS_VALID) |
| <code>gst_sample_get_caps(GstSample *sample) → const GstCaps*</code> | 输入是当前 <code>sample</code> | 取得样本对应的协商格式描述。此管线在 appsink 前要求 <code>video/x-raw,format=BGRA</code>；caps 还携带协商后的宽高等信息。返回的 caps 由 sample 持有，在 sample 释放前有效。[GstSample 文档](https://gstreamer.freedesktop.org/documentation/gstreamer/gstsample.html#gst_sample_get_caps) |
| <code>gst_video_info_from_caps(GstVideoInfo *info, const GstCaps *caps) → gboolean</code> | <code>&amp;info</code> 是输出参数；<code>caps</code> 是刚取得的格式描述 | 把 caps 解析成后续视频处理使用的布局信息，写入 <code>info</code>，包括像素格式、宽高、plane 偏移和 stride。返回 TRUE 表示解析成功；后面的宽高读取和帧映射都依赖它。[GstVideoInfo 文档](https://gstreamer.freedesktop.org/documentation/video/video-info.html#gst_video_info_from_caps) |
| <code>gst_video_frame_map(GstVideoFrame *frame, const GstVideoInfo *info, GstBuffer *buffer, GstMapFlags flags) → gboolean</code> | <code>&amp;mapped</code> 是输出位置；<code>&amp;info</code> 提供图像布局；<code>buffer</code> 提供帧数据；<code>GST_MAP_READ</code> 表示申请读取访问 | 将 buffer 中的视频帧映射为可访问的 <code>GstVideoFrame</code>，后续通过 <code>mapped</code> 取得像素平面地址和实际 stride。返回 TRUE 表示映射成功；完成读取后必须调用 <code>gst_video_frame_unmap(&amp;mapped)</code> 配对解除映射。[GstVideoFrame 文档](https://gstreamer.freedesktop.org/documentation/video/video-frame.html#gst_video_frame_map) |

这里按 appsink 返回的是正常视频样本来处理，默认样本带有 buffer 和 caps。getter 的 API 允许返回空指针；若要覆盖这种异常或特殊样本，需要先判空，再检查 PTS 或解析 caps。当前源码没有把这两个判空步骤单独写出。

三个条件用 <code>&amp;&amp;</code> 短路连接：只有 PTS 有效、caps 能解析、映射成功，才进入后面的 <code>RawVideoFrame</code> 构造。<code>mapped</code> 和 <code>buffer</code> 都依赖当前 sample 的生命周期；代码在复制完像素、解除 frame 映射后才释放 sample。

#### 填充 RawVideoFrame 和采集时间

~~~c++
RawVideoFrame frame;
frame.frame_id = sequence_++;
frame.width = GST_VIDEO_INFO_WIDTH(&info);
frame.height = GST_VIDEO_INFO_HEIGHT(&info);
frame.stride = frame.width * 4;
frame.capture_start_us = static_cast<uint64_t>(
    (gst_element_get_base_time(pipeline) + GST_BUFFER_PTS(buffer)) / 1000 +
    clock_offset);
frame.timestamp_estimated = true;
frame.bgra.resize(std::size_t(frame.stride) * frame.height);
~~~

<code>RawVideoFrame</code> 保存递增的帧编号、画面尺寸、紧密排列的 BGRA 行宽和像素存储空间。采集时间把 GStreamer 管线的 <code>base_time + PTS</code> 从纳秒转成微秒，再加前面算出的 <code>clock_offset</code>，映射到客户端单调时钟。这个 PTS 来自 WGC 采集源，而不是编码器；代码把 <code>timestamp_estimated</code> 设为 <code>true</code>，表示它不是原始设备时间戳。

#### 按行拷贝像素并推入队列

~~~c++
auto* bytes = static_cast<uint8_t*>(
    GST_VIDEO_FRAME_PLANE_DATA(&mapped, 0));
for (int y = 0; y < frame.height; ++y) {
    std::copy_n(
        bytes + y * GST_VIDEO_FRAME_PLANE_STRIDE(&mapped, 0),
        frame.stride,
        frame.bgra.data() + y * frame.stride);
}
gst_video_frame_unmap(&mapped);
output.push(std::move(frame));
~~~

源平面的 stride 可能大于一行实际像素字节数，因此源地址按 <code>GST_VIDEO_FRAME_PLANE_STRIDE</code> 跨行；目标帧则按 <code>width * 4</code> 紧密排列。拷贝后先解除帧映射，再把完整帧移动进输出队列。视频队列容量为 1，队列满时丢弃最旧帧，以较新的画面为先。

处理完样本后，代码调用 <code>gst_sample_unref(sample)</code> 释放样本引用。若 PTS 无效、caps 解析失败或映射失败，该样本不会生成 <code>RawVideoFrame</code>，但仍会释放。

#### 检查管线消息并清理

~~~c++
GstMessage* message = gst_bus_pop_filtered(
    bus, static_cast<GstMessageType>(GST_MESSAGE_ERROR | GST_MESSAGE_EOS));
if (message) {
    if (GST_MESSAGE_TYPE(message) == GST_MESSAGE_ERROR) {
        GError* problem = nullptr;
        gchar* debug = nullptr;
        gst_message_parse_error(message, &problem, &debug);
        spdlog::error("capture: {}", problem->message);
        g_error_free(problem);
        g_free(debug);
    }
    gst_message_unref(message);
    break;
}
~~~

采集循环每轮检查 bus。遇到 <code>ERROR</code> 时解析并记录错误；遇到 <code>EOS</code> 时不再取帧。两种消息都会结束当前管线的采集循环。窗口关闭、最小化或收到停止标志也会结束循环。

~~~c++
gst_element_set_state(pipeline, GST_STATE_NULL);
gst_object_unref(bus);
gst_object_unref(sink);
gst_object_unref(pipeline);
~~~

退出当前采集循环后，代码请求管线进入 <code>NULL</code> 并释放 bus、appsink 和 pipeline 的引用；采集线程随后等待 100 毫秒，再回到窗口查找循环。若 <code>gst_parse_launch</code> 创建管线失败，代码会记录错误并结束采集线程。<code>GstVideoSource::stop()</code> 设置停止标志并等待采集线程退出。

> <code>media.video_backend=native</code> 时，媒体客户端改用 native 视频源；它仍向同一个 <code>RawVideoFrame</code> 队列输出。本节讲解的是 <code>gstreamer</code> 后端。

## CS2 与 Oopz 音频采集

源码：<code>client/src/capture_audio.cpp</code>、<code>client/src/media/audio_packetizer.hpp</code>。

### 双路音频采集数据流

CS2 和 Oopz 各由独立线程采集、重采样、分包，并写入各自的队列；两路不会先混成一路：

~~~mermaid
flowchart LR
    subgraph CS2
        C1[CS2 进程] --> C2[WASAPI 进程回环]
        C2 --> C3[时钟处理与重采样]
        C3 --> C4[AudioPacketizer 320 样本]
        C4 --> C5[CS2 AudioPacket 队列]
    end
    subgraph Oopz
        O1[Oopz 进程] --> O2[WASAPI 进程回环]
        O2 --> O3[时钟处理与重采样]
        O3 --> O4[AudioPacketizer 320 样本]
        O4 --> O5[Oopz AudioPacket 队列]
    end
    C5 --> M[media_client tryPop]
    O5 --> M
    M --> P[publisher push]
~~~

WebRTC 运行使用 <code>IndependentAudioSource</code>，而不是同一文件中的旧式混音采集类 <code>WasapiLoopbackSource</code>。独立采集类为 CS2 和 Oopz 各启动一个线程、一个 WASAPI 进程回环流和一个输出队列，因此两路声音保持分离。

### 启动两路进程回环

<code>IndependentAudioSource::start()</code> 要求调用方提供两条输出队列，并拒绝仅系统混音模式及系统音频回退。它随后为 CS2、Oopz 各启动一个工作线程。每个线程定期按配置中的进程名查找目标进程；进程尚未运行时保持等待，进程出现或重启后再打开对应音频流。

<code>Stream::open()</code> 使用 <code>ActivateAudioInterfaceAsync</code> 激活 WASAPI 的进程回环捕获，并设置包含目标进程子进程的捕获范围。该进程回环分支为输入格式提供 48 kHz、双声道、32 位浮点描述；系统混音分支才通过音频端点读取实际 mix format。当前 WebRTC 独立音轨路径不使用系统混音分支。

### 重采样并切成 20 ms 音频包

工作线程通过 <code>IAudioCaptureClient</code> 读取 WASAPI 数据包。<code>AudioPacketClock</code> 结合设备帧位置和 QPC 时间处理采集时间与连续性；静音标记对应的输入样本按零值处理。随后 <code>Mono16kResampler</code> 将输入变成单声道 16 kHz PCM。

<code>AudioPacketizer</code> 将重采样结果积累为每包 320 个样本，也就是 20 毫秒。每个 <code>AudioPacket</code> 带有来源编号、采样序号、采集时间、PCM 数据、实际收到的样本数，以及断点和时间戳是否估算的标记。生成的包被推入对应的 CS2 或 Oopz 有界队列；音频队列容量来自 <code>cfg.media.max_audio_packets</code>，队列满时会丢弃最旧的包。

进程退出或音频流发生变化时，线程会结束旧片段并关闭旧流，然后等待或重新打开进程。停止采集时，它会先冲出重采样器和 packetizer 中剩余的数据，再退出线程。

## 采集结果交给 Publisher

启动和分发代码在 <code>client/src/media/media_client.cpp</code>。媒体主循环检测到 <code>publisher.stats().connected</code> 后才启动视频与音频源。真实采集模式中，它从视频队列取一帧，并分别从 CS2、Oopz 队列最多取一个音频包，再调用 Publisher：

~~~c++
if (video.tryPop(image)) publisher->push(std::move(image));

AudioPacket packet;
if (cs2.tryPop(packet)) publisher->push(std::move(packet));
if (oopz.tryPop(packet)) publisher->push(std::move(packet));
~~~

这就是本页的结束边界：采集代码负责把数据交给 <code>publisher-&gt;push()</code>。该调用内部如何构造 <code>GstBuffer</code>、设置时间戳并送入 <code>appsrc</code>，以及编码、RTP 封装和 <code>webrtcbin</code> 管线，属于 Publisher 实现，见 [Publisher 管线实现](WebRTC实现.md#publisher-pipeline)。采集开始时机和客户端状态机见 [媒体客户端主流程](WebRTC实现.md#client-lifecycle)。
