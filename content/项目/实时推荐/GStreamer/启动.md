# 启动 WebSocket 与 WebRTC

> 本页是启动入口：先启动 Linux 服务端的 WebSocket 监听，再启动 Windows 客户端。客户端收到服务端的 WebRTC 确认后创建 Publisher；ICE/DTLS 连通后才开始真实采集。WebRTC 建链流程见 [WebRTC.md](WebRTC.md)，配置项见 [配置.md](配置.md)，media_client 主流程实现见 [WebRTC实现.md](WebRTC实现.md#client-lifecycle)，GStreamer 发布器源码见 [WebRTC实现.md](WebRTC实现.md#publisher-pipeline)。

## 启动顺序

~~~mermaid
sequenceDiagram
    participant C as Windows 客户端
    participant S as Linux 服务端 WebSocket
    participant P as 客户端 WebRTC Publisher

    C->>S: WebSocket 握手
    C->>S: start：请求协议 v2 与 WebRTC
    S-->>C: started：确认 transport 与 media_epoch
    C->>P: begin(media_epoch)：创建 Publisher 并发起协商
    P->>S: webrtc_offer / webrtc_ice，经 WebSocket 信令
    S-->>P: webrtc_answer / webrtc_ice，经 WebSocket 信令
    P->>P: ICE 连通并完成 DTLS
    C->>C: connected 后调用 start_sources()
    C->>P: 推送视频帧和两路音频
    P->>S: 经 SRTP 发送 RTP 媒体
~~~

**两个边界要分清：**

- WebSocket 服务端在 Linux 监听；Windows 客户端通过配置的 URL 连接它。
- WebSocket 连接成功不代表 WebRTC 已连通。服务端返回有效的 v2 **started** 后才创建 Publisher；Publisher 的 **connected** 变为 true 后才启动真实采集。

## 1. 启动 Linux WebSocket 服务

当前仓库的隔离 WebRTC 服务示例使用 **config/server.webrtc.yaml**，监听地址是 **0.0.0.0:9003**，HTTP 面板端口是 **8003**。这是候选 WebRTC 服务的配置；启动前要确认本次选择的配置和端口，不能因为 YAML 写了端口就认为服务已经在运行。原有 **9000/8000** 服务与此候选实例是两套服务。

先连接服务器：ssh yh@10.23.66.160。登录后先检查端口是否已有服务占用：

~~~bash
ss -lntp | grep -E ':(9003|8003)\b'
~~~

无输出表示当前没有这些监听端口；有输出时先核对占用进程和服务配置。

确认本次目标端口空闲或已核实占用进程后，再从仓库根目录启动候选服务：

~~~bash
cd /home/lth/csevent
systemd-run --user --unit=tacticlens-webrtc-test --collect \
  --property=WorkingDirectory=/home/lth/csevent \
  /bin/bash /home/lth/csevent/deploy/run_webrtc_server.sh
~~~

确认启动结果和监听端口：

~~~bash
systemctl --user status tacticlens-webrtc-test --no-pager
journalctl --user -u tacticlens-webrtc-test -n 100 --no-pager
ss -lntp | grep -E ':(9003|8003)\b'
~~~

**run_webrtc_server.sh** 默认使用 **config/server.webrtc.yaml**。若改用其他配置，应在启动记录里写出实际传入的配置路径；同一端口不要同时启动两份服务。

## 2. 准备并启动 Windows 客户端

客户端从 **D:\csevent** 仓库根目录运行。WebRTC 需要启用 GStreamer 的 **win-media-debug** 或 **win-media-release** 构建，以及对应的私有 GStreamer SDK；普通 **win-debug** 构建不包含这套媒体运行时。

如果尚未准备私有 SDK，先运行：

~~~powershell
./tools/prepare_media_sdk.ps1
~~~

如果还没有 WebRTC 客户端构建，配置并构建媒体版本：

~~~powershell
cmake --preset win-media-debug
cmake --build --preset win-media-debug --target capture-client --parallel 8
~~~

这会生成供启动脚本选择的媒体构建产物。SDK 检查命令如下：

~~~powershell
$sdk='D:/csevent/var/media-sdk/runtime/PFiles64/gstreamer/1.0/msvc_x86_64'
./tools/run_media_client.ps1 -GStreamerRoot $sdk -Mode Inspect
~~~

检查通过后，用实际采集模式连接服务器：

~~~powershell
./tools/run_media_client.ps1 -GStreamerRoot $sdk -Mode Run -Config config/client.webrtc.yaml
~~~

**Run** 模式读取指定配置并连接远端。示例运行时长为 30 秒；若要常驻，按 [配置.md](配置.md) 调整 **run_seconds**，并用 **Ctrl+C** 正常停止。启动前记录实际使用的配置文件、Debug/Release 构建、SDK 路径和运行时长。

## 3. 启动过程中的检查点

| 阶段 | 应确认的结果 | 这一步还不能说明什么 |
|---|---|---|
| WebSocket 握手 | 客户端生成 session，服务端接受连接 | WebRTC 尚未建立 |
| **started** 确认 | **protocol_version=2**、**selected_transport=webrtc**、**media_epoch** 非零 | Publisher 已开始协商，但还未连通 |
| SDP 与 ICE 信令 | Offer/Answer 的三轨映射通过，双方交换 ICE 候选 | 信令完成不等于 ICE/DTLS 已连接 |
| WebRTC connected | 客户端状态报告 **connected=true** | 还需确认媒体源启动并有数据 |
| 采集与收包 | **sources_started=true**，客户端有媒体计数，服务端报告或归档对应 session 的媒体 | 合成输入的结果不能代替真实游戏和麦克风验收 |

客户端每 5 秒输出媒体状态；最终报告写入配置指定的 **media.report_path**（字段和路径说明见 [配置.md](配置.md)）。远端 **Run** 的 **client_run_completed** 只表示客户端流程完成，不是服务端收到视频和音频的独立证据；需要按 session 到服务端报告、日志或归档目录核对。

## 4. 运行模式与验收范围

| 模式 | 是否连接远端 WebSocket | 输入 | 能证明的范围 |
|---|---:|---|---|
| **Inspect** | 否 | 无 | 检查 GStreamer 运行时和插件；不验证网络 |
| **SelfTest** | 否 | 合成媒体、本机接收 | 检查本机 WebRTC 媒体链 |
| **Probe** | 否 | 真实采集、本机接收 | 检查本机采集与媒体链 |
| **UplinkTest** | 是 | 合成媒体 | 检查远端协议和媒体接收；不验收游戏画面或真实音频 |
| **Run** | 是 | 配置指定的真实采集 | 端到端运行入口；仍需用服务端证据确认收包 |

## 5. 常见未启动位置

- WebSocket 连接失败：核对服务进程、客户端 URL、端口、防火墙及双方 token。
- 收到拒绝或没有有效 **started**：核对服务端是否支持协议 v2、是否启用 WebRTC，以及本次加载的服务端配置。
- GStreamer 初始化或管线失败：确认使用媒体构建，并通过启动脚本提供匹配的私有 SDK 和插件路径。
- 信令完成但 ICE/DTLS 超时：先核对双方网络和 UDP 通路。仓库的历史验证记录是内网直连；跨网、NAT 和 TURN 尚不能据此判定通过。
- Publisher 已连接但没有媒体：核对 CS2 窗口、CS2/Oopz 进程、采集配置和 **sources_started**。

断线后客户端会清理旧 Publisher 和采集源，再按有限次数尝试控制连接重连；纯 ICE 失败不会自动切换到旧 WebSocket 媒体协议。
