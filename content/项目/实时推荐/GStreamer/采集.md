# 采集

> 本文记录当前客户端的实况采集实现。视频默认由 GStreamer 的 WGC 源直接接入 Publisher 管线；窗口发现、采集源启停、帧检查和时间戳处理均按当前源码说明。音频仍由独立 WASAPI 采集链路提供。
>
> 音频采集到客户端 WebRTC 上传入口为止；WebRTC 建链、媒体轨和上传流程见 [WebRTC 流程](WebRTC.md)。旧版采集记录保留在[采集(旧).md](<采集(旧).md>)。

## 当前实现概览

实况配置默认使用 <code>media.video_backend=gstreamer</code>。目标窗口句柄交给 Publisher 后，视频帧在同一条 GStreamer 管线内从 WGC 流向编码器：

~~~mermaid
flowchart LR
    A[CaptureWindowMonitor提供HWND] --> B[setVideoWindow绑定窗口]
    B --> C[d3d11screencapturesrc WGC]
    C --> D[单帧queue]
    D --> E[d3d11convert]
    E --> F[NV12]
    F --> G[H.264编码器]
    G --> H[RTP / webrtcbin]
~~~

GStreamer 路径中，采集 buffer 在管线内直接流向编码器；采集侧不把画面映射到 CPU，也不经过 C++ 视频帧队列。

## 采集启动时序

远端实况的顺序从服务端确认 <code>started</code> 开始。<code>media_client</code> 校验会话参数后调用 <code>begin(media_epoch)</code>；<code>begin()</code> 创建 Publisher 并调用 <code>WebRtcPublisher::start()</code>。这一步会先启动 GStreamer Publisher 父管线，但 WGC 的 <code>capture</code> 子元素保持锁定。

服务端 <code>started</code> 消息处理中的调用：

~~~c++
else if (op == "started") {
    // 校验 protocol_version、selected_transport 和 media_epoch
    begin(message["media_epoch"].get<uint32_t>());
}
~~~

<code>begin()</code> 内部创建 Publisher 并传入视频采集模式：

~~~c++
publisher = std::make_unique<WebRtcPublisher>();
publisher->start(cfg, epoch, signal_callback, local_receiver, gpu_capture);
~~~

在 <code>WebRtcPublisher::start()</code> 中，管线解析成功后，<code>gpu_capture</code> 分支先取回 <code>capture</code> 并锁定它。锁定代码在父管线切换到 <code>PLAYING</code> 之前执行：

~~~c++
if (gpu_capture) {
  self.video_capture = gst_bin_get_by_name(GST_BIN(self.pipeline), "capture");
  gst_element_set_locked_state(self.video_capture, TRUE);
  // 随后在 source pad 和 encoder sink pad 注册探针
}
~~~

<code>gst_element_set_locked_state(..., TRUE)</code> 只锁定 WGC 子元素；它不阻止 Publisher 父管线启动。两个 pad probe 的注册细节见“管线解析后的探针注册”小节。

锁定和两个 pad probe 注册完成后，<code>WebRtcPublisher::start()</code> 调用 <code>gst_element_set_state(self.pipeline, GST_STATE_PLAYING)</code>，向 GStreamer 请求父管线进入 <code>PLAYING</code>。未锁定的元素随父管线开始状态切换；<code>capture</code> 因先前调用 <code>gst_element_set_locked_state(..., TRUE)</code> 而保持锁定，不会随父管线开始采集。如果状态请求返回 <code>GST_STATE_CHANGE_FAILURE</code>，代码会停止 Publisher 并抛出启动错误。

发出状态请求后，<code>WebRtcPublisher::start()</code> 读取 pipeline clock 和 <code>base_time</code>，计算 <code>origin_us</code>，将 GStreamer running time 对齐到客户端单调时钟。

协商入口是 <code>Impl::negotiate()</code>：<code>start()</code> 预先将它注册到 <code>on-negotiation-needed</code>，并在时钟初始化后再显式调用一次；两条入口共用 <code>offered</code> 去重，避免重复创建 Offer。<code>negotiate()</code> 向本地 <code>webrtcbin</code> 异步请求创建 Offer，结果由 <code>offerReady()</code> 整理并交给信令发送路径。Publisher 管线细节见 [WebRTC实现.md：Publisher 管线](WebRTC实现.md#publisher-pipeline)；协商和 Offer/Answer 流程见 [信令与协商回调](WebRTC信令与回调实现.md#signaling-callbacks) 和 [Offer/Answer 步骤索引](WebRTC信令与回调实现.md#offer-answer-full-chain)。

GStreamer 父管线进入 <code>PLAYING</code> 是为 Publisher 元素和协商做准备，不代表视频已经开始采集。WebRTC 连通后，媒体主循环才启动窗口监视器；监视器取得 HWND 后，<code>setVideoWindow()</code> 才解除 <code>capture</code> 的锁定并启动 WGC 采集。

连接门槛和 HWND 更新在 <code>client/src/media/media_client.cpp</code>：

~~~c++
if (!sources_started && connection["connected"].get<bool>()) {
    start_sources();
}
if (gpu_capture && sources_started)
    publisher->setVideoWindow(window_monitor.window());
~~~

完整时序如下。注意父 GStreamer 管线进入 <code>PLAYING</code> 发生在 WebRTC 连接和窗口监视器启动之前；真正开始 WGC 采集则发生在 HWND 绑定之后。

~~~mermaid
sequenceDiagram
    participant S as Server
    participant M as media_client
    participant P as WebRtcPublisher
    participant W as CaptureWindowMonitor
    participant C as WGC capture子元素
    S->>M: started(media_epoch)
    M->>M: 校验消息并调用begin(epoch)
    M->>P: WebRtcPublisher::start(...)
    P->>C: 取得capture并锁定
    P->>P: 父管线进入PLAYING
    P->>S: 发起Offer / WebRTC协商
    loop 主循环检查连接
        M->>P: stats()
        alt WebRTC已连接且采集未启动
            M->>W: start(window_process)
            loop 窗口监视
                W-->>M: 当前HWND或0
            end
            M->>P: setVideoWindow(HWND)
            P->>C: 设置窗口、解锁并同步状态
            C-->>P: WGC buffer进入编码器
        end
    end
~~~

<code>sources_started</code> 只表示采集启动请求已发出，并不表示监视器已找到窗口或已有视频帧。首次调用 <code>setVideoWindow()</code> 时句柄可能仍是 0；窗口找到后，主循环会再次传入有效 HWND。

## 目标窗口发现

GStreamer 路径下，窗口监视器只负责查找并发布 HWND，实际 WGC 采集由 Publisher 的 <code>capture</code> 子元素完成。监视器在 WebRTC 已连接后才启动；<code>start_sources()</code> 中的分支是：

~~~c++
if (gpu_capture) {
    window_monitor.start(std::wstring(cfg.window_process.begin(), cfg.window_process.end()));
} else {
    std::string error;
    if (!native_video.startRaw(*video, cfg.media.target_fps, cfg.window_process, &error))
        throw std::runtime_error(error);
}
~~~

当 <code>gpu_capture</code> 为真时，<code>window_monitor.start()</code> 创建后台线程并立即返回；它不会在这里启动 GStreamer 源。Native 分支则直接启动 <code>WgcFrameSource</code>，不走本节的窗口监视器路径。

### 监视线程何时重新枚举

<code>CaptureWindowMonitor::start()</code> 在线程中保留当前 HWND 和 PID。线程每 100 毫秒发布一次当前句柄；只有句柄不存在，或当前窗口无效、不可见、最小化、PID 变化时，才重新调用 <code>EnumWindows</code>：

~~~c++
while (!stop_) {
    if (!window || visibleWindowProcess(window) != pid) {
        WindowSearch search{process};
        EnumWindows(enumerate, reinterpret_cast<LPARAM>(&search));
        window = search.window;
        pid = search.pid;
    }
    window_ = reinterpret_cast<std::uintptr_t>(window);
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
}
~~~

<code>visibleWindowProcess()</code> 先检查句柄是否有效、窗口是否可见且未最小化，再读取窗口所属 PID；不符合条件时返回 0。若当前句柄仍有效且 PID 没变，监视线程复用它，不会每 100 毫秒重新枚举所有窗口。没有找到候选窗口时 <code>window</code> 保持空值，下一轮会继续枚举。

### 如何从候选窗口中选目标

<code>EnumWindows</code> 对每个顶层窗口调用 <code>enumerate()</code>。回调先检查窗口和客户区，再查询进程 exe 路径，并与配置的 <code>window_process</code> 匹配。匹配的候选中保留客户区面积最大的窗口：

~~~c++
BOOL CALLBACK enumerate(HWND window, LPARAM data) {
    auto& search = *reinterpret_cast<WindowSearch*>(data);
    const auto pid = visibleWindowProcess(window);
    if (!pid) return TRUE;

    RECT rect{};
    if (!GetClientRect(window, &rect)) return TRUE;
    const auto area = (rect.right - rect.left) * (rect.bottom - rect.top);
    if (area <= search.area) return TRUE;

    auto process = OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, FALSE, pid);
    if (!process) return TRUE;
    wchar_t path[32768];
    DWORD count = static_cast<DWORD>(std::size(path));
    const auto found = QueryFullProcessImageNameW(process, 0, path, &count);
    CloseHandle(process);
    if (found && processMatches(std::wstring_view(path, count), search.name)) {
        search.window = window;
        search.pid = pid;
        search.area = area;
    }
    return TRUE;
}
~~~

<code>return TRUE</code> 表示继续枚举其他顶层窗口。面积不大于当前最佳候选的窗口会提前跳过；其余窗口只有在 exe 路径匹配时才会写入 <code>search</code>。枚举结束后，监视线程把最佳 HWND 写入原子变量 <code>window_</code>。

### 主循环把 HWND 交给 Publisher

<code>media_client</code> 在 Publisher 报告连接成功后调用 <code>start_sources()</code>，然后在主循环中读取当前 HWND 并更新采集源：

~~~c++
if (!sources_started && connection["connected"].get<bool>()) {
    start_sources();
}
if (gpu_capture && sources_started)
    publisher->setVideoWindow(window_monitor.window());
~~~

<code>window_monitor.window()</code> 是对原子 HWND 的读取。监视器刚启动时通常返回 0；主循环仍会继续调用 <code>setVideoWindow(0)</code>。窗口找到后，下一轮会传入有效 HWND，Publisher 才为 <code>capture</code> 设置窗口句柄、解锁并同步到父管线状态。窗口发现只提供句柄，绑定和启动细节见前面的“HWND 如何启用采集源”小节。

## GStreamer WGC 管线

管线在 <code>client/src/media/webrtc_publisher.cpp</code> 的 <code>WebRtcPublisher::start()</code> 中构造。实况配置使用 <code>media.video_backend=gstreamer</code> 时，<code>gpu_capture</code> 分支把 WGC 源直接放进 Publisher 的 GStreamer 管线：

~~~text
d3d11screencapturesrc name=capture capture-api=wgc
  window-capture-mode=client show-cursor=false !
video/x-raw(memory:D3D11Memory),format=BGRA,framerate=<target_fps>/1 !
queue name=video_in max-size-buffers=1 max-size-time=0 max-size-bytes=0
  leaky=downstream !
d3d11convert !
video/x-raw(memory:D3D11Memory),format=NV12,colorimetry=bt709 !
mfh264enc name=encoder bitrate=<bitrate_kbps>
  low-latency=true gop-size=<target_fps> !
video/x-h264,stream-format=byte-stream,alignment=au,profile=constrained-baseline !
...
~~~

从左到右，管线里的 `!` 表示把前一个元素的输出接到下一个元素的输入。源元素负责产生窗口画面的 buffer；caps（媒体格式声明）约束相邻元素之间协商出的画面格式；之后队列、格式转换和编码器依次处理这些 buffer。

### WGC 窗口源与输入格式

~~~text
d3d11screencapturesrc name=capture capture-api=wgc
  window-capture-mode=client show-cursor=false !
video/x-raw(memory:D3D11Memory),format=BGRA,framerate=<target_fps>/1
~~~

- `d3d11screencapturesrc` 是 GStreamer 的 Direct3D 11 屏幕/窗口采集源。它使用 Windows Graphics Capture（WGC）取得目标窗口画面，输出原始视频 buffer。
- `name=capture` 给这个源实例命名为 `capture`。Publisher 在启动时按这个名字找到它、先锁定它；窗口监视器取得 HWND 后，再将句柄绑定给它并解除锁定。启动顺序见“采集启动时序”和“HWND 如何启用采集源”。
- `capture-api=wgc` 指定使用 Windows Graphics Capture API。
- `window-capture-mode=client` 指定只捕获窗口客户区，不包括标题栏和边框。
- `show-cursor=false` 表示采集画面中不显示鼠标光标。
- `video/x-raw` 表示未编码的原始视频。`format=BGRA` 规定每个像素使用蓝、绿、红、透明度四个 8 位通道的存储格式。
- `(memory:D3D11Memory)` 表明 buffer 使用 GStreamer 的 D3D11 GPU 内存类型。此分支的画面由 GStreamer 元素在 GPU 内存路径上传递；客户端不把每帧映射成 CPU 像素数组，也不经 `RawVideoFrame` 的 C++ 视频队列。
- `framerate=<target_fps>/1` 将目标帧率写进 caps，例如 `30/1` 表示每秒 30 帧。这里约束/协商媒体帧率，不是宽高设置；实际宽高由窗口源协商，并在编码器输入探针中按客户端配置校验。

### 单帧缓冲队列

~~~text
queue name=video_in max-size-buffers=1 max-size-time=0 max-size-bytes=0
  leaky=downstream
~~~

- `queue` 在 GStreamer 内部建立缓冲边界和独立的处理任务，让采集源与后续转换/编码可以分别推进。它是管线内部队列，不是 `media_client` 中的 `BoundedQueue<RawVideoFrame>`。
- `name=video_in` 给队列命名为 `video_in`，便于识别管线元素。
- `max-size-buffers=1` 让此队列最多等待一个视频 buffer。
- `max-size-time=0` 和 `max-size-bytes=0` 关闭按累计时长、字节数计算的队列上限，因此这里实际以一个 buffer 的上限控制积压。
- `leaky=downstream` 指队列满时丢掉队列中较旧的待处理 buffer，使较新的画面能继续进入下游。这会牺牲部分帧，换取队列不因编码变慢而持续堆积旧画面。

因此它限制的是 `video_in` 队列里等待处理的 buffer 数量；已经从队列取走、正在转换或编码的帧不计入这个队列上限。

### GPU 像素格式转换

~~~text
d3d11convert !
video/x-raw(memory:D3D11Memory),format=NV12,colorimetry=bt709
~~~

- `d3d11convert` 使用 D3D11 转换视频画面格式/颜色信息，使其满足后续编码器的输入要求。
- `format=NV12` 约束转换结果为 NV12，即 YUV 4:2:0 格式；`colorimetry=bt709` 声明按 BT.709 色彩参数解释画面。它们是输出格式与色彩解释，不是采集分辨率或编码码率设置。
- 输出仍声明 `(memory:D3D11Memory)`，表示协商目标是 D3D11 GPU 内存中的 NV12 buffer。

### 后续 H.264 编码

~~~text
mfh264enc name=encoder bitrate=<bitrate_kbps>
  low-latency=true gop-size=<target_fps>
~~~

- `mfh264enc` 使用 Windows Media Foundation 进行 H.264 编码；`name=encoder` 是 Publisher 查找该元素并在其输入 pad 注册视频探针时使用的名称。
- `bitrate=<bitrate_kbps>` 来自 `cfg.media.bitrate_kbps`，单位为 kbit/s。
- `low-latency=true` 请求编码器使用低延迟模式。
- `gop-size=<target_fps>` 将 GOP 大小设为目标帧率，例如 30 fps 时设为 30 帧；这通常约为一秒一组关键帧，实际间隔还受编码器行为影响。
- 后续 H.264 输出约束、时间轴整理、解析、RTP 封装和 `webrtcbin` 发送属于 Publisher 的共同下游，详见 [Publisher 管线实现](WebRTC实现.md#publisher-pipeline)。

尺寸不匹配时，编码器输入处的 `captureVideo()` 会拒绝该 buffer，具体检查见本页“管线解析后的探针注册”。

### 管线解析后的探针注册

<code>gst_parse_launch()</code> 创建整条管线成功后，<code>WebRtcPublisher::start()</code> 先取回采集源并锁定它，再给采集源输出端和编码器输入端分别安装探针。随后才会把父管线切到 <code>PLAYING</code> 并发起协商：

~~~c++
if (gpu_capture) {
  self.video_capture = gst_bin_get_by_name(GST_BIN(self.pipeline), "capture");
  // The publisher can negotiate while no capturable game window exists.
  gst_element_set_locked_state(self.video_capture, TRUE);
  auto *source_pad = gst_element_get_static_pad(self.video_capture, "src");
  gst_pad_add_probe(source_pad, GST_PAD_PROBE_TYPE_EVENT_DOWNSTREAM,
                    Impl::captureEvent, &self, nullptr);
  gst_object_unref(source_pad);

  auto *encoder = gst_bin_get_by_name(GST_BIN(self.pipeline), "encoder");
  auto *input = gst_element_get_static_pad(encoder, "sink");
  gst_pad_add_probe(input, GST_PAD_PROBE_TYPE_BUFFER, Impl::captureVideo,
                    &self, nullptr);
  gst_object_unref(input);
  gst_object_unref(encoder);
}
~~~

<code>gst_object_unref()</code> 只释放临时取得的 pad 和 encoder 引用；probe 已安装在管线持有的 pad 上，不会因释放这些局部引用而被移除。以上注册在父管线进入 <code>PLAYING</code> 前完成。

这两个探针挂在不同 pad 上，因此回调看到的数据不同：采集源 <code>src</code> pad 上的事件探针进入 <code>captureEvent()</code>；编码器 <code>sink</code> pad 上的 buffer 探针进入 <code>captureVideo()</code>。

#### <code>captureEvent()</code>：处理采集源 EOS

~~~c++
static GstPadProbeReturn captureEvent(GstPad *, GstPadProbeInfo *info,
                                     gpointer data) {
  if (GST_EVENT_TYPE(GST_PAD_PROBE_INFO_EVENT(info)) != GST_EVENT_EOS)
    return GST_PAD_PROBE_OK;
  auto &self = *static_cast<Impl *>(data);
  self.video_capture_interrupted = true;
  return GST_PAD_PROBE_DROP;
}
~~~

回调注册在采集源 <code>src</code> pad 的下游事件流上。参数和分支的含义如下：

- 第一个 <code>GstPad*</code> 参数在函数签名中留空，因为回调不需要再查询 pad；<code>info</code> 指向当前事件探针信息，<code>GST_PAD_PROBE_INFO_EVENT(info)</code> 从中取出正在经过的事件。
- 注册时传入的 <code>&self</code> 会作为 <code>data</code> 传回回调，再转换成 <code>Impl</code> 引用，以便设置 Publisher 的中断标记。
- 当前事件不是 EOS 时返回 <code>GST_PAD_PROBE_OK</code>：放行这个事件，探针继续留在 pad 上等待后续事件。
- 当前事件是 EOS 时设置 <code>video_capture_interrupted</code>，再返回 <code>GST_PAD_PROBE_DROP</code>：拦下这一个 EOS。这个回调只发出中断信号，不在探针线程里重启源；主循环随后在 <code>setVideoWindow()</code> 中消费标记、停止旧源并安排重试。

> [!NOTE]
>
> `return GST_PAD_PROBE_DROP;` 会丢弃当前经过探针的那条数据，不再让它继续沿管线传递

#### <code>captureVideo()</code>：检查编码器输入并记录采集身份

~~~c++
static GstPadProbeReturn captureVideo(GstPad *pad, GstPadProbeInfo *info,
                                     gpointer data) {
  auto &self = *static_cast<Impl *>(data);
  auto *buffer = GST_PAD_PROBE_INFO_BUFFER(info);
  if (!self.connected.load() || !GST_BUFFER_PTS_IS_VALID(buffer))
    return GST_PAD_PROBE_DROP;

  auto *caps = gst_pad_get_current_caps(pad);
  GstVideoInfo layout;
  const bool have_layout = caps && gst_video_info_from_caps(&layout, caps);
  if (caps)
    gst_caps_unref(caps);
  if (!have_layout ||
      !self.acceptVideoLayout(GST_VIDEO_INFO_WIDTH(&layout),
                              GST_VIDEO_INFO_HEIGHT(&layout), true))
    return GST_PAD_PROBE_DROP;

  auto *event = gst_pad_get_sticky_event(pad, GST_EVENT_SEGMENT, 0);
  if (!event)
    return GST_PAD_PROBE_DROP;
  const GstSegment *segment = nullptr;
  gst_event_parse_segment(event, &segment);
  const auto running_time = segment->format == GST_FORMAT_TIME
                                ? gst_segment_to_running_time(
                                      segment, GST_FORMAT_TIME, GST_BUFFER_PTS(buffer))
                                : GST_CLOCK_TIME_NONE;
  gst_event_unref(event);
  if (!GST_CLOCK_TIME_IS_VALID(running_time))
    return GST_PAD_PROBE_DROP;

  buffer = gst_buffer_make_writable(buffer);
  GST_PAD_PROBE_INFO_DATA(info) = buffer;
  if (!buffer)
    return GST_PAD_PROBE_DROP;

  self.recordVideoSubmission(buffer, running_time, self.tracks[0].submitted.load(),
                             self.origin_us + running_time / GST_USECOND);
  return GST_PAD_PROBE_OK;
}
~~~

回调注册在编码器 <code>sink</code> pad 的 buffer 流上，因此它检查的是**进入 H.264 编码器前的原始视频 buffer**。三个参数分别是：<code>pad</code> 为当前编码器输入 pad，用来读取协商后的 caps 和 sticky segment；<code>info</code> 提供当前 buffer，并允许回调替换 buffer 指针；<code>data</code> 是注册时传入的 <code>&self</code>，转换为 <code>Impl</code> 后访问连接状态、时间起点和视频轨道记录。

按代码执行顺序看：

1. **取出 buffer 并检查发送条件。** <code>GST_PAD_PROBE_INFO_BUFFER(info)</code> 取得当前帧。尚未连接，或 buffer 没有有效 PTS 时，返回 <code>GST_PAD_PROBE_DROP</code> 丢弃当前帧。

2. **确认 caps 和画面尺寸。** <code>gst_pad_get_current_caps(pad)</code> 读取编码器输入 pad 当前协商出的格式；<code>gst_video_info_from_caps()</code> 将其解析成宽、高等视频布局信息，读完后用 <code>gst_caps_unref()</code> 释放 caps 引用。caps 缺失、解析失败，或 <code>acceptVideoLayout()</code> 判定尺寸/布局不受支持时，都丢弃当前帧。这里传入的 <code>true</code> 表示这一路的采集时间戳质量是估算值。

3. **把 buffer PTS 换算到管线时间轴。** <code>gst_pad_get_sticky_event()</code> 取得 pad 上最近生效的 <code>SEGMENT</code> 事件；只有 segment 格式为 <code>GST_FORMAT_TIME</code> 时，才用 <code>gst_segment_to_running_time()</code> 将 buffer 的源 PTS 转成 running time。取不到 segment 时直接丢帧；拿到事件后，无论转换结果有效与否都会先释放事件，转换结果无效再丢帧。

4. **准备可写 buffer。** <code>gst_buffer_make_writable()</code> 确保后续添加时间元数据时 buffer 可写；若底层 buffer 正被共享，GStreamer 可在这里执行写时复制。

   随后将返回的 buffer 写回 <code>GST_PAD_PROBE_INFO_DATA(info)</code>，保证探针放行时后续编码器收到的是这个可写 buffer。若准备失败则丢帧；这里不会把视频像素映射到 CPU 后逐像素复制。

5. **记录帧身份并放行。** <code>recordVideoSubmission()</code> 为可写 buffer 添加采集时间元数据，并保存本次 running time、帧编号和采集时间的关联。随后返回 <code>GST_PAD_PROBE_OK</code>，让当前 buffer 继续进入编码器，同时保留探针供后续帧使用。具体如何校验布局、添加元数据，见下面两个辅助函数。

##### <code>acceptVideoLayout()</code>：校验布局并发布状态

<code>captureVideo()</code> 从协商后的 caps 取出宽高，再调用这个函数判断当前输入是否符合配置：

~~~c++
bool acceptVideoLayout(int width, int height, bool timestamp_estimated,
                       bool packed = true) {
  auto &track = tracks[0];
  if (!packed || width != cfg.media.width || height != cfg.media.height) {
    ++track.unsupported;
    if (track.layout_supported)
      outgoing({{"op", "media_status"}, {"stream_id", "game_video"},
                {"video_state", "unsupported_layout"},
                {"width", width}, {"height", height}});
    track.layout_supported = false;
    return false;
  }
  if (!track.submitted || !track.layout_supported ||
      track.video_quality_estimated != timestamp_estimated)
    outgoing({{"op", "media_status"}, {"stream_id", "game_video"},
              {"video_state", "capturing"}, {"width", width}, {"height", height},
              {"timestamp_quality", timestamp_estimated ? "estimated" : "device"}});
  track.layout_supported = true;
  track.video_quality_estimated = timestamp_estimated;
  return true;
}
~~~

- <code>tracks[0]</code> 是游戏视频轨道。<code>packed</code>、宽度或高度不符合要求时，函数增加 <code>unsupported</code> 计数，将布局标为不支持并返回 <code>false</code>；<code>captureVideo()</code> 收到 <code>false</code> 后会丢弃当前 buffer。
- <code>track.layout_supported</code> 用来识别状态变化：只有从“支持”转为“不支持”时才发送一次 <code>unsupported_layout</code>，避免每帧都重复上报。
- 布局通过时，如果这是首帧、刚从不支持状态恢复，或时间戳质量发生变化，就发送 <code>capturing</code> 状态；随后保存布局和时间戳质量并返回 <code>true</code>。
- 在这里的 WGC 调用中，第三个参数传 <code>true</code>，表示采集时间戳是估算值；第四个参数省略，因此 <code>packed</code> 使用默认值 <code>true</code>。其他 native 帧入口会根据 stride 是否等于 <code>width * 4</code> 显式传入布局结果。

##### <code>recordVideoSubmission()</code>：添加参考时间戳并保存帧关联

<code>captureVideo()</code> 通过这个函数把估算的单调时钟采集时间附加到 buffer，同时把时间和帧编号记入视频轨道：

~~~c++
void recordVideoSubmission(GstBuffer *buffer, GstClockTime pts,
                           uint64_t frame_id, uint64_t capture_us) {
  auto &track = tracks[0];
  auto *reference = gst_caps_new_empty_simple("timestamp/x-tacticlens-monotonic");
  gst_buffer_add_reference_timestamp_meta(buffer, reference,
                                          capture_us * GST_USECOND,
                                          GST_CLOCK_TIME_NONE);
  gst_caps_unref(reference);
  remember(track, pts, {frame_id, capture_us});
  if (track.submitted.fetch_add(1) == 0)
    track.first_submitted_capture = capture_us;
  track.last_submitted_capture = capture_us;
  track.last_submitted_id = frame_id;
}
~~~

- <code>gst_caps_new_empty_simple()</code> 创建参考时钟标识 <code>timestamp/x-tacticlens-monotonic</code>。这个标识说明下面附加的时间戳属于 TacticLens 客户端单调时钟域。

- <code>gst_buffer_add_reference_timestamp_meta()</code> 在原 buffer 上添加 <code>GstReferenceTimestampMeta</code>：时间值是 <code>capture_us</code> 乘以 <code>GST_USECOND</code>，即从微秒换回 GStreamer 使用的纳秒；duration 传 <code>GST_CLOCK_TIME_NONE</code>，表示不提供持续时间。它添加的是一份参考时间元数据，不会改写 buffer 原有的 PTS。[GstBuffer 参考时间戳元数据](https://gstreamer.freedesktop.org/documentation/gstreamer/gstbuffer.html)

  > [!NOTE]
  >
  > **在 buffer 上附加一份“这帧对应的客户端单调时钟采集时间”元数据**，供后续编码帧关联使用。它不会改写 buffer 原有的 PTS。
  >
  > - `buffer`：要添加元数据的视频 buffer。
  > - `reference`：时间基准的标识；这里是 `timestamp/x-tacticlens-monotonic`，表示后面的时间值属于 TacticLens 的单调时钟域。
  > - `capture_us * GST_USECOND`：把微秒换成纳秒，因为 GStreamer 的 `GstClockTime` 用纳秒。比如 `1,234,567 µs` 会传成 `1,234,567,000 ns`。
  > - `GST_CLOCK_TIME_NONE`：不提供时间持续长度；这里只记录一个采集时刻。

- <code>gst_caps_unref()</code> 释放本地创建的 caps 引用；参考时间元数据仍附着在这个编码器输入 buffer 上。编码器是否会把这份元数据复制到编码后的输出 buffer，不能在这里假定；后续 <code>encodedVideo()</code> 会实际检查输出 buffer 上是否还存在该元数据，再决定能否关联编码帧身份，详见 [发送端媒体回调](WebRTC信令与回调实现.md#impl-sender-callbacks)。

- 最后更新已提交帧数、首帧采集时间和最近一帧的编号/时间。调用处在传入 <code>track.submitted.load()</code> 后才会走到这里，因此该值作为本帧的编号；<code>fetch_add(1)</code> 随后将计数加一。

**<code>remember()</code> 保存媒体单位身份映射：**在轨道身份表中保存 <code>pts → {source_unit_id, capture_start_us}</code>。视频调用里，<code>source_unit_id</code> 是帧编号，键 <code>pts</code> 是 segment 换算得到的 <code>running_time</code>。实现如下：

~~~c++
void remember(Track &track, GstClockTime pts,
              tl::media::CaptureMetadata metadata) {
  std::lock_guard lock(track.mutex);
  track.identities[pts] = metadata;
  if (metadata.capture_start_us > 2000000) {
    for (auto item = track.identities.begin();
         item != track.identities.end();) {
      if (item->second.capture_start_us < metadata.capture_start_us - 2000000)
        item = track.identities.erase(item);
      else
        ++item;
    }
  }
  while (track.identities.size() > 256)
    track.identities.erase(track.identities.begin());
}
~~~

- <code>std::lock_guard</code> 在访问身份表期间持有 <code>track.mutex</code>；编码后回调读取同一张表时也使用这把锁，避免并发读写冲突。
- <code>track.identities[pts] = metadata</code> 用时间值作为键，保存对应的帧编号和采集时间。在这条 WGC 探针路径中，键 <code>pts</code> 是传入的 <code>running_time</code>。
- 当采集时间超过 2 秒后，循环删除采集时间早于“当前采集时间减 2 秒”的记录，把身份表限制在近期数据范围内。
- <code>track.identities</code> 是按键排序的 <code>std::map</code>。记录数超过 256 条时，删除键值最小的项，继续限制表的大小。

<code>remember()</code> 也用于音频 <code>push()</code>。音频调用先按来源选择轨道，再用音频 buffer 的 PTS 和采样编号记录身份：

~~~c++
auto &track = self.tracks.at(packet.source + 1);
// ...根据 packet 的 sample_index 计算 pts...
self.remember(track, pts, {packet.sample_index, packet.capture_start_us});
~~~

- 视频传入 <code>tracks[0]</code>；音频传入 <code>tracks[packet.source + 1]</code>，分别对应不同的音频轨道。每个 <code>Track</code> 自己持有一张 <code>identities</code> 表和一把 <code>mutex</code>，所以即使音视频 PTS 数值相同，也会写入不同的表，不会互相覆盖。
- 同一条轨道内若以完全相同的 PTS 再次调用，<code>track.identities[pts] = metadata</code> 会更新该键对应的记录。正常情况下，各视频帧或音频包的时间位置不同；如果发生同键写入，则后写入的身份会覆盖先前值。
- 后续发送路径根据编码后 buffer 的 PTS 查身份表，把对应的帧编号/采样编号和采集时间编码到 RTP 扩展中。音频编码器可能调整时间戳，因此发送路径还会按邻近时间锚点匹配；详见 [发送端媒体回调](WebRTC信令与回调实现.md#impl-sender-callbacks)。

以上各个 <code>GST_PAD_PROBE_DROP</code> 都只丢弃当前事件或 buffer，不会注销探针；<code>GST_PAD_PROBE_OK</code> 则放行当前数据并保留探针。

<code>captureVideo()</code> 不把画面映射为 CPU 像素，也不构造 <code>RawVideoFrame</code>；它只检查 GStreamer buffer 并为后续编码/RTP 关联记录采集身份。

##### PTS 与采集时间映射

<code>captureVideo()</code> 使用 sticky <code>GstSegment</code> 把 WGC buffer PTS 转成 Publisher 管线的 running time；再结合 Publisher 在父管线进入 <code>PLAYING</code> 后计算的 <code>origin_us</code>，换算出客户端单调时钟采集时间：

~~~text
origin_us = client_monotonic_now_us - pipeline_running_time_us
capture_time_us = origin_us + running_time / GST_USECOND
~~~

<code>recordVideoSubmission()</code> 使用 running time 作为身份映射键，记录帧编号和估算的采集时间；同时给 buffer 附加 <code>GstReferenceTimestampMeta</code>，标明该时间属于 TacticLens 单调时钟域。编码后如何用这份身份关联 RTP 扩展，见 [发送端媒体回调](WebRTC信令与回调实现.md#impl-sender-callbacks)。

这里的 PTS 是 WGC buffer 时间戳，不是捕获设备提供的硬件时间戳；<code>captureVideo()</code> 调用 <code>acceptVideoLayout(..., true)</code>，因此采集时间质量标记为估算值。




## HWND 启用采集源

上一节的初始化代码先锁定 <code>capture</code>，之后 <code>WebRtcPublisher::start()</code> 才把父管线切到 <code>PLAYING</code> 并发起协商。此时启动的是 Publisher 管线，WGC 子元素仍不采帧。

WebRTC 连接后，<code>media_client</code> 启动窗口监视器；监视器找到 HWND 后，主循环将 HWND 传给 <code>setVideoWindow()</code>。只有这里才会为 WGC 源绑定窗口并解除锁定：

~~~c++
void WebRtcPublisher::setVideoWindow(std::uintptr_t window) {
  auto &self = *impl_;
  if (!self.video_capture)
    return;
  if (!self.connected.load())
    window = 0;

  const auto now = std::chrono::steady_clock::now();
  if (self.video_capture_interrupted.exchange(false)) {
    self.stopVideoCapture();
    self.video_retry_at = now + std::chrono::milliseconds(500);
  }
  if (window == self.video_window)
    return;
  self.stopVideoCapture();
  if (!window || now < self.video_retry_at)
    return;

  auto *pipeline_clock = gst_element_get_clock(self.pipeline);
  if (!pipeline_clock)
    return;
  const bool clock_set = gst_element_set_clock(self.video_capture, pipeline_clock);
  gst_object_unref(pipeline_clock);
  if (!clock_set) {
    self.error("Could not set the publisher clock on the window capture source");
    return;
  }
  gst_element_set_base_time(self.video_capture, gst_element_get_base_time(self.pipeline));
  g_object_set(self.video_capture, "window-handle", static_cast<guint64>(window), nullptr);
  self.video_window = window;
  gst_element_set_locked_state(self.video_capture, FALSE);
  if (!gst_element_sync_state_with_parent(self.video_capture)) {
    spdlog::warn("Could not start GStreamer window capture");
    self.stopVideoCapture();
    self.video_retry_at = now + std::chrono::milliseconds(500);
    return;
  }
  self.requestVideoKeyframe();
}
~~~

代码可以按三段理解：

- **连接门控与旧源回收：** Publisher 未连接时把 HWND 清零；如果源被标记为中断，先停止旧源，并设置 500 毫秒重试时间。HWND 没变化时直接返回；切换窗口时则先停止旧采集源。
- **把窗口接到 Publisher 时间线上：** 取得父管线时钟并设置给采集源；再复制父管线的 <code>base_time</code>，然后设置 <code>window-handle</code>。这样源元素启动时使用与 Publisher 一致的时钟域。
- **解除锁定并启动：** <code>gst_element_set_locked_state(..., FALSE)</code> 允许采集源跟随父管线运行；<code>gst_element_sync_state_with_parent()</code> 请求它进入父管线当前状态。失败时停止源并安排重试；成功后请求关键帧。

如果监视器没有找到窗口，它会传入 0；如果游戏窗口关闭、隐藏或最小化，监视器也会更新为无效 HWND。Publisher 据此停止当前源，等窗口重新可用后再绑定。

## 采集错误与恢复

WGC 源 pad 上的事件探针监视 EOS。收到 EOS 时设置中断标记并拦截该事件。Publisher bus 收到来自 WGC 源的错误时也标记中断；其他管线元素的错误按 Publisher 故障上报。

主循环继续调用 <code>setVideoWindow()</code> 时会处理这个标记：Publisher 锁定旧源并将其切到 NULL，等待约 500 毫秒后再尝试启动。若同步到父管线失败，也会停止这次启动并进入重试间隔。

目标窗口关闭、隐藏或最小化时，监视器会提供 0 或重新找到的 HWND；Publisher 据此停止旧采集，或重新绑定窗口。断线和退出时，<code>media_client</code> 停止窗口监视与音频采集，再解绑视频源并由 <code>WebRtcPublisher::stop()</code> 清理管线。

### 1. 连通后启动两路采集

<code>media_client</code> 在 Publisher 报告 WebRTC 已连接、且采集源尚未启动时调用 <code>start_sources()</code>。音频分支调用 <code>audio.start({&cs2, &oopz}, ...)</code>，<code>IndependentAudioSource::start()</code> 为 CS2、Oopz 各创建一个工作线程，并把两条独立的有界队列交给采集器：

~~~c++
if (!audio.start({&cs2, &oopz}, cfg, status_callback, &error))
    throw std::runtime_error(error);
~~~

#### <code>IndependentAudioSource::start()</code>：校验并启动双线程

<code>start_sources()</code> 调用这个方法后，方法先检查两条输出队列和采集模式，再保存配置并启动两个工作线程：

~~~c++
bool IndependentAudioSource::start(
    std::array<BoundedQueue<media::AudioPacket>*, 2> outputs,
    const ClientConfig& cfg, Status status, std::string* err) {
    if (!outputs[0] || !outputs[1] ||
        cfg.audio_capture_mode == "system" ||
        cfg.audio_allow_system_fallback) {
        if (err)
            *err = "20ms process capture requires two queues and system fallback disabled";
        return false;
    }
    if (!stop_.exchange(false)) {
        if (err) *err = "already started";
        return false;
    }
    outputs_ = outputs;
    cfg_ = cfg;
    status_ = std::move(status);
    epoch_ = clock::nowSec();
    for (int i = 0; i < 2; ++i)
        threads_[i] = std::thread([this, i] { run(i); });
    return true;
}
~~~

启动顺序如下：

1. **验证输入。** 两个队列都必须有效；采集模式不能是 <code>system</code>，也不能允许系统混音回退。任一条件不满足就写入 <code>err</code> 并返回 <code>false</code>。
2. **防止重复启动。** <code>stop_.exchange(false)</code> 将停止标记切到运行状态；如果原值已经是 <code>false</code>，说明采集器已启动，返回 <code>already started</code>。
3. **保存共享状态。** 保存队列、配置和状态回调。<code>status_ = std::move(status)</code> 将回调转移到对象成员，供工作线程上报状态；<code>epoch_</code> 建立 CS2 与 Oopz 共用的单调时钟时间轴，用于计算采样编号。
4. **创建两个工作线程。** <code>i = 0</code> 的线程处理 CS2，<code>i = 1</code> 的线程处理 Oopz；具体查进程、打开 WASAPI 流和读取数据发生在各自的 <code>run(i)</code> 中。

返回 <code>true</code> 表示两个线程已启动，不表示目标进程已找到或音频包已经产生。线程内的进程查找与重连流程如下。

每个线程约每秒按配置的进程名重新查找 PID。目标进程不存在时保持等待；首次打开失败时报告状态并继续重试；PID 变化时先结束旧流，再按新 PID 打开进程回环流。因此游戏或 Oopz 重启后，可以重新接上新的进程实例。

> [!NOTE]
>
> `status_ = std::move(status);` 把调用方传入的状态回调保存到对象里。两个采集线程之后会用它上报各自进程的等待、打开失败和运行状态；`std::move` 是转移回调对象，避免复制。
>
> `epoch_ = clock::nowSec();` 记录两路采集共用的单调时钟起点。后续用它把采集位置换算成 16 kHz 时间轴上的 `sample_index`，让 CS2 和 Oopz 的样本能对齐。逐包的采集时间仍由 `capture_start_us` 记录。

### WASAPI 采集会话(Stream)与数据包结构

每个采集线程维护一个 `Stream`，保存当前 WASAPI 会话和时间线状态；分包器则把处理后的样本整理成 `AudioPacket`，交给对应输出队列。本节先说明这两个结构及 `Stream` 的状态管理方法；`run(source)` 如何依次使用它们，放在下一节按代码顺序展开。

#### `Stream`：每路采集会话状态

先看 `Stream` 的成员字段摘录；`close()`、`open()`、`status()` 成员函数在后面按流程分别展开：

~~~c++
ComPtr<IAudioClient> client;
ComPtr<IAudioCaptureClient> capture;
std::unique_ptr<Mono16kResampler> resampler;

AudioPacketClock clock;
DWORD pid = 0;
int rate = 0, channels = 0;
bool floating = true;
std::string state = "waiting";
double origin = 0;
uint64_t emitted = 0, packets = 0, discontinuities = 0, late_samples = 0;
uint64_t generation = 0, future_samples = 0, overwritten_samples = 0;
~~~

对应成员可以按职责看：

| 成员 | 保存的内容 |
| --- | --- |
| `client`、`capture` | WASAPI 的音频客户端与采集接口（COM 对象），用于保持当前进程回环流并读取数据。 |
| `pid`、`rate`、`channels`、`floating` | 当前目标进程 PID，以及输入采样率、声道数和浮点/整数样本格式。 |
| `clock` | `AudioPacketClock` 的设备位置、QPC 时间线和时间戳诊断状态。 |
| `resampler` | 当前输入流到单声道 16 kHz 的重采样器及其处理上下文；跨多个 WASAPI 块连续工作。 |
| `state`、`origin`、`emitted` | 状态文本、当前音频时间段起点和输出位置状态；其中 `emitted` 由旧 `WasapiLoopbackSource` 路径使用，当前 `IndependentAudioSource::run()` 不更新。 |
| `packets`、`discontinuities`、`generation` 等计数 | 当前路径维护的 WASAPI 缓冲块数、时间段中断数、成功打开流的代数，以及旧路径保留的对齐统计量。 |

`client` 和 `capture` 持有 WASAPI 的 COM 接口；`pid`、`rate`、`channels`、`floating` 描述当前接入的进程和输入格式；`clock` 跟踪设备帧位置与 QPC 时间；`resampler` 保存跨缓冲块连续重采样需要的状态。`state` 是上报用的状态文本，`origin` 是当前音频时间段的起点。`packets`、`discontinuities`、`generation` 是当前实现会维护的统计量。

这个对象保存的是**采集会话状态**，不是完整录音。`GetBuffer()` 取出的样本先进入局部 `input`，再经过 `resampler` 和 `AudioPacketizer`；packetizer 收满样本后把 `AudioPacket` 推到输出队列。重采样器和 packetizer 各自会保留继续处理所需的少量上下文或未满一包的样本。

`Stream` 也被旧的 `WasapiLoopbackSource` 路径复用，所以成员中还保留 `emitted`、`late_samples`、`future_samples`、`overwritten_samples` 等旧路径字段。当前 `IndependentAudioSource::run()` 不更新这些字段；`status()` 仍会把后三类计数写入状态 JSON，而 `emitted` 不在 JSON 中。

#### `Stream::close()`：释放旧采集会话

~~~c++
void close() {
    if (client) client->Stop();
    capture.Reset(); client.Reset(); resampler.reset(); origin = 0; emitted = 0;
}
~~~

先停止仍打开的 `IAudioClient`，再释放 capture/client 接口和重采样器，并清掉当前时间段的 `origin`、`emitted`。`close()` 本身不设置 `state`，也不清空 `pid`、`packets`、`discontinuities` 或 `generation`；由调用它的 `run()` 分支决定随后设为 `waiting`、`failed` 还是 `stopped`。对象析构时也会调用 `close()`，作为资源兜底。

`open()` 先清理旧会话并记录目标 PID：

##### 异步申请 IAudioClient

`auto handler = Microsoft::WRL::Make<Activation>();`创建 `Activation` 回调对象。它负责接收 Windows 的异步完成通知，并保存完成结果、事件句柄和创建好的 `IAudioClient`

`AUDIOCLIENT_ACTIVATION_PARAMS params{};` 创建参数结构并清零：`params` 是告诉 Windows 要激活哪种音频客户端、目标进程是谁的配置。

`AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK` 指定使用**进程回环采集**：采集目标进程输出的声音，而**不是麦克风输入**或整台电脑的播放混音。

`params.ProcessLoopbackParams.TargetProcessId = target` 指定目标进程 PID。**这里的 `target` 是此前找到的进程 ID。**

`PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE` 把目标进程及其子进程的音频一并纳入。激活最多等待 3 秒，超时或 HRESULT 失败就返回错误。当前 `run()` 传入 `false`，因此上面的 `else` 旧系统混音分支不会执行。

###### `PROPVARIANT` 格式

接下来把结构装进 Windows API 要求的 `PROPVARIANT` 格式：

```c++
PROPVARIANT prop{};
prop.vt = VT_BLOB;
```

`PROPVARIANT` 是 Windows 通用的属性容器。`prop{}` 将它初始化；`VT_BLOB` 表示接下来 `prop` 里装的是一段原始字节数据。

```
prop.blob.cbSize = sizeof(params);
```

告诉 Windows 这段字节数据有多大，也就是 `params` 结构的大小。

```
prop.blob.pBlobData = reinterpret_cast<BYTE*>(&params);
```

把 `params` 的地址交给 `PROPVARIANT`，并按字节指针 `BYTE*` 的类型传递。`reinterpret_cast` 只是转换指针类型，不会复制或改写结构内容。

```
ComPtr<IActivateAudioInterfaceAsyncOperation> operation;
```

准备一个智能指针，用来接收 Windows 返回的异步操作对象。`ComPtr` 会自动管理 COM 对象的引用和释放。

###### 异步申请 IAudioClient

```
hr = ActivateAudioInterfaceAsync(
    VIRTUAL_AUDIO_DEVICE_PROCESS_LOOPBACK,
    __uuidof(IAudioClient),
    &prop,
    handler.Get(),
    &operation);
```

参数依次表示：

- `VIRTUAL_AUDIO_DEVICE_PROCESS_LOOPBACK`：使用 Windows 提供的进程回环虚拟设备。
- `__uuidof(IAudioClient)`：请求拿到 `IAudioClient` 接口。
- `&prop`：传入刚才打包的进程回环参数。
- `handler.Get()`：传入完成通知对象。激活完成后，Windows 会通知它。
- `&operation`：接收异步操作对象。

这是异步调用：`hr` 只表示**请求是否成功提交**，不代表音频客户端已经准备好。**后面代码还要等 `handler` 的事件**，并检查激活结果，成功后才能从 `handler` 取出真正的 `IAudioClient`。

```
if (WaitForSingleObject(handler->event, 3000) != WAIT_OBJECT_0)
    return HRESULT_FROM_WIN32(ERROR_TIMEOUT);
```

最多等待 3000 毫秒，让 `Activation` 回调通知“激活完成”。`WAIT_OBJECT_0` 表示事件已触发，可以继续。代码把其他等待结果都转换成超时错误。

###### 激活最终结果

```
if (FAILED(handler->result)) return handler->result;
client = handler->client;
```

事件触发后，检查**激活最终结果**。成功时，把回调保存的 `IAudioClient` 复制到 `client`，供后面的采集代码使用。这里的 `handler->result` 和前面的 `hr` 不同：`hr` 是“请求有没有提交成功”，`handler->result` 是“异步激活最后有没有成功”。

###### 设置输入音频格式

```
format.wFormatTag = WAVE_FORMAT_IEEE_FLOAT;
format.nChannels = 2;
format.nSamplesPerSec = 48000;
format.wBitsPerSample = 32;
format.nBlockAlign = 8;
format.nAvgBytesPerSec = 384000;
```

部分 Windows 版本无法通过进程回环客户端查询 `GetMixFormat()`，所以代码手动准备一个格式：

- `WAVE_FORMAT_IEEE_FLOAT`：每个样本是浮点数。
- `nChannels = 2`：立体声。
- `nSamplesPerSec = 48000`：每秒 48,000 帧。
- `wBitsPerSample = 32`：每个声道样本占 32 位，也就是 4 字节。
- `nBlockAlign = 8`：一个音频帧包含两个声道，共 `2 × 4 = 8` 字节。
- `nAvgBytesPerSec = 384000`：每秒数据量是 `48000 × 8 = 384000` 字节。

这里的 `format` 更准确地说是传给 `IAudioClient::Initialize()` 的**捕获流格式请求**，不是从目标进程查到的原生输出格式。目标进程可以用自己的格式播放；进程回环捕获请求则指定希望 `IAudioCaptureClient` 按什么格式交付数据。初始化成功后，代码按这个 `format` 设置 `floating`、`rate`、`channels`，并据此解释 `GetBuffer()` 返回的字节。后面的 `Mono16kResampler` 再把捕获流转换成单声道 16 kHz 音频。

**进程回环在部分 Windows 版本上不能通过 `GetMixFormat()` 查询格式，所以 `!system` 分支准备了 48 kHz、双声道、32 位浮点格式作为捕获流请求。**这不是“检测到了目标进程正好输出 48 kHz 浮点”，而是代码选定一个希望 WASAPI 交付的格式。微软的进程回环示例也采用固定的双声道、44.1 kHz、16 位 PCM，并在 `Initialize()` 时启用 `AUTOCONVERTPCM`；进程回环客户端的 `GetMixFormat()` / `IsFormatSupported()` 在一些实现中不可用。[微软进程回环示例代码](https://github.com/microsoft/Windows-classic-samples/blob/main/Samples/ApplicationLoopback/cpp/LoopbackCapture.cpp)、[微软问答：进程回环的格式查询限制](https://learn.microsoft.com/en-us/answers/questions/1125409/loopbackcapture-activateaudiointerfaceasync-with-v)

接下来代码识别所选捕获流格式，只接受 32 位浮点或 16 位 PCM（也兼容 `WAVE_FORMAT_EXTENSIBLE` 包装）：

##### 初始化WASAPI采集客户端

###### 选择并识别格式

```
const WAVEFORMATEX* f = allocated ? allocated : &format;
```

如果 `allocated` 不为空，就使用它指向的格式；否则使用前面准备好的 `format`。当前 `run()` 调用 `open(pid, false)`，**进程回环分支使用的是 `format`。**

```
floating = f->wFormatTag == WAVE_FORMAT_IEEE_FLOAT;
bool pcm = f->wFormatTag == WAVE_FORMAT_PCM;
```

根据格式标记判断样本是浮点数还是整数 PCM。

```
if (f->wFormatTag == WAVE_FORMAT_EXTENSIBLE) {
    auto* e = reinterpret_cast<const WAVEFORMATEXTENSIBLE*>(f);
    floating = IsEqualGUID(e->SubFormat, KSDATAFORMAT_SUBTYPE_IEEE_FLOAT);
    pcm = IsEqualGUID(e->SubFormat, KSDATAFORMAT_SUBTYPE_PCM);
}
```

有些格式会用 `WAVE_FORMAT_EXTENSIBLE` 作为外层包装。这时把它按扩展格式结构读取，再看 `SubFormat`，才能知道里面实际装的是浮点音频还是 PCM。

```
if ((!floating || f->wBitsPerSample != 32) &&
    (!pcm || f->wBitsPerSample != 16)) {
```

这里只接受两种输入：

- 32 位浮点音频；
- 16 位 PCM 音频。

如果两种都不符合，就释放可能由 `GetMixFormat()` 分配的内存，并返回“不支持的格式”：

```
    if (allocated) CoTaskMemFree(allocated);
    return AUDCLNT_E_UNSUPPORTED_FORMAT;
}
```

###### 记录输入参数并初始化时钟

```
rate = static_cast<int>(f->nSamplesPerSec);
channels = f->nChannels;
clock.reset(rate);
```

把输入采样率和声道数记到 `Stream`。

`clock.reset(rate)` 用这个输入采样率重置音频时钟；这里的 `rate` 是 WASAPI **输入端的采样率**，不是最后输出的 16 kHz。

###### 初始化 WASAPI 客户端

```
hr = client->Initialize(
    AUDCLNT_SHAREMODE_SHARED,
    AUDCLNT_STREAMFLAGS_LOOPBACK |
        (system ? 0 : AUDCLNT_STREAMFLAGS_AUTOCONVERTPCM),
    2000000, 0, f, nullptr);
```

`Initialize()` 按给定模式和格式初始化音频客户端：

- `AUDCLNT_SHAREMODE_SHARED`：使用共享模式。（应用程序可以多个同时播放；独占模式只会放一个程序的）
- `AUDCLNT_STREAMFLAGS_LOOPBACK`：启用回环采集。
- `system ? 0 : AUDCLNT_STREAMFLAGS_AUTOCONVERTPCM`：当前 `system` 是 `false`，所以进程回环会带上自动转换标志。WASAPI 可按需在应用请求的未压缩格式与音频引擎混音格式之间加入声道矩阵和采样率转换；这不代表任意格式都一定被接受。[微软对 `AUTOCONVERTPCM` 的说明](https://learn.microsoft.com/en-us/windows/win32/coreaudio/audclnt-streamflags-xxx-constants)
- `2000000`：缓冲时长，单位是 100 纳秒，等于 200 毫秒。
- `0`：共享模式下的周期参数。
- `f`：刚才选出的输入格式。
- `nullptr`：没有指定音频会话 GUID。

```
if (allocated) CoTaskMemFree(allocated);
if (FAILED(hr)) return hr;
```

`Initialize()` 用完格式后，释放 `GetMixFormat()` 分配的内存。若初始化失败，就把错误返回给调用方；当前代码不会悄悄按错误格式继续读，也没有再尝试其他候选格式。因此 48 kHz 双声道浮点是一个有自动转换配合的固定请求，但不是对所有 Windows 构建都必然成功的保证。

###### 取得采集接口

```
hr = client->GetService(IID_PPV_ARGS(&capture));
if (FAILED(hr)) return hr;
```

从 `IAudioClient` 取得真正用于读取数据的 `IAudioCaptureClient`，后续 `run()` 会通过它调用 `GetBuffer()`。

###### 创建重采样器

告诉它输入的采样率和声道数。它后续会把输入变成单声道 16 kHz 音频。

```
resampler = std::make_unique<Mono16kResampler>(rate, channels);
```

###### WASAPI 客户端启动

```
hr = client->Start();
```

成功时更新会话状态并写日志：

```
if (SUCCEEDED(hr)) {
    ++generation;
    state = "capturing";
    spdlog::info(...);
}
return hr;
```

`generation` 在每次成功启动时加一，`state` 设为 `capturing`。最后返回 `hr`；如果启动失败，`run()` 会负责清理资源并把状态设为 `failed`。

#### `Stream::status()`：上报会话状态

`status()` 把会话当前值转换为 JSON，供 `status_` 回调发送。它不是录音保存接口：

~~~c++
json status(const std::string& process) const {
    return {{"process",process},{"pid",pid},{"state",state},{"input_rate",rate},
        {"channels",channels},{"packets",packets},{"discontinuities",discontinuities},
        {"late_samples",late_samples},{"future_samples",future_samples},
        {"overwritten_samples",overwritten_samples},
        {"timestamp_errors",clock.timestamp_errors},
        {"estimated_timestamp_packets",clock.estimated_packets},
        {"data_discontinuity_flags",clock.data_discontinuity_flags},
        {"qpc_outliers",clock.qpc_outliers},{"clock_reanchors",clock.reanchors},
        {"device_gap_frames",clock.gap_frames},
        {"device_overlap_frames",clock.overlap_frames},{"generation",generation},
        {"resampler","kaiser_sinc_v1"},
        {"resampler_lookahead_frames",resampler?resampler->lookaheadInputFrames():0}};
}
~~~

此 JSON 会包含当前 `IndependentAudioSource::run()` 更新的包数、断点数、打开代数和时钟诊断；旧对齐计数在这条路径中保持初值。`run()` 在进程发现周期、采集错误和线程退出时调用状态回调。

### `AudioPacket`：送入输出队列的数据结构

`AudioPacketizer` 将每路重采样后的 PCM 样本整理成 `AudioPacket`。结构定义如下：

~~~c++
struct AudioPacket {
    int source = 0;
    uint64_t sample_index = 0;
    uint64_t capture_start_us = 0;
    std::vector<int16_t> pcm;
    uint32_t received_samples = 0;
    bool discontinuity = false;
    bool timestamp_estimated = false;
};
~~~

| 成员 | 含义 |
| --- | --- |
| `source` | 音频来源编号：`0` 对应 CS2，`1` 对应 Oopz。 |
| `sample_index` | 这包第一个样本在两路共用 16 kHz 时间轴上的编号。 |
| `capture_start_us` | 这包起始位置对应的客户端单调时钟时间，单位为微秒。 |
| `pcm` | 这包携带的 S16 PCM 样本。 |
| `received_samples` | 包内实际收到的样本数；正常满包为 320，末尾包可能更短。 |
| `discontinuity` | 表示此包是否位于新时间段起始处，供下游识别时间线断点。 |
| `timestamp_estimated` | 表示包的采集时间戳是否由时钟逻辑估算。`false` 表示使用了有效时间戳；`true` 表示时间戳无效 |

每个来源各有一个 `AudioPacketizer`。采集线程把重采样后的 16 kHz 单声道 S16 PCM 样本交给 `push()`；积累到 320 个样本（20 ms）时发出完整包，`finish()` 则发出不足 320 个样本的尾包。包里的来源编号、样本位置、采集时间和时间质量标志由 `AudioPacket` 保存；回调再把它放入该来源的有界队列。

#### `AudioPacketizer` 各函数的职责与调用流程

`AudioPacketizer` 负责把 16 kHz 单声道 PCM 按段整理成 `AudioPacket`。下面先把 `run(source)` 的调用点连起来，再逐个说明 `begin()`、`push()`、`finish()` 和内部 `emit()` 的工作：

~~~c++
media::AudioPacketizer packetizer(source,[&](media::AudioPacket packet) {
    outputs_[source]->push(std::move(packet));
});
auto flush=[&] {
    if (stream.resampler)
        packetizer.push(stream.resampler->flush(),segment_estimated);
    packetizer.finish();
};

if (position.new_segment) {
    flush();
    // 更新时间段并重建 resampler
    packetizer.begin(index,capture_start_us,position.estimated);
}
packetizer.push(stream.resampler->push(input),position.estimated);
~~~

图中的 `flush()` 会在目标进程消失、PID 变化或流需要重开时调用；也会在检测到 `position.new_segment`、WASAPI 读取失败以及线程停止时调用。新时间段的实际顺序是：`flush()` 结束旧段，`run()` 调 `begin()` 建立新段，然后把当前块的重采样结果交给 `push()`。`begin()` 内部还会调用一次 `finish()`，以防旧段仍有未发出的样本；通常前面的 `flush()` 已经清空它。

| 函数 | 谁在什么时候调用 | 作用 |
| --- | --- | --- |
| 构造函数 `AudioPacketizer(source, emit)` | 每个 `run(source)` 线程启动时调用一次。 | 记录来源编号，并保存回调；包发出时，回调把它移动到 `outputs_[source]`。 |
| `begin(sample_index, capture_start_us, estimated)` | `run()` 检测到 `position.new_segment`，并先 `flush()` 旧段后调用。 | 调用 `finish()` 收尾，再设置新段的样本起点、时间戳和估算标记；清零段内 `offset_`，把首包标记为 `discontinuity`，并设为 active。 |
| `push(samples, estimated)` | `run()` 每处理一批 WASAPI 数据时，将 `resampler.push(input)` 的结果传入；`flush()` 也会把 `resampler.flush()` 的尾样本传入。 | 若尚未 `begin()` 就忽略输入；否则逐样本放入 `pending_`，累计估算标记。每收满 320 个样本便调用 `emit(320)`。 |
| `finish()` | `run()` 的 `flush()` 在尾样本 push 后调用；`begin()` 内部也会调用。 | 若 `pending_` 还有样本，调用 `emit()` 发出较短的末包，然后把 packetizer 设为 inactive。没有剩余样本时只结束当前段。 |
| `emit(count)`（私有） | 由 `push()` 在满 320 个样本时调用，或由 `finish()` 在有尾样本时调用。 | 填好 `AudioPacket` 的来源、样本位置、采集时间、PCM、有效样本数和时间标记；清空 `pending_`、推进段内偏移，最后调用 `emit_` 回调。 |

#### 各函数按执行顺序展开

上面的表格先概括“谁调用、何时调用”。下面贴出类中对应的实现，并沿着函数体说明每一步对样本和状态做了什么。

##### 1. 构造函数：保存来源和发包回调

`run(source)` 为当前来源创建一个 `AudioPacketizer`：

~~~c++
media::AudioPacketizer packetizer(source,[&](media::AudioPacket packet) {
    outputs_[source]->push(std::move(packet));
});
~~~

构造函数本身只保存两个后续要用的值，不读取或生成音频：

~~~c++
using Emit = std::function<void(AudioPacket)>;
explicit AudioPacketizer(int source, Emit emit)
    : source_(source), emit_(std::move(emit)) {}
~~~

`source_` 记录当前是哪个来源，之后每个包都会带上它。`emit_` 保存上面的 lambda；`AudioPacketizer` 每组好一包，就调用这个回调。lambda 将包移动到对应的 `outputs_[source]` 队列，供后续主循环取出。因为 `run(source)` 为每个来源在线程内各创建一个实例，两路样本和待发缓存彼此独立。

##### 2. `begin()`：建立一段新的音频时间线

`run()` 只在时钟判断 `position.new_segment` 为真时调用 `begin()`。调用点先结束旧段，再计算新段的全局样本编号和起始时间：

~~~c++
if (position.new_segment) {
    flush();
    if (stream.origin) ++stream.discontinuities;
    stream.origin=position.start;
    segment_estimated=position.estimated;
    stream.resampler=std::make_unique<Mono16kResampler>(stream.rate,stream.channels);
    const auto index=static_cast<uint64_t>(
        (std::max)(0LL,std::llround((position.start-epoch_)*16000)));
    packetizer.begin(index,
        static_cast<uint64_t>(std::llround(position.start*1e6)),
        position.estimated);
}
~~~

`index` 把新段起点换算成相对于共享 `epoch_` 的 16 kHz 样本编号；`position.start * 1e6` 则把起始秒数换算成微秒。随后进入 `begin()`：

~~~c++
void begin(uint64_t sample_index, uint64_t capture_start_us, bool estimated) {
    finish();
    index_=sample_index;
    start_us_=capture_start_us;
    estimated_=estimated;
    offset_=0;
    discontinuity_=true;
    active_=true;
}
~~~

第一步调用 `finish()`，保证上一段若还有未满 320 个样本，就先按旧段的时间信息发出去。`run()` 前面已经执行过 `flush()`，通常此时缓存为空；这里再次收尾是 `begin()` 自身的保护。接着保存新段的起始样本位置、起始时间和段级时间戳质量；`offset_` 从零开始计数，`discontinuity_` 让新段的首个包带断点标记，`active_` 则允许后续 `push()` 接收样本。

##### 3. `push()`：逐样本累积，满 320 个就发包

正常采集时，调用方先将当前 WASAPI 缓冲区交给重采样器，再把输出样本传给 `push()`：

~~~c++
packetizer.push(stream.resampler->push(input), position.estimated);
~~~

重采样器可能一次输出零个、少于 320 个或多于 320 个样本，所以 `push()` 不假设每次调用刚好对应一个包。它的实现是：

~~~c++
void push(std::span<const int16_t> samples, bool estimated=false) {
    if (!active_) return;
    for (auto sample : samples) {
        pending_.push_back(sample);
        estimated_pending_ = estimated_pending_ || estimated;
        if (pending_.size() == 320) emit(320);
    }
}
~~~

如果新时间段还没有通过 `begin()` 建立，`active_` 为假，输入会被忽略。处于活动状态时，函数把传入范围里的样本逐个放进 `pending_`；同时用逻辑或累积 `estimated`，使当前包只要有一批样本的时间戳是估算值，包的标记就会反映出来。每积到 320 个 16 kHz 样本便调用 `emit(320)`：(320 ÷ 16000) 秒 = 0.02 秒，也就是 20 毫秒。若同一次 `push()` 带来更多样本，循环会在发完当前包后继续填下一包。

这里的 `estimated_pending_ = estimated_pending_ || estimated` 是“把当前批次的标记合并进这一包”：`||` 是布尔“或”。例如，当前包此前没有估算标记（`false`），这次传入的是估算时间（`true`），结果就变成 `true`；之后即使某次传入 `false`，它仍保持 `true`。等 `emit()` 发出这一包后，代码会把 `estimated_pending_` 清回 `false`，用于下一包。这样一包若由多次 `push()` 拼成，只要其中任意一批的时间戳是估算的，整包就会标记为估算时间。

结束或切换时间段时，`flush()` 会先让重采样器输出最后一段样本，再把它们交给同一个 packetizer `push()`：

~~~c++
auto flush = [&] {
    if (stream.resampler)
        packetizer.push(stream.resampler->flush(), segment_estimated);
    packetizer.finish();
};
~~~

这里要区分两个 `flush`：`stream.resampler->flush()` 处理的是重采样器，`packetizer.finish()` 处理的是分包器。

重采样器使用带前视窗口的滤波；为了计算靠近输入末尾的输出，它需要看到后续输入帧，所以普通 `resampler.push()` 会暂存末尾附近尚不能计算的部分。采集结束或切段时，`resampler.flush()` 告诉它“后面不会再有输入”，然后把基于现有尾部输入计算出的最后一批 16 kHz 样本返回（滤波窗口缺少的未来部分按零处理）。

这些返回值再交给 `packetizer.push()`，与之前的重采样结果放进同一个 `pending_`。最后 `packetizer.finish()` 把 `pending_` 中不足 320 个的样本发成尾包。因此这两步分别是：重采样器排出尾部输出，分包器排出尾部数据包。

##### 4. `finish()`：发出不足一包的段尾样本并停止接收

`finish()` 由 `flush()` 在重采样器尾样本送入 `push()` 后调用；`begin()` 内部也会调用它：

~~~c++
void finish() {
    if (!pending_.empty()) emit(pending_.size());
    active_=false;
}
~~~

平时 `push()` 一旦凑够 320 个就会立即发包，所以 `pending_` 中通常只会剩 0 到 319 个样本。若仍有样本，`finish()` 按实际剩余数量调用 `emit()`，发出一个较短的尾包；它不会用静音补足 320 个样本。若缓存为空，就不产生空包。最后把 `active_` 设为假，避免旧段结束后、下一次 `begin()` 前误收样本。

在 `run()` 中，`flush()` 会用于目标进程消失、PID 或流变化、检测到新时间段、WASAPI 读取失败，以及采集线程退出等收尾路径。新段的顺序是：先 `flush()` 旧段，再 `begin()` 新段，之后才把新段样本传给 `push()`。

##### 5. `emit()`：组装 `AudioPacket` 并交给队列

`emit()` 是私有函数，只由 `push()` 在满 320 个样本时，或由 `finish()` 在段尾有剩余样本时调用：

~~~c++
void emit(std::size_t count) {
    AudioPacket packet;
    packet.source=source_;
    packet.sample_index=index_+offset_;
    packet.capture_start_us=start_us_+offset_*1000000/16000;
    packet.pcm.assign(pending_.begin(),pending_.end());
    packet.received_samples=static_cast<uint32_t>(count);
    packet.discontinuity=discontinuity_;
    packet.timestamp_estimated=estimated_||estimated_pending_;

    pending_.clear();
    offset_+=count;
    discontinuity_=false;
    estimated_pending_=false;
    emit_(std::move(packet));
}
~~~

组包时，

`sample_index` 是段起始编号加本段已发出的样本数；

`capture_start_us` 用相同的 `offset_` 换算该包的起始时间，采样率为 16 kHz。

`pcm` 保存实际样本，

`received_samples` 记录有效样本数；

时间戳估算标记取段级标记 `estimated_` 与本包累计标记 `estimated_pending_` 的逻辑或。第一包使用 `discontinuity_=true`，随后清为假，因此同一段后续包不会重复标记断点。

> - `estimated_`：当前时间段的时间戳是否是估算的，由 `begin()` 设置。
> - `estimated_pending_`：当前这包累计的样本中，是否有批次的时间戳是估算的，由 `push()` 累积。
>
> 所以，**整段时间是估算的，或者当前包里的任意一批样本时间是估算的，这个包就会标记为 `true`**。这行只设置元数据标记，不会修改音频样本或时间戳本身。

元数据填好后，函数清空待发样本并将 `offset_` 增加本包样本数，为下一包准备正确的位置；然后重置本包的估算标记，最后通过 `emit_` 将包移动到 `outputs_[source]`。所以完整路径是：`run()` 调 `push()` 或 `flush()` → 样本进入 `pending_` → `push()` 满 320 或 `finish()` 收尾时调用 `emit()` → `emit_` 回调把 `AudioPacket` 放入对应队列。

因此，`begin()` 建立一段时间线，`push()` 持续累积样本并在满包时发包，`finish()` 负责把段尾的不足一包样本发出；`emit()` 组装包并将它交给输出队列。

### observe查看时间戳是否连续

每次调用代表收到一个音频包：

- `frames`：包里的音频帧数。
- `device`：设备报告的起始帧位置。
- `stamp`：设备时间戳，单位应与 `arrival` 相同，通常是秒。(`qpc / 1e7 + qpc_offset`)代码把 `qpc` 从 100 纳秒单位换算成秒，再加上偏移量，使它和项目的 `clock::nowSec()` 使用同一时间基准
- `valid`：这次设备时间戳是否可信。
- `discontinuity`：采集 API 是否报告数据不连续。
- `arrival`：包到达时的时间，用于估算无效时间戳。

它返回：

```
{ start, new_segment, estimated }
```

其中：

- `start`：这个包在时间轴上的起始时间。
- `new_segment`：是否开始了一个新的时间段，也就是重新锚定时间轴。
- `estimated`：这次包的位置是否是估算出来的。

#### 时间戳无效时

如果 `valid == false`：

- `timestamp_errors` 和 `estimated_packets` 各加一。
- 如果这是第一个包，用 `arrival - frames / rate` 估算包的起始时间。
- 后续包仍根据已经累计的帧数延续时间轴。
- 返回的 `estimated` 为 `true`。

因此，无效时间戳不会丢掉这个音频包，只是标记其时间位置是估算的。

#### 它如何判断时间是否连续

`expected` 是根据当前时间锚点和已累计帧数推算出的预期时间：

```
origin_ + frames_ / rate_
```

然后检查两种异常：

这两个判断分别检查**设备帧位置**和**时间戳**是否偏离预期。

```
const bool device_break =
    valid && have_device_ && device != device_end_;
```

- `valid`：当前设备位置有效。
- `have_device_`：之前已经记录过有效设备位置。
- `device_end_`：上一包结束后的设备帧位置，通常等于“上一包起始位置 + 帧数”。
- 所以只要当前包的 `device` **不等于上一包应结束的位置**，就认为设备帧位置不连续。

例如：上一包从设备帧 `1000` 开始，含 `480` 帧，那么 `device_end_` 是 `1480`。下一包从 `1480` 开始是连续的；从 `1485` 开始表示中间缺了 5 帧，从 `1470` 开始表示有 10 帧重叠。

```
const bool qpc_break =
    valid && anchored_ && std::abs(stamp - expected) > 0.025;
```

- `anchored_`：已经建立过时间锚点，可以比较时间。
- `expected`：按锚点和累计帧数推算出的当前包预期时间。
- 如果 `stamp` 与 `expected` 相差超过 `0.025` 秒，也就是 **25 毫秒**，就认为时间戳偏离较大。
- `std::abs` 表示无论时间戳早了还是晚了，都会检测出来。

例如，预期时间是 `10.010` 秒，实际 `stamp` 是 `10.040` 秒，相差 30 毫秒，`qpc_break` 就是 `true`。

后面的逻辑会直接用 `device_break` 触发新时间段；`qpc_break` 则只有在没有可用设备位置（`!have_device_`）时，才会单独触发新时间段。

**记录 QPC 时间戳异常**

```
if (qpc_break) ++qpc_outliers;
```

如果时间戳与预期相差超过 25 ms，就把异常计数加一。

**统计设备帧位置的间隙或重叠**

```
if (device_break) {
    if (device > device_end_)
        gap_frames += device - device_end_;
    else
        overlap_frames += device_end_ - device;
}
```

`device_end_` 是上一包预期的结束帧位置：

- 当前 `device` 大于它：中间缺了帧，计入 `gap_frames`。
- 当前 `device` 小于它：与上一包重叠，计入 `overlap_frames`。

**判断是否开始新的时间段**

```
const bool segment =
    !anchored_ || device_break || (qpc_break && !have_device_);
```

以下情况会开启新时间段：

- 还没有时间锚点，这是第一个包；
- 设备帧位置不连续；
- QPC 时间戳偏离预期，且没有设备帧位置可用。

所以，如果设备帧位置连续，即使 QPC 时间戳偏离，也只记录 `qpc_outliers`，不会单独重新分段。

**需要分段时，重设时间锚点**

```
if (segment) {
    if (anchored_) ++reanchors;
    origin_ = valid ? stamp : arrival - double(frames) / rate_;
    frames_ = 0;
    anchored_ = true;
}
```

- 如果此前已经有锚点，`reanchors` 加一。
- 时间戳有效时，用 `stamp` 作为新起点。
- 时间戳无效时，用到达时间减去包时长估算起点。
- 将累计帧数清零，然后标记锚点已建立。

**计算当前包的起始时间并推进帧计数**

```
const double start = origin_ + double(frames_) / rate_;
frames_ += frames;
```

当前包的起始时间是锚点时间加上此前累计帧数对应的时长。随后把当前包的帧数加入累计值，供下一个包计算。

**更新设备帧位置记录**

```
if (valid) {
    device_end_ = device + frames;
    have_device_ = true;
} else if (have_device_) {
    device_end_ += frames;
}
```

有效时，用当前包的设备起始位置加帧数，得到新的预期结束位置。时间戳无效但之前已有设备位置时，则只按包里的帧数推进结束位置。

#### 一个简单例子

假设采样率是 48 kHz，一个包有 480 帧，那么这个包的时长是：

```
480 / 48000 = 0.01 秒
```

若第一个有效时间戳是 `10.0` 秒，后续设备帧位置连续，下一包的起始时间大约就是 `10.01` 秒。

#### 统计字段的含义

- `timestamp_errors`：无效时间戳次数。
- `estimated_packets`：使用估算位置的包数。
- `data_discontinuity_flags`：采集 API 报告不连续的次数。
- `reanchors`：重新建立时间锚点的次数。
- `qpc_outliers`：QPC 时间戳偏离预期超过 25 ms 的次数。
- `gap_frames` / `overlap_frames`：设备帧位置检测出的间隙帧数 / 重叠帧数。

### Mono16kResampler：流式重采样流程

`Mono16kResampler` 在 `client/src/resampler.cpp` 中实现。它接收采集格式的交错多声道 `float` 样本，输出 **16 kHz、单声道、S16 PCM**。这里不是简单地每隔几个输入样本取一个，而是先用低通滤波抑制高频，再按 16 kHz 的时间点计算输出样本。

#### 1. 构造时准备滤波器

构造函数接收实际采集采样率和声道数。采样率需在 8–384 kHz 之间，声道数需在 1–32 之间。若输入已经是 16 kHz，就不需要重采样滤波器，后续只做声道混合和量化。

先检查输入格式，并处理已经是目标采样率的情况：

~~~c++
if (rate < 8000 || rate > 384000 || channels < 1 || channels > 32)
    throw std::invalid_argument("unsupported capture format");
if (rate == output_rate) return;
~~~

采样率或声道数超出支持范围时直接报错。如果输入率已经是 `output_rate`（16 kHz），构造函数提前返回，不创建滤波器；`push()` 会走只混合声道、量化样本的快速路径。

对其他输入率，先计算输入、输出采样率的约分关系和滤波器长度：

~~~c++
divisor_ = std::gcd(rate, output_rate);
half_ = static_cast<int>(std::ceil(
    48.0 * std::max(1.0, double(rate) / output_rate)));
const int phases = output_rate / divisor_;
~~~

`divisor_` 是输入率与 16 kHz 的最大公约数；`phases` 是约分后需要预计算的不同小数相位数。48 kHz 转 16 kHz 时相位数是 1；44.1 kHz 转 16 kHz 时是 160。`half_` 是滤波器中心左右覆盖的输入帧数，每个相位最终有 `2 * half_ + 1` 个 tap。48 kHz 输入时 `half_` 为 144 帧，约 3 ms。

接着设置低通截止频率和 Kaiser 窗参数，并为所有相位准备存储空间：

~~~c++
const double cutoff = 0.45 * std::min(rate, output_rate) / rate;
constexpr double beta = 8.6;
const double denominator = i0(beta);
kernels_.resize(phases);
~~~

`cutoff` 以输入采样率为基准计算。`0.45` 在 Nyquist 边界前留出过渡带；降采样时取较低的采样率作为截止频率基准，减少高频折叠造成的混叠。`beta` 控制 Kaiser 窗的形状；`i0(beta)` 是后续窗函数的归一化分母。`kernels_.resize(phases)` 为每个不同的小数相位创建一个 kernel 槽位。

外层循环为每种小数相位创建一组 tap 系数：

~~~c++
for (int phase = 0; phase < phases; ++phase) {
    const double fraction = double(phase) / phases;
    auto& kernel = kernels_[phase];
    kernel.resize(2 * half_ + 1);
    double total = 0;
    // 内层逐 tap 计算并填入 kernel
}
~~~

`fraction` 从 0 到小于 1，表示输出采样点相对输入帧的不同小数偏移。重采样时，输出点不一定正好落在整数输入帧上，所以要为这些位置预先准备不同的滤波系数。`kernel` 引用当前相位的系数数组；`total` 用于累计本组系数，稍后做归一化。

内层循环为当前相位的每个 tap 计算 Kaiser 窗、sinc 权重，并把系数存入 kernel：

~~~c++
for (int tap = -half_; tap <= half_; ++tap) {
    const double x = tap - fraction;
    const double u = x / half_;
    const double window = std::abs(u) <= 1
        ? i0(beta * std::sqrt(std::max(0.0, 1 - u * u))) / denominator
        : 0;
    const double y = 2 * cutoff * x;
    const double sinc = std::abs(y) < 1e-14
        ? 1
        : std::sin(std::numbers::pi * y) / (std::numbers::pi * y);
    const double weight = 2 * cutoff * sinc * window;
    kernel[tap + half_] = weight;
    total += weight;
}
~~~

`tap` 从 `-half_` 到 `+half_` 遍历滤波器中心两侧的输入帧。`x = tap - fraction` 表示该输入 tap 相对目标输出位置的距离；`u` 把这个距离缩放到窗函数的 `[-1, 1]` 范围。`window` 是 Kaiser 窗：`i0()` 计算第一类零阶修正贝塞尔函数，除以 `i0(beta)` 后窗中心值为 1；超出 `|u| <= 1` 时权重为 0。`max(0.0, 1 - u * u)` 防止浮点误差让平方根输入略小于 0。

`y` 将距离按截止频率缩放。`sinc` 是理想低通滤波器的 sinc 系数；当 `y` 接近 0 时直接取极限值 1，避免 `0/0`。`2 * cutoff * sinc` 得到理想低通的 tap 系数，乘上 Kaiser 窗后成为有限长度、边缘逐渐衰减的实际系数。`tap + half_` 把从负数开始的 tap 编号映射到数组下标；`total` 累加本相位的系数，供后续归一化。

每个相位的系数生成后，统一归一化：

~~~c++
for (auto& weight : kernel)
    weight /= total;
~~~

归一化使这组 kernel 的系数和为 1，保证完整滤波窗口下的直流增益为 1。序列首尾缺少窗口外的输入帧时，这些位置按零处理，所以边界输出仍会受到零填充影响。

构造阶段只预计算这些系数；之后 `emit()` 根据当前输出点的位置选择对应相位，并用该相位的 kernel 对附近输入帧加权求和。

#### 2. `push()` 混合声道并缓存输入

`push()` 每次接收一批交错排列的 `float` 样本。开始处理前，先检查重采样器状态和输入是否包含完整帧：

~~~c++
if (finished_)
    throw std::logic_error("resampler already flushed");
if (input.size() % channels_)
    throw std::invalid_argument("partial audio frame");
~~~

`flush()` 调用后，`finished_` 会变为 `true`，此时不能再向这个实例追加样本。每帧必须包含 `channels_` 个样本，因此输入样本总数不能被声道数整除；否则输入末尾是不完整帧，代码会报错。

如果输入本身已经是 16 kHz，就直接做声道混合和 S16 量化：

~~~c++
if (rate_ == output_rate)
    return downmixMonoPcm16(input, channels_);
~~~

这条分支不进入 sinc 滤波器，也不需要等待前视样本；采样率不变，只将多声道变成单声道并转为 `int16_t`。

其他采样率需要先把输入转成单声道并保存在内部缓冲区。代码先为这批帧预留容量：

~~~c++
buffer_.reserve(buffer_.size() + input.size() / channels_);
~~~

`input.size() / channels_` 是本批的帧数；每个输入帧混成一个单声道样本，所以缓冲区最多需要增加这么多元素。`reserve()` 只扩展容量，不改变当前样本数量。

随后按帧遍历交错样本，把每帧各声道求平均：

~~~c++
for (std::size_t i = 0; i < input.size(); i += channels_) {
    double mono = 0;
    for (int c = 0; c < channels_; ++c)
        mono += std::isfinite(input[i + c]) ? input[i + c] : 0;
    buffer_.push_back(mono / channels_);
}
~~~

外层每次跨过 `channels_` 个样本，移动到下一帧；内层读取当前帧的每个声道。`std::isfinite()` 将 NaN 和无穷值按 0 处理，再把声道值相加并除以声道数，得到一个单声道样本，以 `double` 放入 `buffer_`。

一批输入处理完后，更新累计输入帧数，并尝试输出当前已有足够前视数据的重采样结果：

~~~c++
input_frames_ += input.size() / channels_;
return emit(false);
~~~

`input_frames_` 按帧累计，不乘声道数。`emit(false)` 表示音频还会继续到来：它输出当前可计算的 16 kHz 样本，并把需要等待后续帧的尾部留在缓冲区，等下一次 `push()` 或最终的 `flush()` 再处理。

`buffer_start_` 记录 `buffer_` 第一个样本在本段输入中的帧编号。后续 `emit()` 删除已不再需要的旧样本时，会同步推进这个位置，确保滤波器用全局输入帧编号查找缓冲区样本时仍能对齐。

#### 3. `emit(final)` 按 16 kHz 时间点计算输出

`emit()` 先根据当前累计输入帧数，计算理论上对应多少个 16 kHz 输出样本，并为这些样本预留空间：

~~~c++
const int64_t count = input_frames_ * output_rate / rate_;
out.reserve(static_cast<std::size_t>(count - emitted_));
~~~

`count` 使用整数除法，等于当前输入帧数换算后的输出样本总数；`emitted_` 是已经生成的数量。两者之差是最多还可能生成的样本数。流式情况下，滤波器的前视要求可能让本次实际输出少于这个预留量。

`while (emitted_ < count)` 循环逐个计算尚未生成的输出样本。循环体先把当前输出位置映射到输入时间轴，再检查滤波器所需的未来帧是否已到：

~~~c++
const int64_t numerator = emitted_ * rate_;
const int64_t center = numerator / output_rate;
if (!final && center + half_ >= input_frames_)
    break;
~~~

`numerator / output_rate` 计算当前输出点在输入帧轴上的位置，取整得到滤波中心。若还不是最终输出（`final == false`），并且中心右侧的 `half_` 帧尚未全部到达，滤波器就先停止；下一批输入到来后再继续。`final == true` 时不受这个前视条件限制，因为后面不会再有输入。

计算中心后，根据小数余数选择之前预计算的相位滤波器，并确定这次加权求和要读取的输入范围：

~~~c++
const auto& kernel = kernels_[(numerator % output_rate) / divisor_];
double value = 0;
const int64_t first = std::max<int64_t>(0, center - half_);
const int64_t last = std::min<int64_t>(input_frames_ - 1, center + half_);
~~~

余数对应输出点的小数偏移，除以 `divisor_` 后得到 `kernels_` 中的相位编号。`first` 和 `last` 将滤波窗口限制在本段已有的输入范围内；窗口超出音频开头或结尾的部分没有对应样本，按零处理。

对范围内的输入帧做乘加，得到一个输出采样值：

~~~c++
for (int64_t frame = first; frame <= last; ++frame)
    value += buffer_[static_cast<std::size_t>(frame - buffer_start_)]
           * kernel[frame - center + half_];
out.push_back(quantize(value));
++emitted_;
~~~

每个输入样本乘以对应 tap 的系数后累加到 `value`。`frame - buffer_start_` 把本段的输入帧编号换算成当前缓冲区下标；`frame - center + half_` 则把相对滤波中心的 tap 偏移换算成 kernel 下标。`quantize()` 将结果限制到 `[-1, 1]`，再转换成 `int16_t`。成功生成一个输出后，`emitted_` 加一。

输出后删除不会再参与后续滤波的旧输入样本：

~~~c++
const int64_t keep = std::max<int64_t>(
    0, emitted_ * rate_ / output_rate - half_);
const auto remove = static_cast<std::size_t>(
    std::min(input_frames_, keep) - buffer_start_);
buffer_.erase(buffer_.begin(), buffer_.begin() + remove);
buffer_start_ += remove;
return out;
~~~

`keep` 是下一输出位置左侧滤波窗口的起点，之前的输入帧不会再被使用。`remove` 算出这些旧帧在 `buffer_` 中占多少元素并将其删除；`buffer_start_` 同步前移，保持剩余缓冲区样本与输入帧编号的对应关系。函数最后返回本次新生成的 16 kHz 样本。

#### 4. `flush()` 排出段尾样本

`flush()` 表示当前音频段到此结束：

~~~c++
if (finished_) return {};
~~~

若实例已经结束，重复调用直接返回空向量，不会重复输出尾部样本。

~~~c++
finished_ = true;
~~~

首次调用先标记实例结束，之后若再调用 `push()`，开头的状态检查会抛出异常。

~~~c++
return rate_ == output_rate ? std::vector<int16_t>{} : emit(true);
~~~

输入率为 16 kHz 时此前没有重采样滤波和前视延迟，所以没有尾部样本可排。其他输入率会调用 `emit(true)`：它跳过等待未来帧的条件，计算当前输入对应的最后一批输出；输入区间外的滤波 tap 按零处理。

采集线程的 `flush` 还会把重采样器返回的尾部样本交给 packetizer，再让 packetizer 发出不满 320 个样本的末包：

~~~c++
if (stream.resampler)
    packetizer.push(stream.resampler->flush(), segment_estimated);
packetizer.finish();
~~~

这里的两步职责不同：`resampler->flush()` 排出尚未计算的 16 kHz 音频样本；`packetizer.finish()` 则把最后不足 320 个样本的部分封成尾包。检测到 `position.new_segment` 时，旧重采样器先这样收尾，再创建新实例，避免滤波器缓冲跨过时间段断点。辅助函数 `downmix16k()` 也先调用 `push()`、再调用 `flush()` 并拼接两次结果；`downmixMonoPcm16()` 只做声道混合和量化，不改变采样率。

### 3. `IndependentAudioSource::run(source)` 采集流程

线程从 `IAudioCaptureClient` 读取一批 WASAPI 样本，先转换为浮点 PCM，再由 `Mono16kResampler` 转成 16 kHz 单声道 S16 PCM。`AudioPacketClock` 根据设备帧位置和 QPC 时间维护时间线；时间戳无效时继续保留音频并标记为估算值。检测到新时间段时，线程先结束旧段，再重置重采样器和 packetizer。

#### 3.1 从 `start()` 到 `run(source)`：两路线程入口

第 1 节说明了 `IndependentAudioSource::start()` 的参数校验和队列设置；这里从它启动线程的位置开始，跟踪线程进入 `run(source)` 后如何打开流、采集并分包。线程入口如下：

~~~c++
for (int i = 0; i < 2; ++i)
    threads_[i] = std::thread([this, i] { run(i); });
~~~

`i == 0` 的线程采集 CS2，`i == 1` 的线程采集 Oopz。两个线程分别执行同一套 `run(source)` 流程，拥有各自的 `Stream`、WASAPI 连接和 packetizer：

#### 3.2 `run(source)` 初始化本线程采集器

函数先为工作线程初始化 COM，选择来源对应的进程名，再准备 QPC 时间换算、packetizer 和 `flush`：

~~~c++
Stream stream;
const auto name=source==0 ? cfg_.audio_cs2_process : cfg_.audio_oopz_process;
LARGE_INTEGER frequency,counter;
QueryPerformanceFrequency(&frequency);
QueryPerformanceCounter(&counter);
const double qpc_offset=clock::nowSec()-
    double(counter.QuadPart)/frequency.QuadPart;
media::AudioPacketizer packetizer(source,[&](media::AudioPacket packet) {
    outputs_[source]->push(std::move(packet));
});
bool segment_estimated=false;
auto flush=[&] {
    if (stream.resampler)
        packetizer.push(stream.resampler->flush(),segment_estimated);
    packetizer.finish();
~~~

`Stream stream` 是这个线程的局部对象：CS2 线程和 Oopz 线程各持有一份。

`qpc_offset` 把 WASAPI 给出的 QPC 秒数换到 `clock::nowSec()` 使用的单调时钟基准。

> [!NOTE]
>
> **QPC** 是 *Query Performance Counter* 的简称，可以把它想成 Windows 提供的高精度秒表(**向 Windows 查询高精度计时器的数值**)
>
> - `QueryPerformanceFrequency(&frequency)`：读取秒表每秒跳多少个计数。`frequency` 是“每秒计数数”。
> - `QueryPerformanceCounter(&counter)`：读取此刻的计数值。`counter` 是当前总计数。
> - `counter.QuadPart / frequency.QuadPart`：把总计数换算成秒，得到 QPC 秒表的当前读数。
> - `clock::nowSec()`：读取程序自己使用的单调时钟读数。
> - `qpc_offset`：两个秒表读数的差，用来把 QPC 时间换算成程序时钟的时间。它可以是负数，这是正常的。
>
> 可以把两个时钟想成起点不同的秒表：它们都在计时，但“零秒”不一样。`qpc_offset` 记录这个起点差。
>
> 后面读取音频时，代码会把 WASAPI 给的 QPC 时间戳先换成秒，再加上 `qpc_offset`，就能把音频时间放到程序的时钟线上。这不是为了知道“现在几点”，而是为了让音频包的时间戳彼此对得上。

packetizer 完成一个 `AudioPacket` 时，回调把它推入 `outputs_[source]`。

遇到进程切换、时间段断点、采集错误或线程退出时，`flush` 会排出重采样器的尾部样本并结束 packetizer 当前段。

#### 3.3 `run()` 每秒发现进程并决定是否重连

`discover_at` 初始为 0，所以第一次循环就执行发现；此后每秒检查一次：

~~~c++
        double discover_at=0;
        while (!stop_) {
            const double now=clock::nowSec();
            if (now>=discover_at) {
                discover_at=now+1;
                const auto pid=findProcess(name);
                if (!pid || !stream.client || stream.pid!=pid) {
                    flush();
                    stream.close();
                    stream.pid=pid;
                    stream.state="waiting";
                    if (pid) {
                        const auto opened=stream.open(pid,false);
                        if (FAILED(opened)) {
                            stream.close();
                            stream.state="failed";
                        }
                    }
                }
                if (status_)
                    status_(source,stream.status(name).dump());
            }
~~~

- `discover_at` 是**下次检查目标进程的时间点**，单位是秒。它不是音频时间戳。

##### `const auto pid = findProcess(name);`

- 作用： 同名进程里找到最上层的那个，并返回这个进程自己的 PID。比如 `launcher.exe → game.exe → game.exe`，它返回第一个 `game.exe` 的 PID，而不是 `launcher.exe` 的 PID。

> `CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS, 0)`
> 请 Windows 创建一份**当前进程列表的快照**。这里的 `TH32CS_SNAPPROCESS` 表示快照内容是进程信息。
>
> `PROCESSENTRY32W entry{}; entry.dwSize = sizeof(entry);`
> 准备一个结构体，Windows 会把每个进程的信息填进 `entry`。`W` 表示使用宽字符版本；`dwSize` 是 API 要求调
>
> `std::map<DWORD,DWORD> matches;`
> 准备一张表，保存匹配进程的 **PID → 父进程 PID**。
>
> `if (Process32FirstW(snap, &entry)) do { ... } while (Process32NextW(snap, &entry));`
> 从快照中的第一个进程开始，然后逐个读取后续进程，直到遍历结束。
>
> `Process32FirstW(snap, &entry)`：从快照 `snap` 中读取第一条进程信息，写入 `entry`。
>
> `Process32NextW(snap, &entry)`：继续读取下一条进程信息，覆盖 `entry`。
>
> > [!NOTE]
> >
> > `Process32FirstW(snap, &entry)`
> >
> > // 进程可执行名匹配："cs2" / "cs2.exe" 均可匹配 "C:\...\cs2.exe"（大小写不敏感；
> >
> > // 期望可写全路径自动取 basename）；期望为空 = 不匹配任何窗口。
> >
> > 因为选择了`回环模式`，所以他会读取该进程以及下面所有的子进程，所以需要寻找到同名的最上层

##### 处理pid不一致或通过寻找到的pid创建新流

如果进程不存在、WASAPI 客户端尚未打开，或 PID 与当前流不同，就先冲刷旧段并 `close()`，再记下发现的 PID、将状态设为 `waiting`。PID 非零时才调用 `open(pid,false)`。打开失败后再清理一次并设为 `failed`；目标进程没启动时则保持 `waiting`，下一个发现周期继续查找。每次发现周期结束都会上报一次状态。

`stream.open(pid, false)` 的打开过程见前面的 [Stream::open(pid, false) 实现说明](#stream-open)。

##### 回调采集流信息

```c++
                if (status_) status_(source,stream.status(name).dump());
```

这是一个**状态回调**，把当前采集流的信息传出去。

- `if (status_)`：先检查回调是否已设置。
- `stream.status(name).dump()`：读取流的状态信息，并转成 JSON 字符串。
- `status_(source, ...)`：调用回调，传入来源编号和状态字符串。

#### 3.4 读取 WASAPI 缓冲区并转换样本

有 `capture` 接口时，线程查询可读缓冲区并逐块取数据；单轮最多取 64 块，避免某一路长期占住自己的线程：

~~~c++
            if (stream.capture) {
                UINT32 packet=0;
                auto result=stream.capture->GetNextPacketSize(&packet);
                for (int batch=0;SUCCEEDED(result)&&packet&&batch<64;++batch) {
                    BYTE* data=nullptr;
                    UINT32 frames=0;
                    DWORD flags=0;
                    UINT64 device=0,qpc=0;
                    result=stream.capture->GetBuffer(&data,&frames,&flags,&device,&qpc);
                    if (FAILED(result)) break;
                    const bool valid=
                        !(flags&AUDCLNT_BUFFERFLAGS_TIMESTAMP_ERROR)&&qpc!=0;
                    const auto position=stream.clock.observe(
                        frames,device,qpc/1e7+qpc_offset,valid,
                        (flags&AUDCLNT_BUFFERFLAGS_DATA_DISCONTINUITY)!=0,
                        clock::nowSec());
                    std::vector<float> input(std::size_t(frames)*stream.channels,0);
                    if (!(flags&AUDCLNT_BUFFERFLAGS_SILENT)&&data) {
                        if (stream.floating)
                            std::copy_n(reinterpret_cast<float*>(data),input.size(),input.begin());
                        else
                            for (std::size_t j=0;j<input.size();++j)
                                input[j]=reinterpret_cast<int16_t*>(data)[j]/32768.0f;
                    }
                    stream.capture->ReleaseBuffer(frames);
~~~

- WASAPI 把 `IAudioCaptureClient` 接口写入 `Stream` 的成员 `capture`，也就是 `stream.capture`。

> [!NOTE]
>
> `for循环中` `batch` 是一个**循环计数器**，
>
> 每处理一个 WASAPI 音频包就加 1。它不是帧数，也不是包的大小；可以把它理解成“本轮已经处理了几个包”。`batch < 64` 的意思是：**这一轮最多处理 64 个包**。如果已经处理到 64 个，循环就停；即使此时还有下一个包，也只是留到下一轮再读。外层循环会重新调用 `GetNextPacketSize()`，然后继续处理。**这条限制不会主动丢掉第 65 个包。**

##### 查询下一个packet包，并循环解析

`auto result=stream.capture->GetNextPacketSize(&packet);`**查询**下一个 WASAPI 缓冲包有多大，不会在这行读取音频数据

`GetBuffer()` 每次取到一**批** `frames`，而不是一个音频帧。

> 这些变量是输出位置：WASAPI 会在 `GetBuffer()` 调用中写入数据指针、帧数、状态标记、设备帧位置和 QPC 时间。`frames` 是帧数；立体声的一帧包含左右声道各一个样本。QPC 时间单位是 100 纳秒。[微软对 `GetBuffer()` 参数的说明](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiocaptureclient-getbuffer)

##### 判断时间戳能否使用

```c++
const bool valid =
    !(flags & AUDCLNT_BUFFERFLAGS_TIMESTAMP_ERROR) && qpc != 0;
```

`flags` 中没有时间戳错误标记，并且 `qpc` 不为零，才认为时间戳有效。`&` 在这里是检查某个标记位；`!` 表示“没有”；`&&` 表示两个条件都满足。微软将 `TIMESTAMP_ERROR` 定义为设备位置记录时间不确定。[标记定义](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/ne-audioclient-_audclnt_bufferflags)

##### 计算这批音频的时间位置是否连续（observe)

```c++
const auto position = stream.clock.observe(
    frames, device, qpc / 1e7 + qpc_offset, valid,
    (flags & AUDCLNT_BUFFERFLAGS_DATA_DISCONTINUITY) != 0,
    clock::nowSec());
```

代码把设备位置、QPC 时间戳、时间戳错误标志和数据中断标志交给 `stream.clock.observe()`；`qpc/1e7` 将 WASAPI 的 100 ns 单位换成秒，再加偏移得到客户端单调时钟时间。`observe()` 返回这批音频的起始位置、是否开始新时间段以及时间戳是否为估算值。

`input` 的大小是 `frames × channels`。静音缓冲区保持零；浮点样本直接复制；16 位 PCM 则除以 32768 转成 `float`。拷贝完成后立即 `ReleaseBuffer(frames)`，之后的重采样和分包使用本地 `input`，不再占用 WASAPI 缓冲区。

##### 转换成float样本

```
std::vector<float> input(std::size_t(frames) * stream.channels, 0);
```

每个音频帧通常包含多个声道样本，所以样本总数是 `帧数 × 声道数`。向量初始化为 `0`，因此静音时可以直接保留这些零值。

```
if (!(flags & AUDCLNT_BUFFERFLAGS_SILENT) && data) {
```

只有这段音频**不是静音**，并且数据指针有效时，才读取数据。静音或 `data` 为空时，`input` 保持全零。

```
if (stream.floating)
    std::copy_n(reinterpret_cast<float*>(data), input.size(), input.begin());
```

如果音频格式是浮点数，就把输入缓冲区中的 `float` 样本直接复制到 `input`。

```
else
for (std::size_t j=0;j<input.size();++j) input[j]=reinterpret_cast<int16_t*>(data)[j]/32768.0f;
```

否则，把输入视作 16 位有符号整数，并除以 `32768.0` 转成大约 `[-1, 1)` 范围的浮点样本。例如 `-32768` 转成 `-1.0`，`32767` 转成约 `0.99997`。

要注意：这段代码假设非浮点格式是 **16 位整数 PCM**；如果实际输入是 24 位或 32 位整数 PCM，就需要不同的转换方式。

##### 输入重采样器和打包器

```
stream.capture->ReleaseBuffer(frames);
```

通知 WASAPI：这 `frames` 帧已经处理完，释放刚才取得的采集缓冲区。前面的代码已把样本复制进 `input`，因此后续处理用的是自己的数据。

```
if (position.new_segment) {
    flush();
    if (stream.origin) ++stream.discontinuities;
```

如果 `AudioPacketClock` 判断当前包开启了新时间段：

- `flush()`：把旧段尚未输出的音频处理完，避免旧段和新段的数据混在一起。
- 如果已经有过起点，就把 `discontinuities` 加一；第一次建立起点不算一次中断。

```
stream.origin = position.start;
segment_estimated = position.estimated;
stream.resampler =
    std::make_unique<Mono16kResampler>(stream.rate, stream.channels);
```

保存新段的起始时间，并记录这个起始时间是否为估算值。

接着重建重采样器，使它从新段开始处理；这样滤波器的内部状态不会跨越两个不连续的音频段。

```
const auto index = static_cast<uint64_t>(
    (std::max)(0LL, std::llround((position.start - epoch_) * 16000)));
```

把新段起始时间换算成 **16 kHz 时间轴上的采样点位置**：

- `position.start - epoch_`：起点相对统一时间原点的秒数。
- 乘以 `16000`：换算成 16 kHz 采样点。
- 四舍五入后钳制到不小于 0。

```
packetizer.begin(
    index,
    static_cast<uint64_t>(std::llround(position.start * 1e6)),
    position.estimated);
```

通知打包器新段从哪里开始：

- `index`：在 16 kHz 输出序列中的采样点位置。
- `position.start * 1e6`：把起始时间从秒换算成微秒。
- `position.estimated`：标记时间起点是否是估算值。

然后处理当前包：

```
packetizer.push(
    stream.resampler->push(input),
    position.estimated);
```

先把当前输入样本重采样，再把结果交给打包器；同时传递当前包时间是否为估算值。

最后：

```
++stream.packets;
result = stream.capture->GetNextPacketSize(&packet);
```

增加已处理包数，并查询 WASAPI 队列里下一个待处理包的大小，供后续采集循环使用。

#### 3.5 处理时间段并输出音频包

同一批音频可能开启新的时间段。处理方式紧接在 `ReleaseBuffer()` 后：

~~~c++
                    if (position.new_segment) {
                        flush();
                        if (stream.origin) ++stream.discontinuities;
                        stream.origin=position.start;
                        segment_estimated=position.estimated;
                        stream.resampler=
                            std::make_unique<Mono16kResampler>(stream.rate,stream.channels);
                        const auto index=static_cast<uint64_t>((std::max)(
                            0LL,std::llround((position.start-epoch_)*16000)));
                        packetizer.begin(index,
                            static_cast<uint64_t>(std::llround(position.start*1e6)),
                            position.estimated);
                    }
                    packetizer.push(stream.resampler->push(input),position.estimated);
                    ++stream.packets;
                    result=stream.capture->GetNextPacketSize(&packet);
                }
~~~

新段开始时先 `flush()` 旧重采样器和 packetizer；已有 `origin` 才表示从先前时间段切换过来，因此此时增加 `discontinuities`。之后更新段起点，创建新的重采样器，

并调用 `packetizer.begin()`：`index` 是相对于两路共用 `epoch_` 的 16 kHz 样本编号，第二个参数是段起点的微秒时间戳，第三个参数标记时间戳是否估算。当前输入经重采样后送给 packetizer；每处理一个 WASAPI 缓冲块，`stream.packets` 加一。packetizer 收满 320 个 16 kHz 样本就输出 20 ms 的 `AudioPacket`。

#### 3.6 采集错误、重试与线程退出

~~~c++
                if (FAILED(result)) {
                    flush();
                    stream.close();
                    stream.state="failed";
                    if (status_)
                        status_(source,stream.status(name).dump());
                }
            }
            std::this_thread::sleep_for(std::chrono::milliseconds(2));
        }
        flush();
        stream.close();
        stream.state="stopped";
        if (status_)
            status_(source,stream.status(name).dump());
    } catch (const std::exception& e) {
        spdlog::error("independent audio {}: {}",source,e.what());
    }
    CoUninitialize();
}
~~~

WASAPI 查询失败时，代码刷新尾部音频、关闭当前流并上报 `failed`。工作线程继续运行，下一次进程发现周期会尝试重新打开目标进程。收到 `stop_` 后，循环结束，代码刷新尾部样本、关闭流并上报 `stopped`。异常会写入日志；线程最后调用 `CoUninitialize()`。

整条链路是：`start()` 创建两路工作线程；各线程的 `run(source)` 管理独立 `Stream`，查找目标进程并读取 WASAPI 缓冲区；`Mono16kResampler` 与 `AudioPacketizer` 将样本变成带时间信息的 `AudioPacket`；packetizer 回调把包放入 `outputs_[source]`，再由后续主循环交给 Publisher。
### 4. 两条队列分别交给 Publisher

CS2 和 Oopz 的 <code>AudioPacket</code> 分别进入 <code>BoundedQueue&lt;AudioPacket&gt;</code>，每路容量由 <code>media.audio.max_pending_packets_per_source</code> 控制，当前配置为 10。主循环每轮分别尝试从两条队列各取一个包，不需要等两路同时有数据；取出的包调用 <code>publisher-&gt;push()</code>。这样某一路较忙时不会独占分发循环。

<code>WebRtcPublisher::push(AudioPacket)</code> 按 <code>packet.source</code> 选择 CS2 或 Oopz 音频轨。它为每包创建一个 20 毫秒、640 字节的 PCM <code>GstBuffer</code>，以采集起始时间和 <code>sample_index</code> 计算 PTS，并推入对应的 <code>appsrc</code>。如果是较短的末尾包，buffer 先填静音，再把已有样本写入前部；<code>received_samples</code> 保留原始有效样本数。发生时间线断点时，buffer 会带 <code>DISCONT</code> 标记。

两个 <code>appsrc</code> 都声明输入为交错排列的 S16LE、16 kHz、单声道 PCM；之后各自经过 <code>opusenc</code> 和 <code>rtpopuspay</code>，作为两条独立音频轨接入同一个 <code>webrtcbin</code>。所以这里的 C++ 有界队列用于采集线程与主循环之间交接；GStreamer 音频链从 <code>appsrc</code> 接手后编码为 Opus/RTP，再送入 <code>webrtcbin</code> 上传。WebRTC 媒体轨和上传过程见 [WebRTC 流程](WebRTC.md)。
