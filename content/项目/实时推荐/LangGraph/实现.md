## 2. Runtime 如何编译并调度图

### 服务启动时

`Runtime.start()` 执行以下工作：

1. 启动 `Repository`，打开业务 SQLite 并执行迁移。
2. 创建 `checkpoints` 文件的父目录，以 `AsyncSqliteSaver.from_conn_string()` 打开异步 SQLite checkpointer。
3. 构造 `RoundReviewWorkflow(repo, review_model, saver, publish_mode=...)`。此时 `StateGraph` 被编译并绑定 checkpointer。
4. 将上次中断的 `running`、`deferred`、`waiting_model` 复盘 job 恢复为 `pending`，再启动周期 worker。

在线判断与复盘各有模型网关。配置 `independent_endpoint: true` 时，两者必须是不同的 gateway 实例，并使用独立锁；复盘进行期间 Runtime 可继续读取新观测和执行本地在线判断。

### 回合任务如何产生

- 回合边界由 `Runtime._commit_projection()` 写进 `rounds`。确认关闭时，同一业务事务创建 revision 1 的 `review_jobs`，并将 `ready_at` 设为约一秒后。
- 如果同一旧回合的观测晚到，未开跑的任务会更新 cutoff；若之前 revision 已执行，则追加 revision，避免重开当前实时状态。
- `POST /rounds/{round_uid}/review` 只允许已结束回合，也会在业务库中分配新 revision。

`Runtime._review()` 每轮最多启动一个复盘任务。没有可用 review 模型时 job 进入 `waiting_model`；共享在线模型时，在线请求未完成或采集仍活动会使复盘等待。独立 endpoint 时则按自己的 review lock 运行。到期任务被选中后，Runtime 取该回合的最大 `commit_seq`，在图外调用 `build_context()`，把 job 改为 `running`，再创建 `_run_review()` task。

单次模型请求在 `config/agent.yaml` 中有 `review_deadline_ms: 60000`；Runtime 对完整图执行设 `absolute_deadline_ms: 90000`。超时或未被图节点捕获的异常由 `_run_review()` 记录为 `review_jobs.status='failed'`。模型未配置进入 `waiting_model`，不会开始图或生成虚构模型结果。

## 3. 复盘输入包在图外构建

`build_context(..., review=True)` 不是 LangGraph node。它按 match、round 和 watermark 读取同一回合的观测，压缩各来源 payload，并装入最近最多 24 条该轮判断、回合结果、此前回合摘要和当时可用的对手档案。`input_manifest` 记录 match、round、状态版本、观测水位、截止时间和 event IDs。

复盘读取所有符合该 `round_uid` 且 `commit_seq <= watermark` 的观测；在线判断走的是另一条有时效窗口和来源配额限制的 context 分支。当前复盘的 prior memory 会排除本回合，防止同轮摘要自我引用。进入图后的 `bundle` 是本次运行的固定输入。

## 4. Graph State 与节点更新

`ReviewState` 是 `TypedDict(total=False)`，可选状态键为：

| 键 | 用途 |
|---|---|
| `bundle` | 图外冻结的复盘输入证据包 |
| `round_uid`、`revision` | 业务复盘任务身份，也是幂等提交键的一部分 |
| `candidate` | Review schema 校验前后的候选输出 |
| `error` | 模型错误或 schema/evidence 校验错误；下一次模型调用可读取 |
| `attempt` | 已尝试的模型调用数；最多为 2 |
| `metadata` | 模型名、用量、提示词版本等模型网关元数据 |
| `status` | `model_validated` 或 `degraded_observations_only` |
| `attempt_outputs` | 各次候选及元数据，或调用错误，供 shadow 草稿追溯 |

当前 StateGraph 没定义自定义 reducer；节点返回部分字段更新，普通状态键按默认规则被新值覆盖。这个图没有 interrupt/HITL、工具调用、子图或并行节点。

## 5. 节点、边与错误路径

### 图的实际连接

~~~python
graph.add_node("analyze", self.analyze)
graph.add_node("validate", self.validate)
graph.add_node("fallback", self.fallback)
graph.add_node("commit", self.commit)
graph.add_edge(START, "analyze")
graph.add_edge("analyze", "validate")
graph.add_conditional_edges(
    "validate",
    lambda s: "commit" if not s.get("error")
    else "analyze" if s["attempt"] < 2
    else "fallback",
)
graph.add_edge("fallback", "commit")
graph.add_edge("commit", END)
~~~

### `analyze`

调用 `await model.infer("review", state["bundle"], error=state.get("error"))`。成功时把候选、元数据和累计尝试记录写回 State，并增加 `attempt`。异常被捕获为带类型的 `error`，当前尝试也计数；条件边仍允许再试一次。第二次失败后进入降级分支。

### `validate`

如 `analyze` 已记录调用错误，节点不再尝试解析候选。否则先用 Pydantic `Review.model_validate()` 检查字段和长度，再调用 `validate_evidence()`：检查复盘和假设引用的观测 ID、复核项引用的 judgment ID/证据 ID，并拦截已知胜负冲突和把当前敌情写进下一回合记忆的特定模式。通过后将 `status` 设为 `model_validated`。这些边界校验仍不能证明所有战术结论在语义上真实。

### 条件回边与 `fallback`

验证无错误直接走 `commit`。失败且 `attempt < 2` 时回到 `analyze`，把错误提示给第二次模型调用；达到两次后进入 `fallback`。降级候选明确写明“模型复盘不可用”，引用输入清单中的原始 event IDs，保留未知原因，不编造战术假设。

一次修复不是额外节点，也不是无限自动重试。Runtime 还在图外设置绝对 deadline；遇到非预期异常或业务提交错误时，job 标记 `failed`，而非走 `fallback`。

## 6. `commit` 的两种模式

`commit` 用 `repo.call(write)` 在单写者线程中完成业务库写入；Repository 会对回调执行事务，失败则 rollback。

### 当前 `shadow`

`review.publish_mode: shadow` 时：

1. 把候选和所有 `attempt_outputs` 存到 `review_drafts`，主键为 `(round_uid, revision)`。
2. 将 job 标为 `shadow`，保留最终错误（如有）。
3. 立即返回，不写 `round_summaries`、`evidence_links`、`profile_contributions`、`opponent_profile_versions` 或 `judgment_events`。

这样仍能运行复盘模型、观察格式错误并保留草稿，但不会污染线上发布记忆。

### `validated`

只有配置切换为 `validated` 才执行发布事务。若同一个 `(round_uid, revision)` 已有摘要，提交立即返回，避免重复累计。否则写入复盘摘要和证据关联；当前实现中的档案贡献仅记录 ASR、YOLO、OCR 的来源覆盖情况，不是对手战术行为统计；随后生成新档案版本、写入 judgment review events，并将 job 标为 `completed`。

因此“下一回合读取上一回合已发布摘要/档案”通过业务 SQLite 和 `context.memory()` 实现，不是 checkpoint 跨 thread 提供记忆。当前 `shadow` 下新草稿不会被当作已发布记忆。

## 7. Checkpoint 与崩溃恢复

`RoundReviewWorkflow.run()` 用 `thread_id = f"{round_uid}-r{revision}"` 查 checkpoint：

- 没有历史 State：以 `{round_uid, revision, bundle, attempt: 0}` 启动 `ainvoke()`。
- 存在未完成节点：`snapshot.next` 非空时，用 `ainvoke(None, config)` 从 checkpoint 继续。
- 图已经结束：再次调用 `commit(snapshot.values)`，覆盖“业务事务提交后、LangGraph 完成 checkpoint 前”进程崩溃的窗口。

当前代码将业务库提交设计为幂等：validated 模式先检查摘要唯一键，shadow 草稿使用 `INSERT OR IGNORE`。checkpoint 文件保存图状态；业务库保存比赛事实和可发布结果。两库没有跨库分布式事务，所以恢复靠稳定任务键与幂等写入，而不是宣称 exactly-once。

LangGraph 的 `thread_id` 和 checkpointer 机制见[官方持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)；节点与条件边的通用语义见[Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)。项目固定依赖版本可查 `agent/requirements.lock.txt`（LangGraph 1.2.17、SQLite checkpoint 插件 3.1.2）。

## 总结

- `Runtime` 创建 review job、冻结 watermark、构建 bundle；`RoundReviewWorkflow` 只处理图内复盘。
- 图在格式、证据和少量边界检查失败时回环一次，再降级；异常提交和超时由 Runtime 标成 failed。
- LangGraph checkpoint 以 round/revision 分 thread；SQLite 业务库保存比赛记忆，提交使用稳定键保证可重试。
- 当前配置为独立 review endpoint + `shadow`，所以模型结果不发布到下一回合记忆。
