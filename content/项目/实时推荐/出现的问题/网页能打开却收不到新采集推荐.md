# 网页能打开却收不到新采集推荐

## 涉及文件

- `panel/connection.js`：获取实际 WS 端口、生成连接 URL。
- `panel/panel.js`：副屏连接初始化。
- `server/apps/server_main.cpp`：运行配置接口 GET /api/runtime。
- `config/server.webrtc.yaml`：候选实例端口。
- `tools/test_panel_connection.mjs`：URL 生成和错误配置测试。

## 问题

浏览器能打开 8003 页面，客户端也向 9003 上传媒体，但页面收不到新观测。原因是页面的 WebSocket 端口写死为 9000，连到了另一个服务实例。

当时原实例使用 HTTP8000/WS9000，WebRTC 候选实例使用 HTTP8003/WS9003。两个实例都可以正常响应，所以页面加载成功、WS 握手成功，都没有直接暴露连错实例的问题。

## 修改前

固定端口的逻辑可简化为：

```javascript
const socket = new WebSocket(`ws://${location.hostname}:9000/ws/panel`);
```

访问 8003 也会连接 9000。只把 9000 换成 9003 又会让其他配置出错，继续按 HTTP 端口加固定差值推算也依赖一个没有保证的部署约定。

## 修改后

### 服务端返回自己的实际配置

`server_main.cpp` 注册 `/api/runtime`，从已加载的 cfg 返回 WS 监听端口。以下省略雷达等其他运行字段：

```cpp
drogon::app().registerHandler("/api/runtime",
    [&cfg](const drogon::HttpRequestPtr&,
           std::function<void(const drogon::HttpResponsePtr&)>&& done) {
        auto response = drogon::HttpResponse::newHttpResponse();
        response->setContentTypeCode(drogon::CT_APPLICATION_JSON);
        response->addHeader("Cache-Control", "no-store");
        response->setBody(json({
            {"websocket_port", cfg.listen_port},
            {"capture_transport", cfg.media_enabled ? "webrtc" : "disabled"}
        }).dump());
        done(response);
    }, {drogon::Get});
```

端口来自当前进程配置，不是前端重新读一份默认 YAML。这样页面从哪个 HTTP 实例读取运行配置，就拿到哪个实例发布的 WS 端口。

### 前端按运行配置构造 URL

当前 `panelWebSocketUrl()` 的默认路径为：

```javascript
const response = await request("/api/runtime", {cache: "no-store"});
if (!response.ok) throw new Error("无法读取当前服务的连接配置");
const runtime = await response.json();
if (!Number.isInteger(runtime.websocket_port) ||
    runtime.websocket_port < 1 || runtime.websocket_port > 65535) {
  throw new Error("服务返回的 WebSocket 端口无效");
}

const url = new URL(location.href);
url.protocol = location.protocol === "https:" ? "wss:" : "ws:";
url.port = String(runtime.websocket_port);
url.pathname = "/ws/panel";
url.search = "";
url.hash = "";
return url.href;
```

URL API 处理主机、端口与 IPv6 格式，不手工拼接字符串。页面上的查询参数和 hash 不应该原样带到 WS 接口，因此清空。

反向代理可以显式提供完整覆盖地址：

```javascript
if (override) {
  const url = new URL(override);
  if (!["ws:", "wss:"].includes(url.protocol)) {
    throw new Error("WebSocket 地址必须使用 ws 或 wss");
  }
  return url.href;
}
```

## 为什么这样改

修改后，关联地址来自实际服务实例，不再依赖写死的端口或端口差值。`no-store` 避免旧运行配置被缓存。配置读取失败时明确报错和重试，而不是悄悄猜另一个端口。

HTTPS 页面生成 wss URL，可以保持协议选择一致；但真正的 TLS 终止和代理转发仍由部署提供。外部代理端口若与内部监听端口不同，就使用显式 WS 地址，不能期待内部端口自动适配所有网络拓扑。

## 验证

2026-10-26，8003 页面接到候选实例的真实 OCR 观测，“短梯”查询自动播放 1、2、9、19 号视频。四个 video 均为 paused=false、readyState=4、error=null，1920×1080，播放时间继续推进。

专项测试覆盖实际端口、HTTPS、IPv6、显式代理和非法端口；停止采集后清空，新会话恢复推荐。

## 总结

我沿着“页面从哪里加载、观测由哪个实例产生、WS 订阅连到哪里”查出了实例错配，再让服务端发布运行配置。多实例联调中，接口各自可用不等于它们连在同一条业务链上，必须核对实际地址和会话。
