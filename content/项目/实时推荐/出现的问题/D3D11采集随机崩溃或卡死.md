# D3D11 采集随机崩溃或卡死

## 涉及文件

| 文件 | 作用 |
| --- | --- |
| `client/src/capture_video.cpp` | 创建 D3D11 设备、设置多线程保护、执行纹理复制与 Map |
| `client/src/capture_video.hpp` | 视频采集对象的生命周期 |

## 背景与现象（S）

WGC 采集通过 `CreateFreeThreaded` 帧池接收图像，回调由 WinRT 线程池触发。开发初期出现过随机崩溃和线程卡死，表现并不固定，有时像堆损坏，很难靠某一帧图像稳定复现。

## 要达到的目标（T）

使采集回调中使用的 D3D11 设备上下文在多线程环境下受到正确保护，保证后续纹理复制、CPU 读取和编码能够稳定运行。

## 排查与根因（A）

回调来自线程池，不能因为业务上“只有一条采集链”就认为 D3D11 的访问天然串行。项目使用的 immediate context 没有开启对应的多线程保护，跨线程访问存在风险。

排查重点从“哪一张图像触发崩溃”转为“设备上下文会被哪些线程访问”。这是共享底层资源的访问约束问题，单纯给 JPEG 编码或上传队列加锁不能解决。

## 如何解决

创建 D3D11 设备后，从 context 获取 `ID3D11Multithread`，在开始采集前启用保护。当前关键代码为：

```cpp
auto multithread = context.as<ID3D11Multithread>();
multithread->SetMultithreadProtected(TRUE);
```

该接口所需头文件是 `d3d11_4.h`。初始化完成后再建立并启动采集，避免回调先运行、保护设置后补上的窗口。

同一初始化区域还使用 `CreateDirect3D11DeviceFromDXGIDevice` 将 DXGI 设备包装成 WinRT 需要的设备对象；这一转换与多线程保护分别承担接口适配和并发访问保护职责。

## 验证与结果（R）

2026-10-04 开发日志将此问题记录为已解决。修复后的同轮 INT-1 验证完成了 15 秒真机采集、上传和服务器归档。

原记录没有给出独立的长时间压力测试数据，因此可以确认该次烟测和修复记录，不能据此填写“连续运行若干小时零崩溃”。

## 可以复用的经验

遇到死法不固定的图形采集崩溃，先梳理线程与共享资源：谁创建 device/context，谁调用 CopyResource/Map，回调运行在哪个线程，以及资源何时销毁。事件回调只规定触发方式，并不自动满足底层 API 的线程约束。
