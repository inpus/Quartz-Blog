# WGC 采集运行 15 秒却只得到 1 帧

## 涉及文件

- `client/src/capture_video.cpp`：FrameArrived 回调、取帧、节流和编码。
- `client/src/capture_video.hpp`：采集对象和状态。

## 问题

我把采集频率设为 1fps，运行 15 秒却只收到 1 帧。WebSocket 没断开，采集进程也没有报错，但后面不再有图像上传。

## 定位

沿着 FrameArrived → 取帧 → 编码 → 入队这条路径检查，问题出在节流判断的位置：未到下一次编码时间就直接返回，跳过了 `TryGetNextFrame()`。

WGC 使用有限容量的帧池。当时帧池深度为 2，不取出帧，缓冲很快就会被占满。这次故障中，池满之后不再有后续 FrameArrived 回调，节流代码也就没有机会再次执行。

## 修改前

按故障逻辑简化，原来的顺序是先判断时间，再取帧：

```cpp
frame_pool.FrameArrived([ctx, interval](auto const& sender, auto&&) {
    const auto now = std::chrono::steady_clock::now();
    if (now - ctx->last < interval) {
        return;  // 没到编码时间，连帧池里的帧也不取。
    }
    ctx->last = now;

    if (auto frame = sender.TryGetNextFrame()) {
        // 读纹理、JPEG 编码、入上传队列。
    }
});
```

假设第一帧在 0 秒处理完成，后面两帧在 0.02 秒和 0.04 秒到达，都因为不足 1 秒直接返回。它们还占着帧池，不能指望程序等到 1 秒后自动恢复，因为执行节流判断本身就依赖新的回调。

## 修改后

每次收到回调都取帧，只对后面的图像处理做节流。当前回调的关键部分如下：

```cpp
const auto interval = std::chrono::milliseconds(1000 / fps_);
ctx->last = std::chrono::steady_clock::now() - interval;

frame_pool.FrameArrived(
    [this, ctx, frame_pool, interval](auto const& sender, auto&&) {
        if (stop_) return;

        const auto now = std::chrono::steady_clock::now();
        const bool due = now - ctx->last >= interval;
        if (due) ctx->last = now;

        if (auto frame = sender.TryGetNextFrame()) {
            if (!due) return;

            const auto content = frame.ContentSize();
            auto access = frame.Surface()
                .as<d3d11interop::IDirect3DDxgiInterfaceAccess>();
            // 继续获取纹理，CopyResource、Map，编码或输出 raw frame。
        }
    });
```

`ctx->last` 初始化为“现在减一个间隔”，让首帧可以立即处理。`due` 只决定要不要读纹理和编码，不再决定是否消费帧池。没有到点时，局部 `frame` 随 return 退出作用域，其持有的帧引用得到释放。

## 为什么这样改

修改前把两种频率绑在一起：底层产生帧的频率和我需要编码上传的频率。WGC 可能持续产生帧，我只需要其中一部分。

改完之后，无用帧也会被及时取出和释放，帧池能继续周转；昂贵的 GPU→CPU 读取和编码仍然保持 1fps，不会因为持续取帧就全部执行。

```text
修改前：未到编码时间 → 不取帧 → 帧池占满 → 采集停住
修改后：每次取帧 → 未到时间直接释放 → 到时间才编码
```

这里的原则也适用于摄像头和解码队列：如果生产端依赖缓冲回收才能继续，降低处理频率时也要考虑怎么释放不处理的数据。

## 验证

2026-10-04 的 15 秒真机测试中，服务器收到 15 张 JPEG，`frames.tsv` 有 15 行，同时保存了 15 秒 WAV 并生成回放视频。Windows 16/16、Linux 48/48 测试通过。这是旧 JPEG/WS 链路的验证记录。

## 总结

我遇到的是采集侧帧池没有被消费，不是上传丢帧。修复时没有提高帧率，而是把“取帧”和“编码”分开：回调来了就取帧释放，编码才按时间节流。排查这类问题时，要分别看回调、取帧、编码和发送计数，不能只看最后收到几张图。
