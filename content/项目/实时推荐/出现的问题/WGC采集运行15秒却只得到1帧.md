# WGC 采集运行 15 秒却只得到 1 帧

## 涉及文件

| 文件 | 作用 |
| --- | --- |
| `client/src/capture_video.cpp` | WGC 帧池、FrameArrived 回调、取帧与节流 |
| `client/src/capture_video.hpp` | 采集对象与状态声明 |

## 背景与现象（S）

M0 阶段使用 Windows Graphics Capture 采集主显示器，再将图像编码成 JPEG 上传。目标采集频率是 1fps，15 秒烟测却只得到 1 帧。连接并没有断，进程也没有立即报错，看起来像采集事件停止触发。

## 要达到的目标（T）

持续接收 WGC 帧，同时只按配置频率编码和上传。降低业务处理频率时，底层帧池仍需要正常取出并释放帧。

## 排查与根因（A）

WGC 使用深度为 2 的帧池，应用通过 `FrameArrived` 回调调用 `TryGetNextFrame()` 取得帧。原来的节流思路是“未到 1 秒直接 return”，连取帧也一起跳过。

错误流程可以简化为：

```text
第一帧到达 → 取帧、编码
后续帧到达 → 未到节流时间 → 不取帧
帧池逐渐填满 → 后续 FrameArrived 不再继续到来
没有新回调 → 没有机会再次检查节流时间
```

问题发生在采集队列的消费环节。只观察编码后的帧数，很容易误以为是编码器或网络上传出了问题。

## 如何解决

把“消费帧池”和“处理业务帧”分开。每次回调都尝试取帧；如果没有达到节流间隔，取出后直接释放，跳过纹理读取、编码和入队。

当前实现的关键顺序是：

```cpp
const bool due = now - ctx->last >= interval;
if (due) ctx->last = now;
if (auto frame = sender.TryGetNextFrame()) {
    if (!due) return;
    // 继续读取纹理、编码或输出 raw frame。
}
```

这里的 `frame` 是局部对象，提前返回时也会释放。帧池可以持续周转，而昂贵处理仍保持目标频率。

## 验证与结果（R）

2026-10-04 的 INT-1 真机烟测中，Windows 客户端运行 15 秒，服务器归档得到 15 张 JPEG、`frames.tsv` 15 行以及 15 秒 WAV，并在收尾时生成回放视频。当日 Windows 16/16、Linux 48/48 测试通过。

这是当时 M0 的显示器采集与旧传输链验证；后续客户端已有窗口采集和 WebRTC 路径。

## 可以复用的经验

对事件驱动的有限缓冲区，业务节流应该控制处理频率，不能随意停止消费。排查“第一帧正常，后面不再来”时，应同时检查回调次数、取帧次数和编码次数，确定停在哪一层。
