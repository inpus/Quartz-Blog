# 车道线程退出时发生析构竞争

## 涉及文件

- `server/libs/core/lane.cpp`：requestStop、工作线程循环和基类析构。
- `server/libs/core/lane.hpp`：FastLane、VoiceLane 的回调成员和析构。
- `tests/tsan.supp`：依赖库 TSan 抑制项。

## 问题

TSan 检测到对象析构与工作线程虚调用之间的 vptr 数据竞争。我的停止函数只调用了 `request_stop()`，但对象继续析构时，工作线程仍可能在 `onEnvelope()` 或派生类回调里。

## 修改前

这是修复提交 `51cb20c` 之前的停止逻辑：

```cpp
Lane::~Lane() { requestStop(); }

void Lane::requestStop() {
    if (thread_.joinable()) thread_.request_stop();
}
```

工作线程则持续使用 this 并调用虚函数：

```cpp
while (!st.stop_requested()) {
    auto env = bus_.consume(prio_, timeout_ms);
    if (env) {
        onEnvelope(*env);
        continue;
    }
    if (tick_interval_.count() > 0) onTick();
}
```

停止标记只有在线程下一次检查时才生效。如果它已经进入 onEnvelope，request_stop 不会强行中断正在执行的函数。

我也不能只依赖 `std::jthread` 析构自动 join。派生类成员先销毁，之后才轮到基类成员；FastLane 的 `on_cvevent_` 可能已经销毁，而线程仍通过虚函数访问它。进入基类析构后继续与虚调用并发，还会涉及 vptr 的变化。

## 修改后

第一步，把“发出停止请求”和“等线程退出”放到同一个入口：

```cpp
void Lane::requestStop() {
    if (thread_.joinable()) {
        thread_.request_stop();
        thread_.join();
    }
}

Lane::~Lane() { requestStop(); }
```

第二步，派生类在自己的成员被销毁之前，主动调用这个入口：

```cpp
class FastLane : public Lane {
public:
    ~FastLane() override { requestStop(); }

protected:
    void onEnvelope(const Envelope& e) override;

private:
    std::function<void(const Envelope&)> on_cvevent_;
};
```

当前 VoiceLane 也在析构函数体中提前 requestStop，保护它自己的音频和 idle 回调成员。

## 为什么这样改

C++ 析构顺序是执行派生类析构函数体，再销毁派生类成员，之后执行基类析构。把 join 放进派生类析构函数体，就能在回调成员仍有效时等线程退出。

```text
修改前：request_stop → 派生成员销毁 → 工作线程可能仍访问回调
修改后：request_stop → join 完成 → 派生成员销毁 → 基类析构
```

join 返回后，工作线程已结束，后续析构不再与它访问对象的操作重叠。基类析构再次进入 requestStop 时，线程已经不可 join，因此不会重复等待。

这里的 requestStop 由外部管理线程调用，不能让工作线程自己 join 自己。也不能持有工作线程退出所需的锁再 join，否则可能形成死锁。

队列 consume 有超时，空闲线程大约在一个消费等待周期内检查停止。约 200ms 是空闲等待的量级；如果业务回调本身运行更久，join 仍要等它返回。

## 验证

2026-10-04，修复后 TSan 54/54、linux-debug 54/54 通过。TSan 对未插桩依赖的已知报告按清单处理，项目自身代码的竞争没有被一起屏蔽。

## 总结

我补的不只是一个 join，而是把 join 放到了派生类资源销毁之前。jthread 能自动管理线程，不代表它知道线程依赖哪些成员、这些成员什么时候失效。带后台线程的对象需要明确收尾顺序：先通知，等执行结束，再销毁线程会用到的资源。
