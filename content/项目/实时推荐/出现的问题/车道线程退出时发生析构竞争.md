# 车道线程退出时发生析构竞争

## 涉及文件

| 文件 | 作用 |
| --- | --- |
| `server/libs/core/lane.cpp` | Lane::requestStop、工作线程循环与基类析构 |
| `server/libs/core/lane.hpp` | FastLane/VoiceLane 的回调成员和派生类析构 |
| `tests/tsan.supp` | 已记录的依赖库 TSan 抑制项 |

## 背景与现象（S）

2026-10-04 首次真正跑通 TSan 后，检测到 Lane 的析构与工作线程虚调用之间存在 vptr 数据竞争。原来的停止流程只发送停止请求，线程不一定已经离开 `onEnvelope()`，对象却开始析构。

## 要达到的目标（T）

在回调成员、派生对象和虚函数调用依赖的状态被销毁前，确认工作线程已经退出。

## 排查与根因（A）

`request_stop()` 只设置停止状态。线程通常要等消费操作返回，再检查 stop_token；这一间隔中仍可能执行回调。

仅依赖 `std::jthread` 成员最终析构时自动 join 也不够。C++ 对象先执行派生类析构并销毁派生成员，再进入基类析构。FastLane 的 `on_cvevent_` 可能比基类中线程的收尾更早被销毁。

```text
主线程：开始析构派生对象 → 回调成员销毁 → 基类收尾
工作线程：                 仍在调用 onEnvelope()/回调
```

这是“对象还在析构，线程还在用对象”的竞争窗口。

## 如何解决

将停止请求和等待退出放进同一收尾入口：

```cpp
void Lane::requestStop() {
    if (thread_.joinable()) {
        thread_.request_stop();
        thread_.join();
    }
}
```

同时在 FastLane 的析构函数体中调用 `requestStop()`，在 `on_cvevent_` 成员销毁前完成 join。当前 VoiceLane 也采用相同的提前停止方式，基类析构再调用该入口作为收尾保障。

调用顺序变为：派生对象仍完整时发停止请求 → 等待工作线程退出 → 销毁回调成员 → 析构基类。该入口用于外部控制线程收尾，不应由被 join 的工作线程自身调用。

## 验证与结果（R）

2026-10-04 的 TSan 构建与 54/54 测试通过，项目自身代码零报告；同轮 linux-debug 54/54 通过。文档估计空闲消费等待带来的响应上限约 200ms；若线程正执行耗时业务，实际 join 仍需等该业务返回。

当轮另外解决了 TSan 的 ASLR 启动问题和编译器环境问题，并将依赖库抑制项与项目代码报告分开，保证“通过”来自真正运行的检查。

## 可以复用的经验

RAII 的正确性取决于资源销毁顺序。带后台线程的继承层次中，要先列出线程访问哪些派生成员，再决定在哪一层停止和 join；只在基类析构里等待，可能已经太晚。
