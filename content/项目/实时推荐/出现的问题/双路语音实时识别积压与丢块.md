# 双路语音实时识别积压与丢块

## 涉及文件

- `server/libs/slowlane/voice_chain/voice_chain.cpp`：PCM/ASR 两级工作线程、分源状态和排尾。
- `server/libs/slowlane/voice_chain/source_queue.hpp`：分源容量、轮询和停止控制。
- `server/libs/slowlane/voice_chain/cuda_dpdfnet.cpp`：固定 GPU 缓冲、I/O Binding 和 CUDA Graph。
- `server/libs/slowlane/voice_chain/denoiser.cpp`：去噪后端接入。
- `config/voice.webrtc.yaml`：实时处理和后端配置。
- `server/tests/voice_queue_tests.cpp`：容量隔离、公平性及关闭排空测试。

## 问题

双路音频能传到服务器，但识别越跑越落后，队列开始丢块。之前处理 90.2 秒录音约需 119 秒，单独去噪 RTF 约 1.24，说明这条流水线本身就跟不上输入。

RTF 是处理时间除以音频时长。RTF=1.24，表示处理 1 秒音频约花 1.24 秒；即使网络和队列完全正常，持续输入也会积压。

## 修改前

原来的同步调用可以简化为：

```cpp
void onAudio(const Envelope& audio) {
    // 在消费 P1 的线程里完成后面的工作。
    auto enhanced = denoise(audio);
    auto segments = vad(enhanced);
    for (const auto& segment : segments) {
        auto text = asr.transcribe(segment.samples);
        save(text);
    }
}
```

这段是流程示意，接口名已简化。一次 ASR 在运行时，线程无法继续消费后面的 PCM；CS2 的耗时又会影响 Oopz。另一个问题是去噪计算本身慢，即使把原函数搬到后台，RTF>1 仍会积压。

所以我分两部分改：先拆调度，再优化去噪执行，不能只加队列。

## 修改后

### 1. P1 只投递，PCM 和 ASR 分开执行

当前 VoiceChain 内部有两条工作线程和两级队列：

```cpp
SourceQueue<Envelope> pcm_queue{4};
SourceQueue<AsrJob> asr_queue{2};
std::thread processing_thread, asr_thread;
```

4 和 2 是每个来源的普通任务容量，不是所有来源合用的总容量。实时路径的 submit 只尝试入队，并记录拒收：

```cpp
const auto source = envelope.payload.value("audio_source", "mixed");
if (!pcm_queue.tryPush(
        source, envelope, envelope.payload.value("flush", false))) {
    count(envelope.session_id, source, "pcm_queue_drops");
    // 同时记录 latency log，保留会话、来源和序号。
}
```

PCM 工作线程执行去噪/VAD，VAD 产出的完整段再交给 ASR：

```cpp
void runProcessing() {
    while (!pcm_queue.drained()) {
        if (auto envelope = pcm_queue.pop()) safeAccept(*envelope);
        else expire();  // 此处省略实际代码中的异常处理。
    }
    // 关闭时继续 finish 各源剩余状态。
}

// speech() 中组装好 job 后：
if (!cfg.realtime) recognize(std::move(job));
else if (!asr_queue.tryPush(s.audio_source, std::move(job))) {
    count(s.session_id, s.audio_source, "asr_queue_drops");
}
```

ASR 线程独立取段并 recognize。一个来源的模型状态、pending PCM、VAD 状态分别保存；CS2 先 DPDFNet8 去噪，Oopz 直接 VAD。这里是共享 PCM 工作线程加一条 ASR 线程，不是两个来源各自同时运行一套 ASR。

### 2. 来源之间隔离容量，取任务时轮询

`SourceQueue::pop()` 中的轮询核心是：

```cpp
for (int i = 0; i < 3; ++i) {
    const auto index = (next_ + i) % 3;
    if (queues_[index].empty()) continue;

    auto value = std::move(queues_[index].front());
    queues_[index].pop_front();
    if (!value.control) --normal_[index];
    next_ = (index + 1) % 3;
    return std::move(value.item);
}
```

取走某源一个任务后，下次从下一个来源检查。缺源直接跳过，不等两路凑齐；某源占满自己的容量也不会占掉另一源的槽位。它提供按任务轮询的公平性，不保证每个来源得到完全相同的 CPU 时间。

停止控制与普通数据放在同源 FIFO 中，允许有限的额外控制容量，避免普通任务满了就无法提交排尾；不是给停止消息开一条能越过前面音频的捷径。

### 3. 用固定 GPU 地址执行 CUDA Graph

我把 CS2 去噪接入 `ort_cuda_graph`。创建 Session 时开启 CUDA Graph，并禁止去噪模型静默回退 CPU：

```cpp
options.AddConfigEntry("session.disable_cpu_ep_fallback", "1");
const char* keys[] = {
    "device_id", "enable_cuda_graph", "cudnn_conv_algo_search"
};
const char* values[] = {gpu.c_str(), "1", "HEURISTIC"};
// UpdateCUDAProviderOptions 后，AppendExecutionProvider_CUDA_V2。
```

GPU 输入谱、输出谱和两份循环状态只分配一次，再建立两套固定绑定：

```cpp
for (int i = 0; i < 2; ++i) {
    binding[i] = std::make_unique<Ort::IoBinding>(*session);
    binding[i]->BindInput(inputs[0].c_str(), spec);
    binding[i]->BindInput(inputs[1].c_str(), states[i]);
    binding[i]->BindOutput(outputs[0].c_str(), enhanced);
    binding[i]->BindOutput(outputs[1].c_str(), states[1-i]);
    run_options[i].AddConfigEntry("gpu_graph_id", std::to_string(i).c_str());
}
```

两套图分别固定 `state0 → state1`、`state1 → state0`。推理时在这两套绑定之间切换：

```cpp
cuda.transfer(spec.GetTensorMutableData<float>(),
              spectrum.data(), spectrum.size() * sizeof(float), 1);
session->Run(run_options[position], *binding[position]);
binding[position]->SynchronizeOutputs();
cuda.transfer(enhanced_spectrum.data(), enhanced.GetTensorData<float>(),
              enhanced_spectrum.size() * sizeof(float), 2);
position = 1 - position;
```

循环状态留在 GPU 上，不需要每次重新分配、重新绑定。FFT/IFFT 仍在 CPU，所以这条路径仍有谱的上传和输出读取，没有把它写成全程 GPU 或零拷贝。

### 4. 在实际工作线程预热，停止后排空

Graph 后端由 PCM 处理线程初始化，主线程等待初始化完成后才继续开放服务。构造中先执行两次 infer，捕获两种状态地址，再 reset，避免把预热状态带进真实音频。

结束会话时先完成媒体排尾，再让 PCM、VAD 和 ASR 处理完已接受的数据。`stopped` 可以报告转写 pending；最后写 `voice-summary.json`，再发布 transcription_complete。不能收到停采确认就认为所有文字已经生成。

## 为什么这样改

分线程以后，长时间 ASR 不再堵住 PCM 消费；分源有界队列限制内存和来源相互影响；CUDA Graph 固定执行图及地址，降低重复执行开销，使去噪吞吐真正超过实时输入。三者分别解决阻塞、容量隔离和计算速度，少一项都可能继续积压。

队列满仍然明确记账。一次零丢弃测试说明当次负载能跟上，不表示以后任何输入长度、分段频率都不会溢出。

## 验证

2026-10-26，暖机后的同源 10 秒对照：

| 指标 | 原 sherpa 后端 | CUDA Graph 后端 |
| --- | ---: | ---: |
| 处理时间 | 12.651 秒 | 4.537 秒 |
| RTF | 1.265 | 0.454 |
| 输入/输出样本数 | 160000/160000 | 160000/160000 |

输出最大绝对差约 `9.59e-5`，SNR 约 72.95dB，用来检查数值一致性。

70 秒跨机文件回放中，每源有效音频 68.38 秒，输入和处理样本都是 1094080；CS2 分段/转写为 3/3，Oopz 为 22/22，两级队列丢弃、处理错误、重复和时间断点均为 0。报告为 `var/realtime-20261026/final-acceptance.json`。这次是既有录音和截图的实时回放，不是新设备现场或识别准确率验收。

## 总结

这次我没有靠扩大缓冲掩盖延迟，而是把 PCM 和 ASR 拆开，用分源轮询队列隔离容量，再用固定 I/O 与 CUDA Graph 提高去噪吞吐。最终同时核对输入样本、处理样本、丢弃和转写数，确认当次双路输入确实处理完整。
